Themes for a successor

What the open backlog says about where Firstmate hurts today, read for someone designing Guildmaster rather than for someone triaging Firstmate.

The recurring classes of defect

Reading across all 488 open defects, the same handful of shapes recur far more than any specific bug does. None of these are one-off mistakes; each shows up in a different subsystem every time, which is why they read as classes rather than incidents.

1. Ownership and identity races under concurrency and restart

Two actors (main and the supervision branch, or a live worker and a relaunching one) each assume they are the only writer, and the system has no shared lock or identity check to prove otherwise. Examples: a reserved backlog lease is claimed by only one of the two actors that mutate data/backlog.md (#2983); a reused worktree-pool slot leaves an old task’s record pointing at it, so teardown refuses both tasks (#5231); a relaunch stops the old agent before the backlog gate can refuse, stranding a held task with no agent (#5136); fm_pid_alive treats a zombie process as live and preserves dead supervision ownership (#3620); status files carry no write-side identity at all, so a forged line can surface as crew-authored (#2962, flagged as a design flaw below). A from-scratch design should decide up front which state is single-writer by construction and which genuinely needs a lock, rather than discovering the boundary one race at a time.

2. Success is reported before it is true

fm-teardown.sh --force reports complete while the task branch ref survives (#4374); a squash merge strands stacked PRs and duplicate PRs on one branch go unnoticed (#4504); tasks-axi add --start can mark a row in-flight with no dispatch record and nothing ever corrects it (#4753); a merge gate treats an absent required check the same as a passing one (#5344, a design flaw). The common failure is a status line or exit code that asserts an outcome the system never actually verified.

3. A backend’s native state and Firstmate’s model of it disagree

Every terminal backend (Herdr, tmux, Pi, Codex, Grok, OpenCode, Orca) has its own idea of idle/working/done, and Firstmate’s classifiers have to infer that state from rendered terminal output rather than a real API in most cases. A compact Pi composer layout with one separator instead of two cannot be proven empty (#5445); an away-mode inject never delivers to an idle Grok pane because its composer reads unknown all night (#3436); dead Pi crewmates are reconciled as busy after a host reboot (#3545); Kimi turn-end hook markers are TOML comments that do not survive Kimi CLI config rewrites (#1064). This category (composer/idle-state detection plus backends and terminals) is large precisely because there is one shared, hard problem — proving a remote terminal’s state from a screen capture — solved once per backend instead of once.

4. Test and CI signal drifts out of sync with the code it checks

.github/workflows/ci.yml asserts an exact passing-test count (#4770); a fixture-only case fails specifically on macOS because a copied bash binary is SIGKILLed by code-signing (#3535); a serial test lane does not scrub inherited fleet-home overrides (#3536). None of these are wrong production behaviour; they are the safety net itself becoming unreliable, which is a maintenance-cost class distinct from the other three.

Most requested capabilities

Feature requests are a much smaller slice of the backlog (71 of 563, 12.6%), but they cluster tightly into three asks, in descending order of volume.

  1. Broader integration surface. By far the largest feature-request cluster, spread across several categories because it recurs at every layer: forge support (GitLab via glab #695, full GitLab parity #826, Forgejo/Gitea #4821), platform support (native Windows #504, #479, #170), and harness/terminal adapters (Copilot #604, Cursor Agent CLI #771, Junie CLI #4454, kiro-cli-chat #503, superterm #457, Reasonix #190, a hosted Grok Bot as captain #4098). The shape of the ask is consistent: Firstmate’s backend/forge abstraction is real enough that users keep proposing to slot one more implementation into it, which is itself a compliment to that abstraction and a signal about how many implementations a successor should expect to eventually carry.
  2. Quota, account and cost control. Multiple accounts for one provider in quota-aware dispatch (#4379), an opt-in per-home account pin (#4265), sleeping through a quota window instead of failing (#3062), per-task model selection for cost (#146), and a capacity-bounded backlog with an upstream-issue zone (#4466). Read together, these ask for dispatch to be a first-class, configurable policy rather than an implicit consequence of whichever account happens to be ambient.
  3. Pipeline and delivery configurability. A config-registered delivery mode instead of a fork (#5450, itself flagged as a design flaw), a soft cap with severity escape on no-mistakes review rounds (#3923), fan-out and cost ceilings with machine-checkable loop stops (#3632, filed twice: #3625), and letting the captain configure which skill runs at each workflow phase (#1244). The common thread is that delivery/review behaviour is currently hard-coded policy, and users keep asking for it to become declarative configuration instead.

Two categories account for 38% of every open ticket: worktree and task lifecycle (110) and backends and terminals (105). Counting which script a ticket’s body actually names, rather than which category it landed in, sharpens the same picture:

fm-spawn.sh — the script that launches a task — is named in more open tickets than any other file by a wide margin, with the watcher/wake chain (fm-watch.sh, fm-watch-arm.sh, fm-wake-lib.sh, fm-claude-stop-autoarm.sh: 128 mentions combined) as the second concentration. A successor should expect that launching a task correctly and noticing what a running task is doing are the two hardest, highest-traffic mechanisms in a system shaped like this one, and should budget design and test effort accordingly rather than treating them as plumbing.

These read as the mechanism doing exactly what it was built to do — the contract itself is what would need to change. They are the highest-value signal in this snapshot for a ground-up redesign, because a successor can design the contract out from the start instead of patching around it later.

Backlog hygiene, as evidenced by the tracker itself

Seven pairs of tickets (14 total, 2.5% of everything open) are exact-duplicate titles, all in the narrow number range 3624–3635 — consistent with one filing session submitting the same batch twice rather than independent reports converging:

  • #5230, #5229 — watcher wedge-escalates a healthy cursor worker blocked in a synchronous no-mistakes call
  • #3635, #3629 — tmux backend accepts prefix-matched targets and can steer a sibling pane
  • #3634, #3627 — task IDs are used raw across filesystem and regex deletion paths
  • #3633, #3626 — teardown landedness uses stale remote refs and ignores stash entries
  • #3632, #3625 — add fan-out and cost ceilings with machine-checkable loop stops
  • #3631, #3624 — byte-identical inherited config can generate repeated CONFIG_REREAD steers
  • #3630, #3628 — pending-reply recovery uses ambiguous destination and wrong-home escalation

This corroborates #4018 (“Backlog hygiene: open issues stay open past the merge/PR that resolves them, get handed out as unclaimed work”) and #3096 (decision-log number collisions across parallel workers): closing and de-duplication is itself a place this system under-invests, not just a nuisance in this snapshot.

Two in three open tickets already have a proposed fix

370 of 563 open tickets (65.7%) carry a ready-for-pr label (368 alone, plus 2 that carry both labels) and 22 (3.9%) carry existing-pr (20 alone, plus the same 2); only 173 (30.7%) carry neither. Read against the defect/feature split above, the picture is not a system whose problems are undiagnosed or unfixed — it is one where diagnosis and even a candidate patch routinely outpace review and merge capacity. A successor inheriting this shape should treat review throughput, not root-cause discovery, as the scarce resource to design for.

An unverified third-party report, read as data

#5269 reports a cluster of open, unmerged PRs (mostly from two accounts) introducing an unfamiliar “Jev”/“Jev System One” gating layer and a “Kun Cheng” external source shelf into sensitive-command handling and fleet automation, and separately notes that a same-named skill circulating elsewhere reportedly instructs an agent to fetch and follow externally-hosted instructions on every invocation. This snapshot repeats it here only as a filed report to a maintainer, exactly as the ticket presents it: unconfirmed, not investigated further by its own author, and not investigated, fetched, or acted on by this snapshot either. It is recorded because a successor’s PR-review and dependency-loading design should assume this class of attempt will be made against it too, not because anything in it has been verified.
