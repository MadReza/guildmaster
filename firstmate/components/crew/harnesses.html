Harness adapters

A harness is the agent CLI that runs inside a worker's pane: Claude Code, Codex, Pi, and ten others. An adapter is everything Firstmate must know to launch, observe, and control one of them. Firstmate dispatches only onto adapters it has verified, and "verified" has a precise, multi-owner meaning.

Read against Firstmate commit ada21f5b. Up: Crew. The skill's routing and wording belong to Prompts and skills; busy-state semantics belong to Supervision.

The rule

"The verified harnesses are claude, codex, opencode, pi, pi-signed, grok, kimi, cursor, and omp, plus muse, gemini, rovo, and agy for crewmates and scouts only; never dispatch on an unverified adapter" AGENTS.md:219. If a static config names an unverified adapter, Firstmate reports it and falls back only to a verified one AGENTS.md:220. It tells the captain the runtime is not verified, uses its own verified runtime for current work, and does not pause that work .agents/skills/harness-adapters/SKILL.md:25-31. The executable list is fm_control_harnesses bin/fm-control-lib.sh:64-69.

What "verified" means

A harness is not verified by being launchable. The skill's verification plan requires every owner to land together: "A value remains unreachable until its executable owner, portable regression, applicable credentialed live guard, and verification record land together" .agents/skills/harness-adapters/references/common/dispatch.md:27-33. The owners are spread across the codebase:

Each harness reference opens with its evidence date and version, for example "Busy hooks verified 2026-07-28 on Claude Code 2.1.220" .agents/skills/harness-adapters/references/harness/claude.md:3, or "Verified 2026-09-02 on Rovo CLI 202609.1.2 for crewmate/scout work only" .agents/skills/harness-adapters/references/harness/rovo.md:3. The references are "empirical knowledge for those executable owners", and never a second owner .agents/skills/harness-adapters/references/common/dispatch.md:18-25. For verifying a new CLI, the spawn's raw-launch escape hatch accepts any whitespace-containing string as a literal command, "only for a trivial supervised task" bin/fm-spawn.sh:154-155 .agents/skills/harness-adapters/references/common/dispatch.md:29.

Detection and static resolution

bin/fm-harness.sh prints the harness the first mate itself runs on. It combines two kinds of evidence: environment markers, which a child inherits and a multiplexer can replay stale, and process ancestry, "the structural fact about who actually owns the process tree, so it is what settles a disagreement" bin/fm-harness.sh:47-57. detect_own is the single place that combines them. Launches clear foreign markers so a worker is not misdetected as its parent (Launch prefixes).

With no explicit harness, resolution is static bin/fm-harness.sh:2-19:

  • fm-harness.sh crew: config/crew-harness, where absent or default means Firstmate's own harness.
  • fm-harness.sh secondmate: config/secondmate-harness, then config/crew-harness, then its own. That file may add a model and effort token on the same line. The split stays "DURABLE across every respawn" bin/fm-spawn.sh:146-154 bin/fm-spawn.sh:182-190.

When config/crew-dispatch.json exists, static resolution is off for crewmates and scouts and the harness must be passed explicitly. See Dispatch profiles.

The recorded harness is authoritative afterwards

"For recovery and control, use the exact harness= in state/<id>.meta; never infer it from a model or provider" .agents/skills/harness-adapters/SKILL.md:33. A task launched from a raw command records the command's basename, so fm_control_harness_family maps prefixes such as claude* to their adapter. pi, pi-signed, omp and agy must match exactly, and anything else "returns nonzero rather than being guessed into a family" bin/fm-control-lib.sh:79-103.

Model, effort, and provider

  • Scripts receive only concrete axes, never natural-language rules .agents/skills/harness-adapters/references/common/model-and-effort.md:8-9.
  • Record and omit. An effort outside the adapter's accepted set is written to effort= in the record but emitted as no flag, which "preserves launch success instead of passing a known-bad value". ultra is the exception and is refused outside its model scope .agents/skills/harness-adapters/references/common/model-and-effort.md:20-23.
  • Effort fallback. low for well-understood work, xhigh for ambiguous investigation, never max without explicit captain preference .agents/skills/harness-adapters/references/common/model-and-effort.md:12-18.
  • Harness is not provider. "harness=pi with model=xai/grok-* is Pi using xAI, not standalone Grok Build" .agents/skills/harness-adapters/references/common/model-and-effort.md:25-29.

What the adapter decides at runtime

  • Trust dialogs. Claude's workspace-trust dialog cannot be answered by key and is pre-registered by the spawn. agy's is pre-registered, and a post-launch gate backs it up. Cursor passes --trust, muse --yolo, grok avoids its picker by starting in the git root, Pi's is answered with Enter, and Codex shows one on the first run for a repository root .agents/skills/harness-adapters/references/common/control-and-recovery.md:19-25.
  • Completion. "Trust handling is complete only when inspection proves the target started processing its instructions; delivery success alone is not proof" .agents/skills/harness-adapters/SKILL.md:37.
  • No resume verb. Native resume is not deterministic across adapters, so relaunch trusts "instructions on disk, not a private session" docs/agent-control.md:54-56.
Finding: two link bases in one skill

The router says links inside nested references resolve "against the skill directory" .agents/skills/harness-adapters/SKILL.md:22. Most harness references follow that (../../../bin/…). gemini.md and agy.md instead use links relative to their own file (../../../../../bin/…), and claude.md and muse.md mix both styles. A renderer that resolves relative to the file breaks the first group; an agent following the router's rule breaks the second.
