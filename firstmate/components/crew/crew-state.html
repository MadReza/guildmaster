Current state vs events

A worker's status log records what happened, not what is true now. bin/fm-crew-state.sh answers "what is this worker doing right now?" deterministically, from the most authoritative source available, and reconciles the possibly stale log against it.

Read against Firstmate commit ada21f5b. Up: Crew. The status log format and verbs belong to Communication; the watcher that consumes this verdict belongs to Supervision.

The problem it solves

"state/<id>.status is an append-only, best-effort EVENT LOG. Crews append only wake-worthy transitions … and nothing when they silently resume, so tail -1 of that log reports the last EVENT, not the current STATE" bin/fm-crew-state.sh:4-11. A worker that reported needs-decision, got its answer, and went back to work still shows needs-decision as its last line. The supervisor contract therefore splits the two: status tails are "wake-event history", and current state needs targeted reconciliation AGENTS.md:247. Validation outcome is judged "by the resolved state line from bin/fm-crew-state.sh … never by shell liveness, the last status event, or a raw run record" AGENTS.md:387.

The output: one line

state: <working|parked|done|blocked|paused|failed|unknown> · source: <run-step|pane|status-log|remote-endpoint|none> · <detail>

It is "token-tight" so the first mate can read it every heartbeat bin/fm-crew-state.sh:22-25. The script is "Read-only and side-effect free", always exits 0 on a successful read, and exits 2 only on a usage error bin/fm-crew-state.sh:148-149. The first emit exits the script, so the first matching source decides bin/fm-crew-state.sh:192-197. Invocation: bin/fm-crew-state.sh <id>.

The decision order

Step 3: the pipeline run is authoritative

When a no-mistakes run is attributed to the crew, its step decides the state, "regardless of pane liveness", so "a finished crew whose endpoint has closed still reports its run-step state" bin/fm-crew-state.sh:284-287. Attribution is strict, and bin/fm-nm-run-lib.sh owns the rules:

  • "Branch name alone is not enough: a historical run on a reused branch whose head was rewritten or diverged must not be attributed" bin/fm-crew-state.sh:36-39.
  • A run that is executing (pending, running, fixing, ci) binds regardless of head, because the pipeline rebases and commits fix rounds in its own checkout. It stops binding once an explicit probe has shown the daemon is down, because a record left saying running by a dead daemon "is evidence from a dead instrument" bin/fm-crew-state.sh:40-54.
  • Every other run matches only when its head equals the worktree's HEAD or descends from it bin/fm-crew-state.sh:54-59.

For a passed run, a merge-poll retirement receipt or a forge read bounded to 5 seconds supplies PR detail; FM_CREW_STATE_NO_FORGE=1 skips the forge read, and a missing PR identity "yields an honest unknown, never an optimistic merged claim" bin/fm-crew-state.sh:17-21.

Reconciling a stale log

The log is read through status_current_line in bin/fm-classify-lib.sh, not tail -1. Open decisions survive unrelated events, and "continuation prose cannot hide a declaration" bin/fm-crew-state.sh:115-117 bin/fm-crew-state.sh:242-243. Against a live run:

  • A needs-decision or blocked line whose run has moved on is "deterministically stale and is flagged superseded".
  • A parked run plus a needs-decision line agree and read as parked.
  • A blocked: line reporting a refused or missing daemon socket stays blocked while it is the latest event. Other daemon or timeout claims "are superseded BECAUSE THE RUN IS ALIVE", and are answered "by steering the crew to reattach, not by escalating".

Source: bin/fm-crew-state.sh:115-132. The verb-to-state mapping has one owner, map_log_state bin/fm-crew-state.sh:227-240, and a trailing resolved: line never becomes state or detail bin/fm-crew-state.sh:1217-1232.

Unknown is never death

Without an attributed run, only positive evidence may read as gone. "a backend that failed to answer is unknown, never death". On tmux and Herdr, missing and dead from the recovery-grade classifier report unknown · none with "backend target gone". Any other probe failure reports "backend unreachable". Backends without a classifier keep the older rule that a failed capture means gone bin/fm-crew-state.sh:1145-1201. A remote secondmate whose host cannot be reached is "unknown-remote … (not proof of death)" bin/fm-crew-state.sh:245-280.
