Crew

Every worker Firstmate commands, and the scripts that create, steer the lifecycle of, inspect, promote, and retire one. The first mate never edits a project itself, so this area is how any project work gets done at all.

Read against Firstmate commit ada21f5b. Up: Level 2: Containers (the "Workers" and "Secondmate homes" containers).

What problem this area solves

Firstmate's supervisor contract forbids the first mate from editing projects: it delegates "coding, investigation, planning, bug reproduction, and audits to a crewmate you spawn and supervise, or to a secondmate whose registered scope fits" AGENTS.md:22, and it does "not edit, commit, or run state-changing commands under projects/ or in any project worktree" AGENTS.md:28. The crew area is therefore the only way work reaches a project. It has to give each worker a copy of the project nobody else touches, a terminal the captain can watch, a written contract it cannot misread, and a clean exit that never throws away unlanded work.

The design splits judgement from mechanics. The agent decides what to dispatch, with which profile and delivery contract. Guarded bash scripts do the dispatch, the lifecycle actions, and the cleanup, and each one refuses rather than guesses when an input it consumes is missing AGENTS.md:316.

The lifecycle in one paragraph

A task starts as a backlog item and a written brief. Firstmate resolves its profile and delivery contract, then calls fm-spawn.sh, which refuses unless every gate passes. The spawn gets an endpoint from the session backend and a clean, isolated worktree from Treehouse, publishes state/<id>.meta, moves the backlog row to In flight, and launches the harness on a launch brief whose first section is the worker role contract. The worker then reports only by appending to its status log. Firstmate reads current state through fm-crew-state.sh, steers through the inbox, and drives lifecycle through fm-control.sh. A scout can be promoted in place with fm-promote.sh. When a ship's work has landed, or a scout's report exists, fm-teardown.sh returns the worktree, closes the endpoint, removes the record, and closes the row. End-to-end trace walks one worker through all of it.

Where this area meets the others

  • The steering inbox, the status log format, and fm-send.sh belong to Communication. This area only names where they are created and destroyed.
  • The watcher, busy-state sources, stale detection, and away mode belong to Supervision.
  • The operational home, lock primitives, and restart model belong to Persistence.
  • Brief templates, AGENTS.md, and the skills that crew operations load (harness-adapters, stuck-crewmate-recovery, secondmate-provisioning) belong to Prompts and skills.
  • Delivery modes, PR readiness, merges, and clone refresh belong to Delivery.
  • tasks-axi, captain holds, and backlog handoff belong to Backlog and decisions.
  • Remote secondmates on SSH hosts belong to Remote.

Findings worth carrying forward

  • Names that mislead. bin/fm-lease.sh manages per-task supervision leases between the main and branch actors, not worktree leases bin/fm-lease.sh:2-9. bin/fm-landed-lib.sh decides what appears in "Recently Landed", not whether teardown may proceed bin/fm-landed-lib.sh:2-11. The real landed-work test lives inside bin/fm-teardown.sh.
  • Two worktree lease models. Secondmate homes use Treehouse's durable get --lease; crewmate slots use the interactive pane-driven treehouse get, whose lease lapses when the worker exits. Firstmate layers its own owner-claim file on top, and says moving crewmates onto the durable lease is "separate follow-up work" bin/fm-wake-lib.sh:1270-1286. See Worktrees.
  • Reclaim is Herdr-only by necessity. A tmux task record carries no socket identity, so a missing tmux window can never be proven gone and every lifecycle verb refuses it docs/agent-control.md:86-103.
  • A known leak is documented, not fixed. A refused Herdr rebind can leave a stray husk pane docs/agent-control.md:127-131.
  • Link bases disagree inside one skill. harness-adapters says nested reference links resolve against the skill directory .agents/skills/harness-adapters/SKILL.md:22. Most harness references follow that, but gemini.md and agy.md link relative to their own file and claude.md and muse.md mix both (details).
