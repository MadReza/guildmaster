Worktrees and slot claims

Every ship and scout works in a git worktree nobody else touches, leased from a Treehouse pool, proven isolated, reset to a fresh base, and marked with an owner claim so a recycled slot can never be torn down out from under its next worker.

Read against Firstmate commit ada21f5b. Up: Crew.

Who provides the worktree

Treehouse is the worktree provider for the four session-provider backends (tmux, herdr, zellij, cmux). The Orca app provides both the worktree and the terminal docs/configuration.md:136. That split shows in each backend's tool requirements: treehouse is required for tmux, herdr, zellij and cmux, and not for orca bin/fm-backend.sh:294-316. Firstmate installs a pinned Treehouse for CI through bin/fm-install-treehouse.sh docs/herdr-backend.md:32-34.

A Treehouse slot has a fixed <pool>/<slot>/<repo> layout. Firstmate treats a path as a pool slot only when <pool>/treehouse-state.json exists and the slot shares the project's git common directory: "an ordinary linked worktree is not evidence that Treehouse owns it" bin/fm-wake-lib.sh:1253-1268.

Allocation: pane-driven treehouse get

Firstmate never calls Treehouse from its own process to allocate a crew slot. It types the text treehouse get into the new task pane, which leaves the pane's shell sitting in the leased slot, and then reads the pane's current directory to learn which slot it got bin/fm-spawn.sh:3842-3845. This has two consequences the code works around:

  • A cwd read is only a snapshot. While treehouse get is still fetching, the pane reports the repository's primary checkout as its cwd. Some tmux and WSL setups briefly report an unrelated stale path. So a candidate is accepted only after two consecutive reads agree, and every read is screened by the isolation predicate first bin/fm-spawn.sh:3845-3876.
  • The lease is a process lease. The interactive get records only a live process lease (owner pid plus start time). That "answers 'is anything running here', never 'which task owns this'", and it lapses the moment the worker exits bin/fm-wake-lib.sh:1270-1286. Hence the owner claim below.

The poll runs for up to 60 seconds. At the deadline it refuses and names the last path seen and why it was rejected: "treehouse get did not enter an isolated worktree within 60s (last seen '…': …)" bin/fm-spawn.sh:3877-3900.

The isolation assertion

The contract: "Ship/scout spawns refuse to launch unless the resolved task path is a real git worktree root distinct from both the spawning project and its repository's primary checkout, including when the spawning project is a linked worktree" bin/fm-spawn.sh:202-211. The supervisor contract makes a failed assertion stop the task AGENTS.md:330. spawn_worktree_isolated applies four tests in order, each with a named reason bin/fm-spawn.sh:2855-2904:

  1. The path is a readable directory.
  2. It is inside a git worktree, and it is that worktree's root, not a subdirectory.
  3. It is not the spawning project itself.
  4. Its git dir is not the project's common git dir, which is what the primary checkout uses. "A linked spawning home has a different top-level, but the same common dir, so comparing only the two working directories cannot protect primary."

Every comparison uses physically resolved paths, because a backend's cwd read can report /private/tmp where the project path says /tmp. Without that, the guard could misfire in both directions bin/fm-spawn.sh:2809-2819. An empty toplevel is never passed to cd, because bash before 5.3 treats cd "" as success and "would resolve to fm-spawn's OWN cwd" bin/fm-spawn.sh:2869-2873.

The assertion is proven only at launch, so the pane also gets export FM_TASK_ID=<id>. bin/fm-test-run.sh then refuses to execute the behaviour suite from the primary checkout inside a worker bin/fm-spawn.sh:212-217 bin/fm-test-run.sh:98-105. Worker briefs repeat the check as their first setup step ("Verify isolation before anything else"), which is also the first step of a promoted scout's instructions bin/fm-promote.sh:183.

A fresh base, never a stale one

"Only after this isolation check, every fresh ship or scout requires a clean task worktree" bin/fm-spawn.sh:218-225. freshen_spawn_worktree_base bin/fm-spawn.sh:2969-3016:

  • refuses a dirty slot, "refusing to discard uncommitted work";
  • when an origin is configured, fetches it, runs remote set-head origin --auto, fetches the default branch, hard-resets to origin/<default>, and verifies HEAD equals that commit;
  • when no origin is configured, skips the remote check and launches from the clean current HEAD, which is how origin-less local-only projects work;
  • refuses on any fetch, head-resolution, or reset failure "rather than risking a PR based on stale history".

A relaunch reuses the recorded worktree "without fetching or resetting its base" bin/fm-spawn.sh:223-224.

Stale submodules. A pooled slot whose only change is a submodule sitting on an older pin is still refused, but is reported as a stale checkout naming each submodule and both pins. That diagnosis is given only when the checked-out submodule commit is contained in one of its remotes, and no remedy command is printed, because the containment test reads local refs only and "a stale remote-tracking ref can therefore make an unpushed commit look contained" bin/fm-spawn.sh:226-234 bin/fm-spawn.sh:2914-2953.

The project-identity lock

Allocation and return must not interleave, or a slot could be handed to a new task before the old owner's record is gone. One lock per project serializes them across every Firstmate home on the machine bin/fm-wake-lib.sh:1223-1251:

  • It lives in the local root home's state/ as .treehouse-project-<hash>.lock. The root is found by walking .fm-secondmate-parent bindings upward; a remote parent ends the walk, because a lock on this filesystem cannot be observed across machines bin/fm-wake-lib.sh:1184-1221.
  • Its identity is the project's resolved origin URL, so separate clones of one origin share it. An origin-less project falls back to its worktree top.
  • A fresh spawn takes it before allocation and holds it through record publication. Teardown holds it while proving and returning a slot. Contention refuses on both sides bin/fm-spawn.sh:130-145 bin/fm-teardown.sh:122-130.

Slot-owner claims

The claim is Firstmate's own answer to "whose slot is this?". It is a small file at <pool>/<slot>/.fm-slot-owner, beside the checkout rather than inside it, "so claiming a slot can never dirty the copy teardown's landed-work checks inspect" bin/fm-wake-lib.sh:1288-1298. It holds two lines, task=<id> and home=<path>, and it is written atomically by rename bin/fm-wake-lib.sh:1300-1317.

Claim stateMeaningTeardown does
mineclaim names this taskfull cleanup of the slot, then drops the claim
otherslot was reassignedwarns, names the claimant, finishes only this task's own records; no kill, inspection, branch removal, or return in that slot
absenttaken before claims existed, or already returnedkeeps the older record-scan protection only
unsafeclaim file exists but cannot be readrefuses; "never remove it, since an absent claim proceeds"

Sources: bin/fm-wake-lib.sh:1319-1356, bin/fm-teardown.sh:2326-2366, bin/fm-teardown.sh:95-117.

The spawn writes the claim under the project lock, straight after the isolation check, and a slot it cannot claim refuses the spawn "rather than launching a worker whose slot teardown could later release out from under its successor" bin/fm-spawn.sh:3904-3922. An abort before publication drops its own claim; an abort after it leaves the claim for the next spawn to replace bin/fm-spawn.sh:137-145. The release never removes another task's claim bin/fm-wake-lib.sh:1357-1366.

Claims are the second of two protections. Before any cleanup, teardown also requires record exclusivity: no other task record in this home or any locally registered home may name the same live path in worktree= or home= bin/fm-teardown.sh:81-94 bin/fm-teardown.sh:2272-2324. The record scan cannot prove this task is still the owner, because the next owner may have left no reachable record. The claim can.

Secondmate homes use the durable lease

A secondmate home can itself be a Treehouse worktree of the Firstmate repository. bin/fm-home-seed.sh <id> - acquires it with treehouse get --lease --lease-holder <id>, which "durably leases the worktree under the secondmate <id> so the home survives with no live process and is never recycled until the lease is released with 'treehouse return'" bin/fm-home-seed.sh:5-10 bin/fm-home-seed.sh:390-400. Retiring such a secondmate releases that lease; if the return fails, teardown leaves the home and state in place "instead of hiding a still-held lease" bin/fm-teardown.sh:160-163.

Open item in the source

Crewmate slots do not use the durable lease, and the claim file exists to cover that gap. The code records moving crewmate spawns onto the durable lease as "separate follow-up work" bin/fm-wake-lib.sh:1285-1286. The source does not say whether the claim would then be retired.

Return at teardown

Teardown returns a slot with treehouse return --force, run from the project directory because "treehouse resolves the pool from the working directory". A index.lock ... File exists failure is retried, and a lock is removed only when it is provably stale: no lsof holder and older than FM_STALE_WORKTREE_LOCK_AGE_SECS, 30 seconds by default. "the fix is patience, not rm" bin/fm-teardown.sh:195-224 bin/fm-teardown.sh:1704-1778. See Teardown.
