Dispatch profiles

A profile is the concrete harness, model, and effort a worker is launched with. Firstmate chooses it at intake from natural-language rules and live quota evidence. Scripts only ever receive the resulting three flags, and fm-spawn.sh refuses to launch without them when rules exist.

Read against Firstmate commit ada21f5b. Up: Crew. Related: Harness adapters.

Judgement in the agent, flags in the script

config/crew-dispatch.json is an optional, local, gitignored file of natural-language rules. "The shell scripts do not match those rules; firstmate chooses the best matching rule with judgment … and passes only concrete --harness, --model, and --effort flags to fm-spawn.sh" docs/configuration.md:451-455. The script enforces that the consultation happened: while the file exists, a crewmate or scout spawn without an explicit harness refuses docs/configuration.md:455-457 bin/fm-spawn.sh:2088-2090. Secondmates are exempt and keep their config/secondmate-harness pin.

How a profile is chosen

The rules file

docs/configuration.md is "the single owner of the canonical schema" docs/configuration.md:458. The shape docs/configuration.md:462-478:

{
  "rules": [
    { "when": "<natural-language condition>",
      "approval": "captain",
      "floor": { "scope": "…", "min_percent": 20, "provider": "…" },
      "use": [ { "harness": "…", "model": "…", "effort": "…", "provider": "…", "floor": {…} } ],
      "why": "<rationale>" }
  ],
  "default": [ { "harness": "…", "model": "…", "effort": "…" } ]
}
  • when and use are required per rule; rules may be empty for a default-only setup. use and default each take one profile or a non-empty array, and every profile needs harness docs/configuration.md:480-483.
  • approval, floor, and profile provider are enforced only by typed resolution. "without that opt-in they are inert", and Firstmate reads them as hints docs/configuration.md:484.
  • An unsupported effort is recorded as effort= but omitted from the launch flags; ultra refuses instead docs/configuration.md:504-505.
  • Bootstrap validates the file with jq and reports CREW_DISPATCH: invalid config/crew-dispatch.json - …. "malformed configuration must be reported and corrected rather than selected around" docs/configuration.md:507-512.
  • Secondmate homes inherit the file, so their own crewmates follow the same rules docs/configuration.md:513.

The shipped example routes current-events work to grok, trivial edits to claude with haiku at low, and big ambiguous work to an array of a Claude and a Codex profile. Its default is an array of Codex and Pi profiles docs/examples/crew-dispatch.json:1-26.

Resolving an array

An array is "an implicit quota-aware choice" docs/configuration.md:502. The first mate owns it alone: it starts from quota-axi's default TOON at that intake and ranks by spendPriority "as the one quota-perspective ranker after the skill's eligibility, reasoning-class, and runway-feasibility gates" AGENTS.md:225. The quota-array-dispatch skill owns the procedure:

  1. Eligibility. Only concrete contradicting evidence blocks a candidate, such as a catalog proving the model unsupported. Missing quota or authentication facts are "disclosed uncertainty that keeps a candidate eligible, never a credential or login escalation" AGENTS.md:228-229.
  2. Reasoning-class fit. "Never use spendPriority or remaining quota to silently replace that class" .agents/skills/quota-array-dispatch/SKILL.md:97-101.
  3. Runway feasibility. A window that will run out before the likely completion fails, "even when that candidate has the highest spendPriority" .agents/skills/quota-array-dispatch/SKILL.md:103-110.
  4. Rank. Highest known spendPriority wins. Unknown is never treated as zero or healthy. "Genuine ties: stop and report every tied candidate for captain choice", never by array order or harness name .agents/skills/quota-array-dispatch/SKILL.md:112-130.

Every candidate must be accounted for visibly with its evidence; "never omit a candidate, guess, fall back silently, or call the result quota-informed without them" AGENTS.md:226.

Typed resolution (opt-in)

bin/fm-dispatch-resolve.sh turns the rule match into one tool call. It is off unless TYPESAFE_API_KEY is set in the environment or the home's .env. Off means one dispatch-resolve: off line, exit 0, and no network call bin/fm-dispatch-resolve.sh:8-14. When on, it sends the project name and the whole brief to typesafe.ai's Jev model as one Choice question over every rule's when. "The model never sees quota, catalogs, approvals, why, or use". Everything after the answer runs in jq: the confidence floor of 0.6, approvals, floors, one quota-axi --json snapshot, and the spendPriority argmax bin/fm-dispatch-resolve.sh:16-31 docs/configuration.md:547.

A deliberate gap

"By accepted design, a clear result does not enforce catalog/authentication, reasoning-class, or completion-runway gates" docs/configuration.md:542. That is why Firstmate keeps the right to override it.

The worker-side helper

bin/fm-quota-choose.sh picks the first quota-eligible candidate from an ordered list, using an already-captured snapshot. Its header records a known limitation: it maps each harness to one primary provider family, so a Pi or OpenCode candidate running another provider's model "is checked against the wrong quota row". Authoritative multi-provider routing stays with AGENTS.md and the skill bin/fm-quota-choose.sh:2-38.

Effort when nothing specifies it

The fallback belongs to harness-adapters: explicit captain or configured effort wins. Otherwise "low for well-understood explicit work, xhigh for ambiguous investigation or design, intermediate levels proportionally, and never max without explicit captain preference" AGENTS.md:236-237.
