Pi supervision branch

An alternative shape for the same loop: on a Pi primary, a second conversation inside the same pi process — the supervision branch — handles eligible wakes itself and merges each outcome back into the captain's transcript, so routine fleet traffic never occupies the captain's conversation.

Read against Firstmate commit ada21f5b. Up: Supervision. Contract owner: docs/pi-supervision-branch.md; consume side: docs/watcher-continuity.md:69-98.

What changes and what does not

"Fleet supervision on the Pi primary harness runs on a second conversation - the supervision branch - inside the same pi process as the captain's chat" (docs/pi-supervision-branch.md:8). The watcher, the queue, the drain, and the acknowledgement contract are unchanged; what changes is which conversation receives a wake and runs the drain. It is Pi-only by construction: the branch lives in .pi/extensions/fm-branch-supervision.ts, "which only a Pi primary ever loads", and the bash-side additions "are inert in a home with no branch state" (docs/pi-supervision-branch.md:16-21). omp, though Pi-derived, is out of scope: "every actionable wake is delivered to this conversation, exactly as on Claude" (docs/supervision-protocols/omp.md:26).

Which rows the branch may take (attended)

  • Eligible: task-local signal and stale rows that resolve to a known task, plus fleet-wide heartbeat reviews the cheap bash scan already flagged (docs/pi-supervision-branch.md:9-11).
  • Main-only: every check row ("merge-confirmation polls, Relay mentions, credential/auth failures, and every other legitimately main-only class"), and every watcher-failure alarm, "because only main can repair the watcher cycle" (docs/pi-supervision-branch.md:26).
  • Decision-owned: a row whose payload the watcher marked needs-decision:, and a stale row whose task has an open needs-decision or a current captain-held declaration. "Any signal or stale trigger containing a decision-owned task goes wholly to main", and an unread decision keeps later triggers for that task on main until it is read (docs/pi-supervision-branch.md:28-32).
  • Unsafe: "An unresolvable row makes the scan unsafe and returns the whole wake to main" (docs/pi-supervision-branch.md:11).

The branch recomputes eligibility immediately before prompting and publishes the exact row set through bin/fm-wake-grant.sh, refused if main already claimed any requested row (docs/pi-supervision-branch.md:65-69, docs/watcher-continuity.md:77). A heartbeat review is all-or-nothing: the branch "takes every branch-ownable unread row or none of them", but a co-present check row no longer defers it to main (docs/pi-supervision-branch.md:131-143).

After rows are claimed, "a branch prompt counts as handled only when fm_branch_report appends a durable outcome before that prompt settles"; a provider error or a settled prompt with no report releases the grant back to the watcher (docs/pi-supervision-branch.md:46). Reports are scoped to the tasks the prompt's rows resolve to, so "a task remembered from an earlier wake cannot become a delivered outcome" (docs/pi-supervision-branch.md:47).

Two-stage filter and outcome delivery

"Stage one is unchanged: the bash watcher absorbs everything provably fine at zero token cost. Stage two is the branch's verdict on each handled event": routine becomes a rendered note with no follow-up turn; captain becomes a versioned fm-branch-visible-outcome custom session entry that "persist[s] in the transcript but do[es] not enter model context", with the store sequence as idempotency key (docs/pi-supervision-branch.md:108-115). Display is only half of it: every unprocessed captain row is handed to main in one hidden fm-branch-process request, and "Main closes it only by calling fm_branch_processed with the highest sequence the request listed"; "an unrelated reply, an empty reply, or a reply that paraphrases the outcome leaves the sequence unprocessed" (docs/pi-supervision-branch.md:116-124).

The durable outcome store, bin/fm-branch-outcome.sh, is append-only; "Outcomes are written to the store before delivery to Pi", and a captain row advances the read cursor only after its matching visible entry exists (docs/pi-supervision-branch.md:55-59). The drain's STATUS OUTCOME BACKSTOP section catches a task whose newest captain-facing event has no covering outcome (docs/pi-supervision-branch.md:86-96).

What the branch knows

  • Main's captain and assistant text is mirrored into the branch as read-only fm-main-mirror messages; tool calls, operational injections, and the branch's own merged notes are not (docs/pi-supervision-branch.md:100-106). An authorization addressed to main "does not relax the branch's role limits".
  • Each main session start opens a new branch conversation, "That keeps the branch reasoning from the current generated prompt and the current main dialog rather than from weeks of accumulated thread" (docs/pi-supervision-branch.md:38-42).
  • The branch system prompt, bin/fm-branch-prompt.sh, is byte-stable per firstmate version for provider prompt caching; "any later dynamic content in the branch prefix silently removes most of the cache benefit" (docs/pi-supervision-branch.md:145-152).

Failure behaviour

  • Two consecutive provider errors latch the branch broken; main keeps every wake for a five-minute cooldown, then one wake probes, doubling the cooldown up to one hour on each failed probe (docs/pi-supervision-branch.md:49-52).
  • Delivery runs off Pi's render thread through an explicit serialized queue, with generation and lock-ownership rechecks around every await so "a session replaced mid-delivery fails the next recheck rather than acting into the session that replaced it" (docs/pi-supervision-branch.md:72-84).
  • A known residual: a routine note whose cursor write fails after delivery is sent once more, tracked as a follow-up (docs/pi-supervision-branch.md:58-59).
  • Leases (bin/fm-lease-lib.sh) stop main and branch changing one task at once; the threat model is deliberately "CONFUSED-AGENT-GRADE", not adversarial (docs/pi-supervision-branch.md:60-62).

Postures on Pi

On Pi the away daemon is never launched; "the watcher is the single owner of supervision in both postures, and a leftover state/.afk flag declines nothing" (docs/pi-supervision-branch.md:156-158). While state/.afk-contract exists (docs/pi-supervision-branch.md:160-176):

  • every actionable row is branch-eligible, including checks, decision-owned rows, and heartbeats; the broken-queue vetoes stay;
  • main is parked and reached only for watcher-failure alarms and wakes the branch declines;
  • each wake ends with a fixed POSTURE: AWAY tail plus the record's read-back, so the prompt prefix stays byte-stable;
  • captain-verdict outcomes accumulate without a processing turn until the record is archived;
  • main's standing authority relocates to the branch "and nothing more", only through scripts that opt in while bin/fm-afk-contract.sh validate succeeds: bin/fm-pr-merge.sh merges only a PR green at its live head and refuses --allow-red, bin/fm-spawn.sh dispatches only queued work within the spend cap, bin/fm-send.sh --resolve-key answers pre-answered decisions, and bin/fm-merge-local.sh is never relocated.

"Being away changes how the captain is informed and what happens at a captain-owned decision point, never firstmate's authority set" (docs/pi-supervision-branch.md:178-180). Merge authority itself is owned by Delivery.
