Durability argument

What survives a crashed watcher, an interrupted handling turn, or a restarted session — and what deliberately does not — follows from four ordering rules that every part of the supervision area obeys.

Read against Firstmate commit ada21f5b. Up: Supervision. This page assembles the argument from the component pages; each claim cites the code that carries it.

The four rules

  1. Enqueue before suppress. A durable row is written before any marker records the event as reported. The watcher appends and only then advances .seen-*, .stale-*, or surfaced offsets (bin/fm-watch.sh:2552-2584, bin/fm-watch.sh:2853-2861); the away daemon relies on exactly this: "a crash/restart/missed injection is recovered on the next fm-wake-drain.sh" (bin/fm-supervise-daemon.sh:35-40). Where a marker bounds a repeat, it is written after the append succeeds, because "a marker written ahead of a failed append outlives it, and the next sighting would then absorb the retry" (bin/fm-watch.sh:1219-1224, bin/fm-watch.sh:1587-1595).
  2. Evidence before the row. Every append publishes downtime to the recovery marker before incrementing the sequence and writing the row (bin/fm-wake-lib.sh:1852-1863); a stolen watch lock publishes downtime before the stale lock is removed (bin/fm-wake-lib.sh:1010-1016).
  3. Acknowledge after handling. Rows leave the queue only through --ack-through, run after handling; "interruption before that acknowledgement deliberately leaves the work durable for idempotent re-handling" (AGENTS.md:433).
  4. Detect from persisted state, not from time. Signal detection compares persisted signatures, "so signals that land while no watcher is running are caught by the next one"; check and heartbeat schedules are file mtimes (bin/fm-watch.sh:1695-1715).

Underneath all four: records are replaced with a temp file and mv (bin/fm-wake-lib.sh:647-663), locks record a pid plus a process identity so a recycled pid never authenticates a dead owner (bin/fm-wake-lib.sh:139-174), and a dead owner's lock is stolen under a .steal mutex (bin/fm-wake-lib.sh:933-1031).

What is deliberately not durable

  • Absorbed wakes. A benign wake advances its markers and writes only to state/.watch-triage.log, "never relied on, safe to delete" (AGENTS.md:157). If the absorb was wrong, the heartbeat backstop re-scans every status log past the surfaced offset (bin/fm-watch.sh:1954-1963), and a stopped worker's static pane surfaces through the staleness backbone.
  • Diagnostic ledgers. The triage log, the cycle log, and the delivery ledger are size-capped and "not a supervision dependency" (bin/fm-watch-arm.sh:90-92).
  • A routine Pi branch note may be delivered twice when its cursor write fails; it is not lost (docs/pi-supervision-branch.md:58-59).

Open questions

Host reboot

No supervision document addresses a machine reboot directly. Everything the watcher needs to resume is under state/, and identity-matched locks cannot be satisfied by a recycled pid after boot, so the file-level argument above carries over. Whether a worker's recorded endpoint survives depends on the backend (a tmux server does not survive a reboot), which is Crew's area; the source here does not settle it.

Who restarts a dead away daemon

The daemon survives its own watcher's crashes, but nothing in the scripts read here relaunches the daemon itself. The path back is the model: at session start "If state/.afk is present, load /afk" (AGENTS.md:254), the digest "reports the posture … so a restart re-enters the posture from the record, not from memory" (.agents/skills/afk/SKILL.md:59), and bin/fm-afk-launch.sh start is idempotent and first closes "a recorded-but-dead terminal" by id (bin/fm-afk-launch.sh:50-54). Mid-session, only the turn-end guard's continued blocking signals the loss. How quickly a dead daemon is noticed between turns is therefore not bounded by anything in the source.
