Watcher continuity

The watcher ends after every actionable wake, so something must start the next cycle every time. Firstmate moved that duty out of the model's memory and into per-harness hooks and extensions, all of which go through one verifying wrapper, bin/fm-watch-arm.sh.

Read against Firstmate commit ada21f5b. Up: Supervision. Contract owner: docs/watcher-continuity.md.

The principle

"The watcher remains intentionally one-shot: one actionable reason closes one watcher cycle. Must-work continuity now lives above that process boundary instead of depending on the model remembering a re-arm step" (docs/watcher-continuity.md:3-4). On the harnesses where that is fully true, "The model no longer re-arms after ordinary wakes" and "No PreToolUse hook denies fleet commands based on watcher status" (docs/watcher-continuity.md:45-46).

The arm wrapper: fm-watch-arm.sh

Every harness path reaches the watcher through this script, which exists to make one claim honestly: a watcher is running for this home. Its header warns why a plain background job is not enough: "NEVER fire it and forget with a shell & inside another call: that backgrounded child is reaped when the call returns, leaving NO watcher running and a false 'already running' off the dying process. That exact mistake silently took supervision down for ~30 minutes" (bin/fm-watch-arm.sh:14-17). It must therefore run as the harness's own tracked background task, or inside a hook-owned process tree.

"It NEVER reports started/attached/healthy off a stale beacon or a dead/reused pid" (bin/fm-watch-arm.sh:35-37). The single honesty gate is fm_watcher_healthy: a live pid, whose lock records this home, this watcher path, and a process identity that still matches, with a beacon younger than the grace (bin/fm-wake-lib.sh:139-174, bin/fm-watch-arm.sh:236-249).

Never a clean empty success

"bin/fm-watch-arm.sh never returns a clean empty success" (docs/watcher-continuity.md:102). An adapter that saw exit 0 with no output could mistake a lost cycle for a no-op, so every close is resolved:

  1. an actionable reason is printed as is;
  2. a clean exit with no reason waits for a verified successor and attaches to it;
  3. failing that, the arm consults the watcher's bounded delivery ledger, state/.watch-deliveries.log, which wake() writes with the watcher's pid and process identity before the lock is released; a matching record lets the arm report the delivered reason "even after its durable wake was handled and acknowledged, while an unrelated queue producer or a recycled PID cannot satisfy the match";
  4. only then FAILED - cycle ended without an actionable reason.

Sources: bin/fm-watch-arm.sh:272-339, bin/fm-watch-arm.sh:490-541, bin/fm-push-transition-lib.sh:43-74, docs/watcher-continuity.md:103-108.

Modes

default (arm)
Attach if a healthy watcher exists, otherwise fork and verify one (bin/fm-watch-arm.sh:433-443).
--restart
Stop only the pid in this home's lock after an identity check, wait up to 5 s for it to exit, then own a fresh cycle; a stale recorded lock is cleared through the recovery marker. "NEVER pkill -f bin/fm-watch.sh: that pattern matches every firstmate home's watcher" (bin/fm-watch-arm.sh:54-60, bin/fm-watch-arm.sh:410-431).
--handling-delivered G --watcher-pid P
Confirms that a successor watcher is live and matched, and moves the recovery marker into handling for generation G (bin/fm-watch-arm.sh:403-408). Used by the Pi, omp, and OpenCode adapters before they deliver a wake (.pi/extensions/fm-primary-pi-watch.ts:618, .opencode/plugins/fm-primary-watch-arm.js:201).
FM_WATCH_PREDECESSOR_ARM_PID
Set by persistent adapters; starts the child with FM_WATCH_HANDLING_SUCCESSOR=1 so it does not re-announce downtime, and links the predecessor's cycle-log record to its successor (bin/fm-watch-arm.sh:187-223, bin/fm-watch-arm.sh:481-486).

The lifecycle ledger

One tab-separated record per observed cycle in state/.watch-cycle-exits.log: arm and watcher pids, origin, start and end times, exit code and signal, classified reason, beacon age, lock identity before and after, and successor disposition, capped by FM_WATCH_CYCLE_LOG_MAX_BYTES (256 KiB) and FM_WATCH_CYCLE_LOG_KEEP_LINES (1000). It "is diagnostic evidence, not a supervision dependency" (bin/fm-watch-arm.sh:82-185, docs/watcher-continuity.md:110-113).

Who re-arms, per harness

The supervision model of the primary harness decides what "healthy" means mid-turn (bin/fm-wake-lib.sh:186-216): autoarm (Claude, Cursor: the watcher runs only between turns), extension (Pi, pi-signed, omp: the extension tears the watcher down and respawns it on each wake), persistent (everything else: a tracked live process). The session-start block for the detected harness is rendered from docs/supervision-protocols/ by bin/fm-supervision-instructions.sh; how that prompt is assembled belongs to Prompts and skills.

Ordering: protect the fleet before the model handles the wake

Pi, omp, OpenCode — "Option B"

Pi adds generation ownership across same-process session replacement (/new, /resume, /fork, reload): shutdown flips the durable extension marker from active to handoff but keeps the arm child alive until the next owning session start commits its replacement, and pending actionable closes ride a state-scoped handoff file, state/extensions/pi-primary-watch/session-replacement-actionable.json (.pi/extensions/fm-primary-pi-watch.ts:1-24, docs/watcher-continuity.md:11-14). A follow-up "counts as delivered once Pi accepts it, never once the model reads it" (docs/watcher-continuity.md:14). omp differs: it retires the predecessor at shutdown and, having no shutdown reason, persists the handoff on every shutdown with a pending close (docs/watcher-continuity.md:15).

Claude — successor at the next Stop

The gap between steps 1 and 5 is the one window on Claude with no watcher running. It is covered twice: any event in it is detected by the next watcher, because signal detection compares persisted signatures rather than a start time (Watcher); and the turn-end guard refuses to let the handling turn end without a watcher or an open claim.

Stated limits

  • "No zero-latency guarantee is claimed because lock verification, watcher startup, and bounded retry delays remain deliberate safety work" (docs/watcher-continuity.md:135).
  • OpenCode support "targets persistent TUI sessions rather than headless opencode run" (docs/watcher-continuity.md:136).
  • "No adapter starts a replacement with shell &" (docs/watcher-continuity.md:51).
  • "Only the watcher process touches state/.last-watcher-beat; no helper process can make a wedged watcher appear healthy" (docs/watcher-continuity.md:116).
An arm that forks with &

The arm wrapper's own launch is "$WATCH" >"$child_out" & (bin/fm-watch-arm.sh:481-486). This does not contradict the "never shell &" rule: the child is then verified and waited on for its whole life ("we wait on it, so killing this arm … tears the watcher down too", bin/fm-watch-arm.sh:445-448). The rule forbids fire-and-forget inside another call, not a tracked child.
