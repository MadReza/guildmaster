End-to-end trace

One realistic path through the whole area: a Claude crewmate reports that its pull request is ready while the Claude primary sits idle between turns, and the report travels from the worker's status log to a handled, acknowledged wake and a freshly armed next cycle.

Read against Firstmate commit ada21f5b. Up: Supervision. Assumptions: normal (attended) mode, no state/.afk, default knobs, one task t1 on a tmux backend. Row numbers and the generation G are illustrative.

Starting state

  • The primary's previous turn ended; its Stop auto-arm claimed generation N and is foregrounding bin/fm-watch-arm.sh, whose child bin/fm-watch.sh holds state/.watch.lock and touches the beacon every 15 s (Claude Stop auto-arm).
  • state/.watcher-down reads acked:handling:F from the last handled wake, and the queue is empty.
  • Crewmate t1 is a Claude worker whose .claude hooks were written by bin/fm-spawn.sh (bin/fm-spawn.sh:4078-4091).

How the same path differs elsewhere

  • If the supervisor was mid-turn when t1 reported, no watcher was running (the Claude model runs the watcher only between turns); the rows would be written by cycle N+1 after the Stop, not before.
  • If the turn was interrupted after step 3, the rows stay queued and pending:handling:G stays open; the next watcher start sees handling and waits, and the next drain presents the same rows again (Durability).
  • On Pi, the extension would start cycle N+1 before delivering the wake, and a task-local signal like this one would normally go to the supervision branch rather than the captain's conversation (Continuity, Pi branch).
  • Under /afk, the watcher would queue and exit without absorbing, and the daemon would drain, classify the done as an escalation, acknowledge, and batch it into a digest (Away and quiet).
  • If t1 had written only working: while a no-mistakes step was running, step 5 would find no captain-relevant span, the working proof would pass, and the wake would be absorbed without ever reaching the model (signal triage).
