Turn-end and pull guards

Two guards stop supervision from lapsing unnoticed: a pull guard that shouts inside whatever supervision command runs mid-turn, and a push guard that fires at every primary turn end and refuses to let the turn close with work in flight and no live watcher.

Read against Firstmate commit ada21f5b. Up: Supervision. Contract owner: docs/turnend-guard.md, "the authoritative current contract for the 'no turn ends blind' primary backstop" (docs/turnend-guard.md:3).

Why two guards

"fm-guard.sh (bin/fm-guard.sh) is pull-based: it only warns when some other supervision script happens to run. A primary session that ends a turn without resuming its harness supervision protocol, and then never runs another fleet-touching command itself, can sit blind for hours. This script is push-based: verified harness turn-end hooks invoke it every time the primary is about to end a turn" (bin/fm-turnend-guard.sh:7-12). Neither replaces the live cycle: "Harness-aware turn-end guards are structural backstops, not permission to omit the live cycle" (AGENTS.md:458).

Two different health questions

The guards deliberately ask different questions, because they fire at different moments (bin/fm-wake-lib.sh:176-185):

PredicateQuestionUsed by
fm_watcher_healthy (PID-strict)Does a live process, identity-matched to this home's watcher, hold the lock with a beacon inside grace? "a leftover beacon must never satisfy it".The arm wrapper, the auto-arm, and the turn-end guard, which "fires at the turn boundary where the auto-arm brings a fresh watcher up".
fm_watcher_supervision_verdict (model-aware)Is supervision healthy for this harness's model right now? Sets FM_WATCHER_VERDICT_OK and a reason, no-watcher or stale-beacon.The pull guard, which "fires mid-turn, where the auto-arm model runs no watcher at all".

The model-aware verdict (bin/fm-wake-lib.sh:370-434):

  • autoarm (Claude, Cursor): a fresh beacon is healthy with no live watcher; a stale beacon is still healthy while fm_autoarm_midturn_healthy proves a Claude rewake explains the gap.
  • extension (Pi, pi-signed, omp): a live watcher, or a genuinely unheld lock with a fresh beacon while a live session provably owns continuity through both extensions loaded at their current builds — proven by sha256 digests recorded in state markers and bound to the pid in state/.lock (bin/fm-wake-lib.sh:218-317). A handoff-phase marker never counts.
  • persistent (every other harness): the strict predicate.

The pull guard: bin/fm-guard.sh

Runs inside supervision scripts, inside every drain, and in read-only advisory mode from a lock-refused session start (bin/fm-guard.sh:1-4). It always exits 0: "the guard warns, it never blocks" (bin/fm-guard.sh:42). In order it prints:

  1. Worktree tangle, checked first and independent of work in flight: the primary checkout is on a non-default branch, so "A crewmate likely branched/committed in the primary instead of its own worktree", with restore commands unless read-only (bin/fm-guard.sh:142-165).
  2. WATCHER DOWN - SUPERVISION IS OFF, when supervision is needed and the verdict fails, naming the true cause and a harness-specific repair line from bin/fm-supervision-instructions.sh --repair-line; printed in full once per down episode, keyed to the failing condition "not the beacon mtime, which a healthy between-turns watcher advances every poll", then as a one-line reminder (bin/fm-guard.sh:22-28, bin/fm-guard.sh:176-262).
  3. Queued wakes: "drain them with bin/fm-wake-drain.sh before anything else", counting only the rows the calling actor could present; rows held by a live Pi branch grant get a distinct notice instead, and the branch actor itself gets nothing (bin/fm-guard.sh:29-41, bin/fm-guard.sh:268-281).

The turn-end guard: bin/fm-turnend-guard.sh

Shared behaviour

  • Fail open when it cannot read safely. An empty payload or missing jq exits 0 "because it cannot safely read loop-guard fields" (bin/fm-turnend-guard.sh:125-133, docs/turnend-guard.md:65).
  • Scope. A secondmate home "runs its OWN primary firstmate session, so it must be guarded like the main primary; only child crew/scout worktrees are exempt", told apart by a valid .fm-secondmate-home marker and by git-dir versus git-common-dir (bin/fm-turnend-guard.sh:25-33, bin/fm-turnend-guard.sh:157-169).
  • Need includes a registered custom check or Relay polling even with no task, so a home-level poll keeps running after the last task is torn down (docs/turnend-guard.md:30-34).
  • Away daemon ownership replaces the watcher proof while state/.afk exists, in either mode: a live pid in state/.supervise-daemon.lock whose current identity matches the one it recorded, plus a fresh beacon under the poll-derived grace, because the daemon starts a new one-shot watcher only after handling the previous wake (bin/fm-turnend-guard.sh:209-225, bin/fm-wake-lib.sh:319-346).
  • Loop bound, default mode. Codex and Grok never block twice in one turn: a true stop_hook_active (or stopHookActive, which wins) allows the stop (bin/fm-turnend-guard.sh:50-58, bin/fm-turnend-guard.sh:144-155).
  • The block is a delimited stderr banner, TURN WOULD END BLIND - SUPERVISION IS OFF, naming what needs supervision and the repair line from the emitted protocol, then exit 2 (bin/fm-turnend-guard.sh:227-255).

The --claude cooperative mode

Claude marks every stop after any hook-driven continuation stop_hook_active=true, "including turns started by the asyncRewake auto-arm, so the one-shot allow would re-open the exact blind window this guard exists to close" (the 2026-07-21 incident) (bin/fm-turnend-guard.sh:60-65). So in Claude mode the guard ignores that flag and cooperates with the auto-arm instead:

  • A live foreign session-lock owner gets a systemMessage diagnostic and the stop is allowed, because "That Claude session cannot arm or repair the home without stealing the live owner's lock, so blocking it would create an unbounded loop" (bin/fm-turnend-guard.sh:257-267, docs/turnend-guard.md:37-41).
  • It polls for up to FM_CLAUDE_AUTOARM_SYNC_WAIT_MS (800 ms) for a healthy watcher, an open generation claim, a live legacy claim, or a rewake outcome younger than FM_CLAUDE_AUTOARM_EPOCH_FRESH (15 s) (bin/fm-turnend-guard.sh:351-401, bin/fm-turnend-guard.sh:489-505).
  • Otherwise it re-blocks up to FM_CLAUDE_TURNEND_BLOCK_BUDGET (3) times per session, "safely below Claude Code's hard 8-consecutive-block override". The budget charges each ledger epoch once, and also charges "every re-block against an epoch the auto-arm never advanced past the previous re-block", so "an inert hook that leaves the ledger frozen cannot hold the guard in an unbounded re-block loop" (bin/fm-turnend-guard.sh:82-91, bin/fm-turnend-guard.sh:278-349).
  • Past the budget, with a verified failure episode (the auto-arm committed its one notice and a failed outcome) and a final check that finds neither a healthy watcher nor an open claim, it creates state/.claude-autoarm-failure-alarmed exclusively and allows the stop once with "FIRSTMATE SUPERVISION IS GENUINELY DOWN … Keep this session attended" (bin/fm-turnend-guard.sh:403-487, bin/fm-turnend-guard.sh:507-526). After that alarm the auto-arm "suppresses further exit-2 continuations until positive watcher recovery, so the final fail-open remains reachable" (docs/turnend-guard.md:126).
  • A positively verified healthy watcher clears the notice, the alarm, and the budget together (docs/turnend-guard.md:119, bin/fm-wake-lib.sh:1368-1403).

Passive harnesses (OpenCode, Pi) "fail open at the hook boundary to protect the user session but schedule one bounded follow-up when the predicate blocks" (docs/turnend-guard.md:131-137). Generated follow-ups carry the turn-end-guard operational kind after the U+2063 FIRSTMATE_OP: prefix "so Ahoy does not treat them as captain messages" (docs/turnend-guard.md:134); that prefix belongs to Communication.

Stated limits

  • Headless OpenCode and untrusted Grok project hooks "remain fail-open at the host boundary"; Cursor's stop does not fire in headless cursor-agent -p, and a Cursor primary must be launched with --trust or "the whole integration is inert" (docs/turnend-guard.md:176-184).
  • omp's session_stop "never fires for an interrupted turn or a task session, so those boundaries are deliberately unguarded" (docs/turnend-guard.md:83).
  • A passive adapter that cannot reach its SDK is caught only by the next pull-guard call (docs/turnend-guard.md:173-174).

Grace and the poll cadence

A healthy watcher touches its beacon once per cycle, so the beacon can be up to one poll old. A flat 300 s grace breaks once FM_POLL reaches it — "exactly what a long-poll home (FM_POLL=300) hit against the Claude Stop-hook auto-arm". The auto-arm, the watcher's own pre-acquisition check, and the turn-end guard's daemon branch derive max(300, FM_POLL + 60); "Every other direct FM_GUARD_GRACE reader (bin/fm-guard.sh, the strict-watcher checks in bin/fm-turnend-guard.sh and its harness-specific wrappers, bin/fm-wake-lib.sh) still falls back to the bare 300-second default" (docs/turnend-guard.md:67-75).

Open question: long-poll homes and the strict guard

The turn-end guard's strict watcher check uses GRACE=${FM_GUARD_GRACE:-300} (bin/fm-turnend-guard.sh:99) while the auto-arm exports its poll-derived grace only to the arm it forks (bin/fm-claude-stop-autoarm.sh:274). In a home with FM_POLL at or above 300 and no explicit FM_GUARD_GRACE, the guard would read a healthy mid-wait watcher as stale near the end of each poll. The document states the split as intended; whether the guard's cooperative waits always cover that edge is not settled by the source.
