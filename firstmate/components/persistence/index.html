Persistence

Everything Firstmate writes down, why each record exists, and what it guarantees. The guiding rule: conversation memory is never authoritative. Durable files and live backend inventory are.

Read against Firstmate commit ada21f5b. Up: Level 2 containers.

Why this area exists

Firstmate supervises long-running workers from an agent session that can be cleared, compacted, crash, or be replaced by another harness at any time. The design answer is stated once in the charter: "A restart must be a non-event because durable state and live backend inventory, not conversation memory, are authoritative" AGENTS.md:256. Every obligation that must survive the session is therefore a file in the operational home. Each record is owned by exactly one script, and the script's header comment is that record's contract docs/configuration.md:11.

Three kinds of problem recur, and the rest of this section is organised around them:

  • Where things live. One code root is shared. Each instance has a private home, selected by FM_HOME, with four trees: data/, state/, config/, and projects/. See Operational home layout.
  • Not losing an event. Workers report through append-only status logs. Actionable events enter a durable wake queue that is emptied only after the handling turn acknowledges them. See Per-task records, Wake queue and recovery marker, and Presentation cursors and folded decisions.
  • Not letting the wrong writer win. The home is guarded by a session lock and by per-task, per-home, and per-actor locks and leases. Generation tokens reject stale writers. A check script found in state/ runs only if its bytes match a registered hash. See Locks and leases and Registered state checks.

One path end to end

A single ship task touches nearly every record type. The per-task records trace follows one task from dispatch to teardown. The wake queue trace follows one of that task's status lines through the watcher, the durable queue, the drain, and the acknowledgement.

  1. fm-spawn.sh takes the home's task-set lock and then the task's metadata lock. It writes state/<id>.meta to a temporary file, renames it into place, and starts the backlog row in the same run bin/fm-spawn.sh:1498-1506 bin/fm-spawn.sh:4440-4518.
  2. The worker appends done [at=…]: PR … to state/<id>.status bin/fm-classify-lib.sh:284-290.
  3. The watcher sees new status bytes and appends a signal row to state/.wake-queue. The append first republishes the .watcher-down downtime generation bin/fm-wake-lib.sh:1852-1867.
  4. The supervisor runs fm-wake-drain.sh, which presents the row and prints WAKE_ACK_REQUIRED. After handling, it acknowledges with that exact sequence and generation bin/fm-wake-drain.sh:860-861.
  5. fm-teardown.sh writes state/<id>.backlog-close, removes volatile state, and closes the backlog row. It removes the metadata last and removes the pending-close record once the close lands bin/fm-teardown.sh:15-23 bin/fm-teardown.sh:3653-3700.

Neighbouring areas

This section owns where records live and what each one guarantees. What the records are used for belongs to sibling areas:

  • Supervision: the watcher loop, triage, and the arm and turn-end layers that consume the wake queue.
  • Communication: steering-inbox delivery and the re-ring ladder, status-line vocabulary as a protocol, and the pending replies of secondmates.
  • Backlog and decisions: the backlog's own format and captain holds, which the pending-close record protects.
  • Delivery: the PR poll and merge authority, whose sidecars this section only classifies.
  • Prompts and skills: the /stow skill, which curates durable memory.
  • Remote: remote secondmate homes and the inherited-material transfer over SSH.
