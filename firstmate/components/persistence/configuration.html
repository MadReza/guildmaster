Per-home configuration and inheritance

config/ holds one home's local, gitignored operating choices. Ten of them are primary-authoritative and are pushed into every secondmate home. So is one shared data file. The rest stay local to the home that set them.

Read against Firstmate commit ada21f5b. Up: Persistence.

How config files are shaped

Almost every file is one of three kinds:

  • a presence flag, where only existence is read (trace-context, stow-pass-horizon, turnend-churn-absorb, wedge-defer-parked-gate);
  • a one-token or one-line value (backend, crew-harness, calm, claude-permission-mode, lavish-axi-host, startup-memory-budget);
  • a structured document (crew-dispatch.json, watched-tools.json, launch-env-allowlist, brief-include.md, the bindings under extensions.d/).

Absence nearly always means "the built-in default". Malformed content is handled differently from file to file. Some files fall back to the default. Others refuse the operation that needs them. That difference is recorded per file below.

Findings: the inventories drift from the code's list

The code's inherited set has ten items: crew-dispatch.json, crew-harness, backlog-backend, backend, herdr-presentation-spaces, startup-memory-budget, trace-context, launch-env-allowlist, claude-permission-mode, and lavish-axi-host bin/fm-config-inherit-lib.sh:71. The library's own header prose lists every one of them except launch-env-allowlist bin/fm-config-inherit-lib.sh:2-27. The charter's config/ inventory has no entry for launch-env-allowlist, extensions.d/, or the voice and inbox files AGENTS.md:71-91. The configuration guide does document all of them, and it agrees that the allowlist is inherited docs/configuration.md:402.

How inheritance works

Private config is gitignored, so "a tracked-files fast-forward never carries these items". Inheritance is "an explicit copy run at the convergence points the primary owns - a secondmate spawn (bin/fm-spawn.sh), the bootstrap secondmate sweep (bin/fm-bootstrap.sh), and the focused mid-session config push (bin/fm-config-push.sh). It is PRIMARY-AUTHORITATIVE" bin/fm-config-inherit-lib.sh:30-40.

Copy rules

  • Idempotent. A present source is copied "only when its content differs (idempotent: a re-run never churns mtimes)" bin/fm-config-inherit-lib.sh:185-192.
  • Atomic. The copy goes to .fm-inherit.XXXXXX in the destination directory and is renamed over the target bin/fm-config-inherit-lib.sh:143-170.
  • Absence propagates, but only when proven. "A source item proven absent is mirrored as a missing destination item, so clearing the primary's value clears it downstream too." But "inspection errors or existing nonregular sources leave that destination item unchanged and report an error; inaccessible paths and dangling source links must never silently remove an inherited grant" bin/fm-config-inherit-lib.sh:192-197. Absence is proven with lstat and ENOENT, not assumed from a failed read bin/fm-config-inherit-lib.sh:101-107.
  • Reported. Each item's result is pushed, unchanged, skipped, or error. Only a real copy or remove failure makes the call fail bin/fm-config-inherit-lib.sh:198-203.
  • Session-scoped items. trace-context is an enablement decision frozen per session, so it is copied at launch and "left untouched by live convergence into an already-running home" bin/fm-config-inherit-lib.sh:72-79.

The shared captain-preferences file

data/captain-shared.md is "the one shared data file in this inheritance contract. There is deliberately no shared learnings file" bin/fm-config-inherit-lib.sh:61-66. The source must carry a header, within its first 12 lines, declaring it main-authoritative and read-only in secondmate homes bin/fm-config-inherit-lib.sh:223-231. The downstream copy is mode 0444. A downstream copy that diverged is quarantined as .captain-shared.md.quarantine.<stamp>.<hash>, never overwritten in place, and reported as SECONDMATE_SYNC: … quarantined … drift bin/fm-config-inherit-lib.sh:257-300 bin/fm-config-inherit-lib.sh:388-404. For the rollout rule, secondmate-provisioning is the owner. Existing homes trim data/captain.md "by hand after first propagation rather than deleting private content automatically" docs/configuration.md:247.

Telling a running secondmate

Changing files under a live agent is not enough, because the agent has already read its old config. After a push that changes any allowlisted config item, local routes receive "the generation-specific literal-content pointer". Remote routes receive a durable marked reread nudge. Unchanged config, and changes only to captain-shared.md, send no reread bin/fm-config-push.sh:11-16. The instruction files live under state/.fm-inherited-config-reread* "so it never dirties the home". A send that fails is kept in a bounded retry queue, state/.fm-inherited-config-reread-retry, and quarantined past its limits bin/fm-config-inherit-lib.sh:565-575 bin/fm-config-inherit-lib.sh:611-1072. captain-shared.md "is never allowlisted here and must never be inlined into a reread instruction" bin/fm-config-inherit-lib.sh:580-583.

Deleting a config file

Deleting a file in a primary home returns that choice to its default. For an inherited item, the next convergence also removes it from every secondmate, because absence is mirrored. Deleting an inherited file in a secondmate home lasts only until the next convergence, which restores the primary's value. The two exceptions to "delete means default":

  • config/startup-memory-budget in a primary home is re-materialized as 7500 by the next locked bootstrap docs/configuration.md:258.
  • config/x-mode.env is regenerated by Relay setup while Relay is enabled docs/configuration.md:711.

No config file is a lock, a journal, or a queue, so deleting one never corrupts runtime state. It changes behaviour at the next read. Some files, such as the permission mode and the launch allowlist, are read on every spawn docs/configuration.md:377.
