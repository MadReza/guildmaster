What is safe to delete

A register of Firstmate's records by what happens when one is removed by hand. Each record falls into one of four groups: safe to delete, regenerated, retire only through its owner, or never touch.

Read against Firstmate commit ada21f5b. Up: Persistence.

How to read this page

Rows marked stated repeat what Firstmate's own documents say. Rows marked derived follow from reading the code, where the source makes no explicit safety claim. For derived rows the consequence is described, not endorsed. The general rule from the charter: data/, state/, config/, and projects/ are private operational records that Firstmate "may maintain ... directly" AGENTS.md:44, through the owning script for each record.

Temporary files

Atomic writers leave names such as .<id>.meta.spawn.<pid>, .fm-custom-check.XXXXXX, .wake-queue.ack.XXXXXX, .fm-inherit.XXXXXX, and *.tmp.*. Each writer removes its own temporary file on failure or in an EXIT trap. Examples: bin/fm-check-register.sh:35 bin/fm-check-lib.sh:71-74 bin/fm-wake-lib.sh:657-662.

Open question

Some temporaries could be left behind by a process killed with SIGKILL, which runs no trap. The sources read for this page contain no general sweep for such orphans, and no statement that deleting one is safe. An orphan is not the published record, so the atomic-replace pattern implies it is inert. That is an inference, not a documented guarantee.
