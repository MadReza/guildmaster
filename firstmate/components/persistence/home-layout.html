Operational home layout

One tracked code root supplies the instructions and scripts. Each Firstmate instance keeps its private records in a separate operational home, selected by FM_HOME.

Read against Firstmate commit ada21f5b. Up: Persistence.

Code root versus home

The code root is the Firstmate repository checkout. It holds shared, tracked material: AGENTS.md, README.md, CONTRIBUTING.md, .tasks.toml, CI workflows, bin/, and the skill trees AGENTS.md:45. The operational home holds four private, gitignored trees. FM_HOME selects the home, "while scripts continue to come from their tracked code root" AGENTS.md:54. The repository is "a shared template, while .env, data/, state/, config/, projects/, and .no-mistakes/ are captain-private and gitignored" AGENTS.md:47.

By default the home is the code root, so a primary instance keeps its private trees inside the checkout. They are ignored there .gitignore:1-15. A secondmate is a second, persistent home with its own state, backlog, projects, and session lock AGENTS.md:55.

The four trees

The layout section of the configuration guide is the single owner of the top-level layout. Producer script headers own each child file's fields docs/configuration.md:11.

data/: durable private fleet records
The project and secondmate registries, captain preferences, optional shared captain preferences, learnings, the backlog, briefs, scout reports, and installed content-addressed extension packages under data/extensions/packages/ docs/configuration.md:13. Per task: data/<id>/brief.md and a scout's data/<id>/report.md, which "survives teardown" AGENTS.md:99-100. The /stow cold tier data/memory-archive.md also lives here .agents/skills/stow/SKILL.md:134.
state/: runtime records and signals
Task metadata, append-only status events, endpoint signals, watcher and wake-queue coordination, inactive terminal-outcome receipts under state/terminal-outcomes/, extension namespaces, away-mode state, Relay artifacts, secondmate caches, reconcile requests, config-reread generations, steering inboxes, and pending replies docs/configuration.md:14. The charter lists every entry and its owner AGENTS.md:102-159.
config/: local operating choices
Local, gitignored choices such as the runtime backend, crew harness, dispatch profiles, and explicit extension bindings under config/extensions.d/ docs/configuration.md:15. See Per-home configuration.
projects/: project clones
Clones that Firstmate reads but changes only through "the narrow guarded and concrete captain-approved exceptions in AGENTS.md" docs/configuration.md:15. Firstmate reads projects and crewmates change them AGENTS.md:27-28. Crewmates do that in task worktrees provided by Treehouse or Orca docs/configuration.md:136.

Untracked names beginning with scratchpad are ignored so that temporary scratch "does not make porcelain-based secondmate sync guards treat a home as dirty" docs/configuration.md:16 .gitignore:4.

How a script resolves the home

Every script repeats the same three-line resolution at its top. Two representative copies:

FM_ROOT="${FM_ROOT_OVERRIDE:-$(cd "$SCRIPT_DIR/.." && pwd)}"
FM_HOME="${FM_HOME:-${FM_ROOT_OVERRIDE:-$FM_ROOT}}"
STATE="${FM_STATE_OVERRIDE:-$FM_HOME/state}"

bin/fm-lock.sh:31-33 bin/fm-wake-lib.sh:4-9

  • FM_ROOT_OVERRIDE overrides the code root, including the primary checkout that the worktree-tangle guard watches. When FM_HOME is unset it also acts as the older whole-root override docs/configuration.md:310-311.
  • FM_STATE_OVERRIDE, FM_DATA_OVERRIDE, FM_PROJECTS_OVERRIDE, and FM_CONFIG_OVERRIDE relocate a single tree. They exist "for tests and specialized harness setup" docs/configuration.md:313.
  • Before fm-brief.sh, fm-spawn.sh, or fm-afk-launch.sh persists a path, it resolves a relative FM_HOME, FM_STATE_OVERRIDE, or FM_DATA_OVERRIDE against the caller's working directory. An unresolvable one is rejected with the offending variable named docs/configuration.md:314. fm-spawn.sh also rejects control bytes in those raw inputs docs/configuration.md:315.
  • Lifecycle access to a backlog, task record, or pending-close record must resolve inside its configured root. "A final-component symlink is refused even when its target remains within that root" docs/configuration.md:316. The executable check is fm_backlog_record_parent_authorized, which compares the canonical parent and final path bin/fm-backlog-transition-lib.sh:711-737.

The one deliberate exception: fm-send

Most scripts fall back to the code root when FM_HOME is unset. fm-send.sh refuses instead, "so operator steers cannot silently resolve against the wrong home" docs/configuration.md:312. The implementation refuses an unset or empty FM_HOME, a home that is not a directory, and a missing state/ bin/fm-send.sh:229-241. The steer is the one operation where addressing the wrong home would reach a live agent that belongs to someone else, so failing closed is worth the inconvenience.

Finding: two spellings of "override"

Most scripts use ${FM_STATE_OVERRIDE:-…}, so an explicitly empty override falls back to the default. fm-check-unregister.sh uses ${FM_STATE_OVERRIDE-…} instead, and its header states that "an explicitly empty override … is refused before removal" bin/fm-check-unregister.sh:4-6 bin/fm-check-unregister.sh:14 bin/fm-check-unregister.sh:26-29. The difference is deliberate for a script that deletes. It does mean that the same environment resolves to different homes in different scripts.

Secondmate homes

A secondmate home is seeded by fm-home-seed.sh as a fresh Firstmate worktree leased from the Treehouse pool under the secondmate's id. "Normal restarts do not free or recycle the home" docs/configuration.md:287-293. Two root markers identify it:

  • .fm-secondmate-home: the identity marker. The seed publishes it after the parent binding bin/fm-home-seed.sh:19-20 bin/fm-home-seed.sh:42-43.
  • .fm-secondmate-parent: the durable route back to the parent docs/configuration.md:300.

Both markers are gitignored, so a freshly seeded home never looks dirty to porcelain safety checks docs/configuration.md:301-302 .gitignore:7-8. The parent markers form a chain. fm_firstmate_root_home follows local parent bindings upward to find the one machine-local anchor home, where cross-home locks such as the Treehouse project-identity lock live. It stops at a remote binding, fails closed on a malformed or unreachable binding or a cycle, and stops after 64 levels bin/fm-wake-lib.sh:1183-1230.

The home label also shapes runtime backends. On Herdr, FM_HOME chooses the workspace label: firstmate for the primary and 2ndmate-<id> for a marked secondmate home docs/configuration.md:167. Zellij and cmux embed a readable home label plus a short hash of FM_ROOT in visible titles instead docs/configuration.md:174 docs/configuration.md:177.

What this layout guarantees, and what it does not

  • Guaranteed: two instances never share state/, because each holds its own session lock inside its own home AGENTS.md:55.
  • Guaranteed: tracked-file updates never carry private material, because every private tree is gitignored .gitignore:1-15. That is exactly why config/ inheritance needs its own copy mechanism bin/fm-config-inherit-lib.sh:30-37.
  • Not guaranteed: a bare tasks-axi run addresses the right backlog. .tasks.toml paths resolve against the working directory, not FM_HOME, so a run from the code root reaches the code root's data/. That is why routine backlog commands go through bin/fm-tasks-axi.sh docs/configuration.md:128-130.
  • Not guaranteed: symlinking the code-root backlog into a home keeps them in step. tasks-axi writes by renaming a temporary file over its target, which "replaces a symlink with a regular file" and forks the queue on the first write docs/configuration.md:129.
