Per-task records

Each dispatched task leaves a small, fixed set of files. Its metadata names what exists. Its status log records what happened. Its brief and report outlive it. A pending-close record makes cleanup restartable.

Task metadata: state/<id>.meta

Problem solved. Every later operation must find the task's worktree, endpoint, harness, and delivery contract without asking the agent to remember them. The record's existence is also what "this task exists" means. The spawn script owns the base fields. The runtime-backend section of the configuration guide owns the backend-specific ones docs/configuration.md:18.

How it is written

The record is never edited in place. Spawn takes the task's metadata lock state/.meta-<id>.lock bin/fm-spawn.sh:4440-4444. It writes the whole record to state/.<id>.meta.spawn.<pid> bin/fm-spawn.sh:4445-4450 and publishes it with fm_backlog_atomic_transition publish bin/fm-spawn.sh:4514-4518. That call checks that both paths resolve inside the authorized state root, that neither is a symlink or irregular file, and then renames with mv -f bin/fm-backlog-transition-lib.sh:763-776. fm-pr-check.sh follows the same discipline. It takes the metadata lock, copies every line except pr= and pr_head= into a temporary file, appends the new values, and replaces the record bin/fm-pr-check.sh:123 bin/fm-pr-check.sh:134-138.

A relaunch rebuilds the record from the new launch and then copies forward every key the spawn does not own. preserve_relaunch_meta filters out the owned key list, so fields added later by other scripts, such as pr=, survive a relaunch bin/fm-spawn.sh:4452-4460.

Readers and the endpoint binding

Task selectors in fm-peek.sh, fm-send.sh, and fm-crew-state.sh resolve through fm_backend_resolve_selector. An exact task id matching state/<id>.meta wins over the legacy fm-<id> label docs/configuration.md:158-163. fm-teardown.sh <id> validates "the complete metadata-only endpoint identity before any runtime dispatch or cleanup mutation". Missing, duplicate, malformed, or mismatched endpoint records are "preserved and refused" docs/configuration.md:164-165.

Status log: state/<id>.status

Problem solved. A worker needs one cheap, crash-safe way to tell Firstmate that something happened. It must not need a lock, a daemon, or the supervisor to be awake. An appended line fits: echo "done [at=…]: PR …" >> state/<id>.status. Appending a line is also the event that wakes the watcher.

The key rule. "A state/<id>.status line is a wake event, not current-state truth; bin/fm-crew-state.sh owns current-state reconciliation" AGENTS.md:163. A working: line may be hours stale. A done: line may predate a later fix. Current state is always re-derived from live evidence.

Line grammar

<verb> [key=<slug>] [at=<epoch>]: <note>
needs-decision [key=api-shape]: <summary>
resolved [key=api-shape] [at=1788576000]: answered: use REST
  • Verbs. The captain-relevant set defaults to done:, needs-decision:, blocked:, and failed:, plus legacy free-text tokens. FM_CAPTAIN_RE overrides the set bin/fm-classify-lib.sh:67-78. paused: is a declared external wait, deliberately outside that set bin/fm-classify-lib.sh:80-90.
  • Emission time. An optional [at=<epoch>], at most 12 digits, before the first colon. A missing, malformed, or duplicate stamp means unknown time. Firstmate must "never infer emission time from file mtime, a wake, or observation time", and time "must never decide current state or decision closure" bin/fm-classify-lib.sh:284-296.
  • Decision keys. An optional [key=<slug>] names a decision. A line with no key uses default. A key deeper in the note is prose and "cannot open or close that decision" bin/fm-classify-lib.sh:429-450. The fold over these lines is on Presentation cursors and folded decisions.

Why append-only matters

The cursor code states the invariant it depends on: "every one is created once (>) and only ever appended to (>>) - never replaced, renamed, or rewritten in place" bin/fm-classify-lib.sh:941-947. Because of that, a byte offset plus the file's device and inode is enough to know what has already been read. The one gap is accepted: a same-inode, same-size edit in place is not detected, "because no code path in this repo ever does that to a status file" bin/fm-classify-lib.sh:950-953.

The log does not survive teardown

The log records wake history, not an archive. Teardown calls status_retire_presentation_task, which removes the task's row from the presentation cursor and then deletes state/<id>.status, its open-decisions cursor, and its signal, heartbeat, and daemon seen-markers bin/fm-teardown.sh:3655 bin/fm-classify-lib.sh:1503-1575. What outlives the task is the backlog row with its completion links, and the brief and report under data/<id>/.

Brief and report: data/<id>/

The brief is the worker's written instructions: "per-task crewmate brief, or per-secondmate charter brief when kind=secondmate". The report is "scout task deliverable, written by the crewmate; survives teardown" AGENTS.md:99-100. Teardown reads data/<id>/report.md as the landed-work proof for a scout. It "proceeds only once the report exists" bin/fm-teardown.sh:72-75 bin/fm-teardown.sh:3281. No teardown path removes data/<id>/. Brief authoring belongs to Prompts and skills.

The pairing invariant and the pending-close record

Problem solved. The backlog in data/ and the task record in state/ must agree. The library states it as an invariant: "state/<id>.meta exists <=> this home's backlog row for <id> is In flight; the one teardown crash window is represented by state/<id>.backlog-close" bin/fm-backlog-transition-lib.sh:7-9.

The script that performs the physical change also performs the paired transition, "in the same process, under the per-task meta lock it already holds, before it reports success. Nothing else - not a later agent turn, not a printed reminder - is load-bearing for the pairing" bin/fm-backlog-transition-lib.sh:9-13:

  • fm-spawn.sh: publish the record, then tasks-axi start. No marker is needed, because a crash leaves the record itself as evidence that the row is owed a start bin/fm-backlog-transition-lib.sh:50-52.
  • fm-teardown.sh: the completion links (the PR, the report path) live only in the record being removed. Teardown therefore writes the intended transition to state/<id>.backlog-close first bin/fm-backlog-transition-lib.sh:41-49.
  • fm-bootstrap.sh: at session start, replays every *.backlog-close left behind, in this home only bin/fm-bootstrap.sh:1279-1312.

The record has id=, data=, spawn_gen=, optional cleanup_incomplete=, mode=close|retain, and repeated arg= lines. The validator refuses a control byte, a duplicate or missing field, a foreign id, or a data path outside this home bin/fm-backlog-transition-lib.sh:905-960. The close runs in a fixed order: remove the record, run tasks-axi done, remove the marker bin/fm-backlog-transition-lib.sh:869-875. Replay is idempotent because tasks-axi done on an already-closed task "backfills links without moving the close date" bin/fm-backlog-transition-lib.sh:49-50. mode=retain handles a row that is still an open captain call. Replay then reopens the row with the deliverable recorded instead of closing it bin/fm-backlog-transition-lib.sh:53-57.

Generation tokens in the record

A task id can be reused, and a harness can be relaunched. Records that could be written late therefore carry a token that names one incarnation:

  • spawn_gen=s<epoch>.<pid>.<random> is minted per spawn bin/fm-spawn.sh:4438. The pending-close record stores it. The backlog library requires exactly one spawn_gen line in the record bin/fm-backlog-transition-lib.sh:778-790. Fleet snapshots use it to detect that a task was replaced between two reads bin/fm-fleet-snapshot.sh:617-619, and inactive reconciliation keys incarnations by it bin/fm-inactive-reconcile.sh:302.
  • busy_gen binds the semantic busy-state record. "Arming again replaces the previous incarnation: late events carrying the old gen are rejected as stale from then on" bin/fm-busy-event.sh:13-14. The record is one line, v1 gen=… seq=… state=… source=… event=… ts=…, atomically replaced. seq is strictly increasing per generation, "so an out-of-order apply can never regress a newer record" bin/fm-busy-lib.sh:14-25. What busy state means is covered under Supervision.

The relaunch journal

fm-control.sh relaunch replaces a running agent in the same worktree. Its durable record is state/<id>.control-relaunch, with the prior metadata and brief kept beside it as .meta-prior and .brief-prior bin/fm-control.sh:569-581. Each phase rewrites the journal whole (v1, task, phase, ts, backend, endpoint, worktree, from and to profile) through a temporary file and a rename bin/fm-control.sh:597-622. An EXIT trap rolls back. Before the old agent is touched, rollback restores the brief byte-exact and journals failed:<phase> bin/fm-control.sh:624-640. The contract is that a failure leaves "either the pre-relaunch durable record or a concrete, named partial state - never a task whose record claims an agent that is not running" bin/fm-control.sh:572-576.

What teardown removes, keeps, and refuses

Teardown kills the endpoint, returns the worktree, clears volatile state, and transitions the backlog before it reports success bin/fm-teardown.sh:2-7. In its final phase it removes, in this order bin/fm-teardown.sh:3626-3700:

  1. harness hook tokens, the backend transition record, and the task temp roots;
  2. PR-poll artifacts and the busy-state incarnation, retired by exact generation;
  3. the status log and its cursors (status_retire_presentation_task);
  4. .turn-ended, .progress, per-harness session bindings, the relaunch journal set, .reconcile-nudged, and the branch-outcome index;
  5. the steering inbox, rm -rf state/<id>.inbox. Any unhandled steer is "moot rather than unlanded work" because teardown runs only after landing is confirmed bin/fm-teardown.sh:3664-3667;
  6. finally the metadata, fused with the backlog close or retain, still under the metadata lock bin/fm-teardown.sh:3668-3700.

It keeps data/<id>/. It refuses, before anything destructive, when the endpoint close could not be proven bin/fm-teardown.sh:8-14, when the worktree holds work that has not landed bin/fm-teardown.sh:44-51, when check artifacts are not ordinary single-link files bin/fm-teardown.sh:76-80, and when another record or a slot-owner claim shows the worktree slot belongs to another live task bin/fm-teardown.sh:81-116. --force discards this task's unlanded work. It "does not lift" those other refusals bin/fm-teardown.sh:131-133.
