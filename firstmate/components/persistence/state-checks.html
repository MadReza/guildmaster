Registered state checks

The watcher runs slow polls from state/*.check.sh, but never because a file happens to be there. Each one is either routed to a tracked repository script or run from a private snapshot whose bytes match a registered hash. Anything else is refused and reported.

Read against Firstmate commit ada21f5b. Up: Persistence.

What a state check is

A state check is a slow poll that the watcher runs every FM_CHECK_INTERVAL seconds (default 300). Each run gets FM_CHECK_TIMEOUT seconds (default 30) bin/fm-watch.sh:232-233. The cadence is tracked by the mtime of state/.last-check, "so the cadence survives watcher restarts". Checks are evaluated before the signal scan, so a chatty sibling cannot starve merge detection bin/fm-watch.sh:2364-2372. A check prints one line when Firstmate should wake and nothing otherwise. The charter's authoring rule for a custom check: "keep it an ordinary single-link mode-0700 file, print one line only when firstmate should wake, print nothing otherwise, finish before FM_CHECK_TIMEOUT, then bind its current bytes with bin/fm-check-register.sh <id> before the watcher may execute it" AGENTS.md:398.

Four dispositions

For every state/*.check.sh the watcher chooses exactly one of four paths bin/fm-watch.sh:2374-2418. The inventory states the rule in one line: the watcher "dispatches validated PR data and the byte-identified Relay shim through trusted repository scripts, runs registered custom checks from hash-validated private snapshots, and rejects every other state check without execution" AGENTS.md:117.

The content-trust binding

state/<id>.check-trust is exactly two lines. Any third line fails the read bin/fm-check-lib.sh:17-36:

fm-custom-check-v1
<64 lowercase hex: SHA-256 of state/<id>.check.sh>

Both files must pass fm_pr_private_file_valid. That means a regular file, not a symlink, with an exact mode (0600 for the trust record, 0700 for the check), on the same device as the state/ directory (read in the same invocation), with a link count of exactly 1 bin/fm-pr-lib.sh:285-296. The device check "refuses a file that is not on that directory's own filesystem, such as one bind-mounted over the name, which is also what keeps same-directory rename publication atomic" bin/fm-pr-lib.sh:285-289. The single-link rule means a hard link cannot give a file a second, trusted name. The hash comes from shasum -a 256, or sha256sum as a fallback. With neither tool present, nothing can be registered bin/fm-check-lib.sh:6-15.

Registering: fm-check-register.sh <id>

The header is one sentence: "Bind an intentional custom watcher check to its current bytes." It adds: "Retire with fm-check-unregister.sh <id>; do not hand-compose an rm" bin/fm-check-register.sh:2-4. The script:

  1. refuses a malformed id (exit 2) and a symlinked or missing state/ bin/fm-check-register.sh:17-25;
  2. requires the check to be a regular, non-symlink, mode-0700, single-link file on the state device, and the trust path to be absent or regular on that device bin/fm-check-register.sh:26-31;
  3. hashes the check, then writes the two lines under umask 077 to a temporary file, chmod 0600, re-validates the destination, and renames bin/fm-check-register.sh:32-40;
  4. re-verifies the whole binding with fm_custom_check_registered. If that fails, it removes the trust record it just wrote and exits 1 bin/fm-check-register.sh:41.

Step 4 means a registration either leaves a binding that verifies, or leaves no binding at all.

Executing a custom check

Verifying the check file and then running that same path would leave a window between the two in which the file could change. The watcher closes it with a snapshot bin/fm-check-lib.sh:48-69:

  1. Read and validate the trust record. Validate the check file's mode, device, and link count.
  2. Copy the check to a new private temporary file, state/.fm-custom-check.XXXXXX, and chmod 0600.
  3. Re-verify the snapshot: regular, not a symlink, mode 600, same device, one link. Hash it and compare with the binding.
  4. Run the snapshot, never the original path, with bash under timeout, gtimeout, or a Perl alarm fallback. It runs in its own process group, and stdout is captured to a private temporary file bin/fm-watch.sh:1802-1812 bin/fm-watch.sh:1855-1880.
  5. Remove the snapshot bin/fm-watch.sh:2407-2414.

The file that runs is the one that was hashed. A mode-0600 snapshot is still executable this way, because it is passed to bash as an argument.

The other trusted paths

  • PR poll. The check file must be byte-for-byte the tracked bin/fm-pr-poll.sh. Task and PR data live "only in a private sidecar and are never interpolated into shell source" bin/fm-pr-check.sh:4-5. The watcher captures a snapshot of the sidecar, takes the task's control lock, checks that the snapshot still matches, and runs the tracked script with the validated fields as arguments. A snapshot that changed is skipped bin/fm-watch.sh:2388-2406. The sidecar family (.pr-poll, .pr-poll-registration, .pr-poll-retirement, .merge-authority, .pr-poll-merge-notified) is listed at AGENTS.md:119-123. Invalid retirement receipts are "preserved without running a check or removing poll artifacts" bin/fm-watch.sh:110-112.
  • Relay shim. x-watch.check.sh is accepted only if fmx_poll_shim_valid identifies its bytes for this home and root. Even then the watcher runs the tracked bin/fm-x-poll.sh, not the shim bin/fm-watch.sh:2377-2385.
  • Generated custom checks. The watched-tool poll, the mail poll, and the contributions poll are written by their own scripts and then bound with the same fm-check-register.sh, so they run as ordinary registered checks bin/fm-tool-update-check.sh:14 bin/fm-mail-check.sh:17 bin/fm-contributions.sh:412.

Refusal and retirement

Every file that fails all three trusted paths is added to one list. After the sweep, that list becomes a single wake, check: rejected unauthenticated state checks: <paths>. The files are "refused without execution" bin/fm-watch.sh:108-109 bin/fm-watch.sh:2475-2480. The watcher does not delete them. Removing a check is the supervisor's decision.

fm-check-unregister.sh <id> removes exactly <id>.check.sh and <id>.check-trust, and each must be an ordinary single-link file on the state device. It refuses an explicitly empty FM_STATE_OVERRIDE or a symlinked state/ before removing anything bin/fm-check-unregister.sh:2-8. Teardown validates a task's check artifacts the same way before destructive cleanup and preserves the task's state if that proof fails bin/fm-teardown.sh:76-80.

Trace: a custom check from authoring to wake

  1. The supervisor writes state/deploy-x.check.sh, a script that prints deployed once a URL answers, and runs chmod 0700 on it.
  2. bin/fm-check-register.sh deploy-x writes state/deploy-x.check-trust and prints registered: state/deploy-x.check.sh bin/fm-check-register.sh:42.
  3. On the next sweep, the file is not the Relay shim and has no PR sidecar. fm_custom_check_snapshot_prepare succeeds and the snapshot runs.
  4. Output deployed becomes fm_wake_append check state/deploy-x.check.sh "check: state/deploy-x.check.sh: deployed", and the watcher exits with that reason bin/fm-watch.sh:2466-2472.
  5. If anyone edits the check without re-registering, the hash no longer matches. The file then lands in the rejection wake instead of running.
Finding: the check library has no contract header

bin/fm-check-lib.sh starts directly with its variables and functions, with no header comment bin/fm-check-lib.sh:1-4. By the project's own rule, the script header is the contract. Here the contract is spread across the charter's authoring rule AGENTS.md:398, the inventory line AGENTS.md:117-118, the registrar's two-line header, and the watcher's call sites.

Open question: the threat being defended against

The source states what the binding does, not which attacker it defends against. It never says whether it is meant to stop a worker, a stray tool, or an accidental overwrite from placing an executable in state/. The mechanism detects any change to the registered bytes, and it refuses symlinks, hard links, and cross-device substitutions. How the binding is supposed to hold against a process running as the same user, which could simply re-register, is not stated. Compare the lease library, which states its threat model explicitly bin/fm-lease-lib.sh:35-45.
