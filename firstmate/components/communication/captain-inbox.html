Captain inbox and voice

The captain's side door into Firstmate. A note left while Firstmate is busy is saved to disk and announced with one wake, and stays pending until Firstmate acknowledges it. A spoken front end uses the same note path to hand over real work.

Read against Firstmate commit ada21f5b. Owners: bin/fm-inbox.sh; the spoken interface docs/voice-relay.md. Up: Communication.

Three problems, three mechanisms

The header insists these are different problems (bin/fm-inbox.sh:4-20):

note (and say)
Queue an idea for Firstmate while it is mid-turn and cannot answer. Writes a durable record and appends one check wake, so the note survives a crash and is presented at the next drain. say is the same, with the body transcribed from audio: "Speech is an INPUT METHOD here, not an architecture."
status
"What is happening", from records only. No network, no wake, safe to run in a loop. It ends by reminding the reader that "the last event line is history, not current state" (bin/fm-inbox.sh:1041-1073).
ask
A side question answered by a one-shot model call that never touches Firstmate, the backlog, or the wake queue. "A side question is not fleet work and must not become fleet work."

Only note and announce touch the wake queue (bin/fm-inbox.sh:10-11).

Capturing a note

fm-inbox.sh note [--request-id <id>] [--json] [--] <text>...
fm-inbox.sh note [--request-id <id>] [--json] -        (body from stdin)

A note is written to a temp file and renamed into state/inbox/<epoch>-<random>.note (bin/fm-inbox.sh:425-470). Its format mirrors the steering-inbox record (bin/fm-inbox.sh:287-303):

id=<id>
at=<UTC time>
source=text                   (or the voice/say source)
announce_marker=1
request_id=<id>               (only with --request-id)
--
<body>

An empty body is refused. Only the listed flags are parsed; anything else starting with -- begins the body (bin/fm-inbox.sh:50-51).

Announcing exactly once

announce_note appends one wake, check: captain inbox note <id> - <summary>, keyed inbox:<id>, and writes .announced/<id>. The marker test, the append, and the marker write all happen under the wake-queue lock, because two retries of the same request id can run at once and would otherwise both append (bin/fm-inbox.sh:324-363). A note already acknowledged gets no wake. If the wake cannot be appended the note is still on disk, and the command says so loudly: exit 1 normally, exit 3 with --request-id or --json so a caller can tell "saved but not announced" from "nothing saved" and repair with announce instead of queueing again (bin/fm-inbox.sh:52-56).

announce refuses a note whose announcement state is unknown. Notes from before the marker existed already woke Firstmate at creation, and nothing on disk can prove it, so announcing again would be the duplicate this contract removes. That is why new notes carry announce_marker=1 (bin/fm-inbox.sh:44-49, bin/fm-inbox.sh:259-277).

Idempotent capture with --request-id

The request id is claimed with an exclusive create under .requests/ before announcement, so a repeat returns the original note and prints replay (or "outcome":"replay"), even after a crash between save and wake (bin/fm-inbox.sh:35-40, bin/fm-inbox.sh:400-423).

Handling, replying, and acknowledging

The charter tells Firstmate what to do on the wake: act on a captain inbox note like any check: result, acknowledge it with bin/fm-inbox.sh drain --ack <id> "or it stays counted as still waiting for firstmate", and, when the submitter needs a durable answer, publish it with bin/fm-inbox.sh reply <id> rather than leaving it in the transcript (AGENTS.md:441-442).

  • drain --ack <id>... moves each note to handled/ and prints acked or already-acked (bin/fm-inbox.sh:1116-1137). As with the steering inbox, the move is the acknowledgement.
  • reply <id> <text> records one reply per note under .replies/, stamped with a per-home sequence under a lock, so the receipts cursor is a strict order even for two replies in the same second. A second reply is refused (bin/fm-inbox.sh:61-64, bin/fm-inbox.sh:561-652).
  • receipts is a bounded JSON view of pending and handled notes, their acknowledgement and announcement, and replies. Bounds omit rather than pretend the first page is everything, and omitted[] says how to see more (bin/fm-inbox.sh:57-60).
  • ready reports whether a primary session can receive: session lock, wake-consumer health, away posture. It never takes the lock and never infers liveness from a lock file, a session, or a pane (bin/fm-inbox.sh:65-67).

Configuration and privacy

note, announce, reply, receipts, ready, status, list, and drain need no configuration and make no network call. say and ask send audio or a question to Bedrock and are off until the home configures a region and model; no default is shipped, because "a region, a model id and an AWS profile name somebody's account and somebody's choices" (bin/fm-inbox.sh:69-95; registry: docs/configuration.md:1056-1078).

The spoken interface

A voice agent in front of Firstmate answers "what is happening" from Firstmate's own records, and when asked for real work "says so out loud and queues the request rather than pretending to do it" (docs/voice-relay.md:3-6). The laptop captures and plays audio; the desktop holds the model session; no AWS credentials sit on the laptop (docs/voice-relay.md:13-27). Both ends share one bidirectional byte stream over an ssh exec channel, framed by bin/fm_voice_frame.py, the one file both machines run.

(docs/voice-relay.md:287-296.) Guarantees and limits stated in the doc:

  • What it may say is narrow by default. Without config/voice-read-scope it sends counts only, with no identifier, title, or link assembled. full adds names, titles, and PR links of open work. Finished work and free-form note bodies are excluded at every scope, by construction. config/voice-read-deny reduces matching items to a count. A misspelled scope refuses rather than widening (docs/voice-relay.md:169-209).
  • It never changes a project; real work goes through note (docs/voice-relay.md:273-274).
  • Push to talk only. --listen open-mic refuses at startup because there is no end-of-speech detection (docs/voice-relay.md:211-221).
  • One turn per model session, with no memory across questions, because a second question in a session is always treated as an interruption and a records-reading turn that is interrupted never answers (docs/voice-relay.md:223-248).
  • The laptop audio devices are unverified: no worker can reach the laptop, so the first live run is their test (docs/voice-relay.md:124-128).
