Operational-input markers

Firstmate's own machinery types text into agent sessions too: launch briefs, watcher wakes, turn-end warnings, relayed requests. A fixed invisible prefix lets an agent, and Firstmate's own code, tell that machine-sent text apart from a human typing.

Read against Firstmate commit ada21f5b. Owner: bin/fm-operational-input.sh; compatibility entry point bin/fm-marker-lib.sh. Up: Communication.

What problem it solves

Everything that arrives in an agent's chat looks the same to the agent: a line of text. Some lines come from the captain typing into the pane, and some come from Firstmate scripts. A secondmate in particular must answer the two differently: a request from the main firstmate is answered on the status channel, while an unmarked message is the captain intervening directly and gets a conversational reply (bin/fm-brief.sh:309-320). The marker is how the difference is carried, without inferring provenance from the wording of the body (bin/fm-operational-input.sh:11-15).

Wire forms

The library defines two current forms (bin/fm-operational-input.sh:8-15, bin/fm-operational-input.sh:27-41). U+2063 is the invisible separator character, bytes E2 81 A3.

Generic, typed:     U+2063 "FIRSTMATE_OP: v1 " <kind> ": " <body>
From-firstmate:     "[fm-from-firstmate]" U+2063 <body>
Kinds
session-start, watcher, turn-end-guard, away-supervisor, launch-brief, branch-outcome (bin/fm-operational-input.sh:31), plus from-firstmate, which uses its own carrier. An unknown kind is refused at encode time and not recognised at parse time (bin/fm-operational-input.sh:43-81).
Why the from-firstmate form is different
Secondmates already running have the [fm-from-firstmate] label in their charter, so the carrier stays byte-compatible with them (bin/fm-operational-input.sh:37-41). The brief tells a secondmate the marker is "untypable, so a human never produces it" (bin/fm-brief.sh:311-312).
Idempotent marking
fm_message_mark_from_firstmate adds the carrier only if it is not already there (bin/fm-operational-input.sh:178-187).

A live example is the first line of every crewmate launch prompt: fm-spawn.sh builds each harness command with "$(… encode launch-brief < brief)" (bin/fm-spawn.sh:1859), so the brief arrives prefixed FIRSTMATE_OP: v1 launch-brief: .

Cross-language use

The file is both a sourceable library and a CLI for JavaScript and TypeScript integrations (bin/fm-operational-input.sh:4-25):

fm-operational-input.sh encode <kind>   # body on stdin
fm-operational-input.sh kind            # which current kind, if any
fm-operational-input.sh classify        # current or legacy kind
fm-operational-input.sh body            # strip the header

Success prints exactly one value; a non-match exits 1 silently; misuse exits 2.

Legacy transcripts

Older persisted transcripts carry pre-protocol text: a bare session-start instruction, a FIRSTMATE WATCHER WAKE: prefix, a "TURN WOULD END BLIND" prefix, an away-supervisor escalate prefix, and an untyped FIRSTMATE_OP: prefix from an earlier change. classify recognises them so old transcripts still parse, and the source says these literals "must never be used by current producers" (bin/fm-operational-input.sh:117-160).

What the marker does not do

  • It is not authentication. It tells an honest agent where text came from; it does not stop another process from writing the same bytes.
  • It does not make text executable. A marked /quit is chat, which is exactly why lifecycle moved to the control plane.
  • It is not added to crewmate or scout steers, explicit backend targets, or --key sends (bin/fm-send.sh:100-103).
