Data plane and control plane

Firstmate reaches a running agent in two separate ways: text the agent reads and thinks about, and a short fixed list of lifecycle actions that stop or replace the agent. They use different commands on purpose, because a lifecycle command sent as a message is read as chat and not obeyed.

Read against Firstmate commit ada21f5b. Owners: bin/fm-send.sh (data), bin/fm-control.sh and bin/fm-control-lib.sh (control), with the design note docs/agent-control.md. Up: Communication.

The two planes

Data plane: bin/fm-send.sh
Conversational text for the agent to read. For a kind=secondmate target it always adds the from-firstmate routing marker, because a secondmate is itself a firstmate and its reply must come back through its status channel (docs/agent-control.md:5-6). See fm-send.
Control plane: bin/fm-control.sh
Allowlisted lifecycle verbs, interrupt, exit, relaunch, addressed to an exact task id, each with a checked postcondition (docs/agent-control.md:8, bin/fm-control.sh:1-21).

Why mixing them is unsafe

The data plane's marking is right for a message and wrong for a lifecycle command. A routing-marked /quit reaches a secondmate as [fm-from-firstmate] /quit, which the agent reasons about instead of executing (docs/agent-control.md:10-12; bin/fm-control-lib.sh:5-13). The design note records that this failure repeated across harnesses and homes, and that the workaround, "remember to use an unmarked send and improvise the right key per harness", lived only in agent prose and so failed again whenever a session forgot it.

The risk runs in both directions:

  • Lifecycle over the data plane is not obeyed when marked, and when unmarked it depends on the agent guessing the right key or command for its harness, with no proof that anything stopped.
  • Text over the control plane is impossible by construction: there is "deliberately NO arbitrary-text and NO generic raw-key entry point" in fm-control.sh; "fm-send remains the only way to send an agent something to read" (bin/fm-control.sh:19-21).

The data plane's own typed path exists for the narrow case where text must reach the harness's parser, such as a slash command to a crewmate. Its classification reads the text before marking, but for a secondmate the marker still comes first, so a marked parser command still arrives as chat. fm-send keeps that behaviour for byte compatibility and names a follow-up that owns it (bin/fm-send.sh:88-94).

What the control plane guarantees

bin/fm-control-lib.sh is the one executable owner of three tables, which have no side effects and can be tested as a contract (bin/fm-control-lib.sh:15-37):

  1. Verb allowlist: interrupt, exit, relaunch (bin/fm-control-lib.sh:49-62).
  2. Per-harness mechanics: the interrupt key (Escape for most, C-c for grok), how many times (twice for opencode), the composer clear (Ctrl+U for muse only), whether cancellation can be acknowledged, and the exit command (/exit or /quit) (bin/fm-control-lib.sh:132-193).
  3. Per-backend capability: which keys a backend can deliver (Orca: Enter and C-c only) and whether it has a recovery-grade agent-state reader (tmux and Herdr only) (bin/fm-control-lib.sh:195-221).

(docs/agent-control.md:31-48.) Things that are deliberately not verbs: teardown and discard stay with bin/fm-teardown.sh; resume is not deterministic across adapters, and relaunch covers the need because "the brief on disk - not a harness-private session - is the durable instruction" (docs/agent-control.md:50-56). That last point ties the planes together: the durable text a relaunched agent reads is the brief, not anything the control plane types.

Targeting is exact: a bare task id with a state/<id>.meta record in this home, passing endpoint-identity validation. A legacy fm-<id> label, a session:window target, and a remotely placed secondmate are refused (bin/fm-control.sh:90-100). The control plane fails closed on unverified harnesses, backends that cannot deliver the key, backends without a state reader, ambiguous states, and a composer holding text (bin/fm-control.sh:101-114). The full transactional relaunch and endpoint reclaim are part of the worker lifecycle and belong to Crew.

Header and design note disagree on resume

The library header lists which adapters cannot resume deterministically as codex and grok (session id at exit), opencode (--continue), and claude, pi, pi-signed, omp, kimi (no contract) (bin/fm-control-lib.sh:39-46). The design note adds gemini to the session-id group and agy to the no-contract group (docs/agent-control.md:55). The conclusion is the same, but the header's list is stale against the verified-harness list, which includes both gemini and agy (bin/fm-control-lib.sh:67-69).

Rule of thumb, from the source

You want the agent to…Use
read an instruction, answer, or a decisionfm-send.sh <task> "…" (inbox plane)
run a harness slash command, locallyfm-send.sh <task> "/…" (typed plane; not for secondmates, see above)
stop its current turnfm-control.sh <task> interrupt
stop entirely, keeping its workfm-control.sh <task> exit
be replaced, or switch harnessfm-control.sh <task> relaunch --note "…"
be removed with its worktreefm-teardown.sh (neither plane)
