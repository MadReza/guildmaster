fm-send: steering a worker

bin/fm-send.sh is the one command Firstmate uses to give a running agent something to read. It picks between a durable inbox and direct typing, marks messages to secondmates, tracks replies it expects, and can close a decision in the same call.

Read against Firstmate commit ada21f5b. Owner: bin/fm-send.sh (its header, lines 1–216, is the contract). Up: Communication.

How it is invoked

fm-send.sh <target> [--resolve-key <key>]... [--fire-and-forget <delivery-id>] <text...>
fm-send.sh <target> --key Enter|Escape|C-c

(bin/fm-send.sh:4, bin/fm-send.sh:14-16.) Flags must come before the text; everything after the last flag is the message, so ordinary sends are byte-identical to before the flags existed (bin/fm-send.sh:463-465). Real invocations from the source:

  • The pending-reply recovery repost: env FM_HOME="$parent_home" FM_PENDING_REPLY_EXISTING_CORR="$corr" fm-send.sh "$task_id" "$msg" (bin/fm-pending-reply-lib.sh:966-967).
  • The resend command fm-send itself prints after a lost remote transport, of the form FM_HOME=… FM_PENDING_REPLY_EXISTING_CORR=<corr> …/fm-send.sh <original args> (bin/fm-send.sh:969-980).

Before anything is sent

  1. Gate agents are refused. A no-mistakes validation agent must never steer a crewmate, so the script fails closed first (bin/fm-send.sh:223-227).
  2. FM_HOME must be set explicitly and its state/ must exist. fm-send is the one script that does not default the home to the repository root (bin/fm-send.sh:229-242; docs/configuration.md:1085).
  3. A supervision guard runs (bin/fm-guard.sh) but only warns: "the requested message WILL still be sent" (bin/fm-send.sh:263).
  4. The target is resolved, strictly (bin/fm-send.sh:340-442). Accepted: an exact task id or a legacy fm-<id> label resolved through state/<id>.meta; an explicit backend target that matches recorded meta; or a well-formed explicit target whose live endpoint can be verified (one colon assumes tmux, two or more assume Herdr). Anything else is refused with what was tried. The header's reason: "a 'successful' send to the wrong endpoint is worse than a loud failure" (bin/fm-send.sh:5-9).
  5. The supervision lease is checked. If the other Pi supervision actor holds this task's lease, the steer is refused. A home without the Pi supervision branch has no lease files and passes (bin/fm-send.sh:449-461). The lease itself belongs to Supervision.
  6. Empty text is refused before anything is marked, recorded, or typed, because an empty marked request would carry only marker and correlation bytes and leave the parent waiting on a reply to nothing (bin/fm-send.sh:10-13, bin/fm-send.sh:795-798).

Choosing a plane

The header names two delivery paths, which it calls data planes (bin/fm-send.sh:18-86). Both carry text for the agent to read; neither is the control plane.

The inbox plane

This is the default for text to any task recorded in this home, local or remote (bin/fm-send.sh:20-54). The mechanics of the record and doorbell are on the steering inbox page. The local path (bin/fm-send.sh:1007-1093):

  1. Lock the task's meta file and re-read it. If the endpoint, backend, or (when a caller pinned it) spawn generation changed, or the task became remote, refuse: "the task retired or changed endpoint during target resolution" (bin/fm-send.sh:1017-1036).
  2. Write the record, idempotently only for fire-and-forget (bin/fm-send.sh:1037-1043). A write failure exits 1 and discards a freshly created reply expectation.
  3. Mark any pending-reply expectation delivered (not resolved).
  4. Close any --resolve-key decisions, now, at enqueue time.
  5. Ring the doorbell. No ring outcome changes the exit status; the three non-zero ring results each print a notice and still exit 0 (bin/fm-send.sh:1082-1092).

Exit contract: 0 means the steer is durably recorded. Nonzero means nothing was confirmed delivered and a resend is appropriate, with one exception: a decision close that failed after delivery exits nonzero and prints the exact manual close command with "do not resend the answer" (bin/fm-send.sh:26-31). There is no "delivered but unconfirmed" outcome on this plane (bin/fm-send.sh:47-50).

The typed plane

Some local text must reach the terminal itself (bin/fm-send.sh:61-80):

  • A leading / is a harness slash command.
  • A leading $ to a codex target is a codex skill invocation. The $ rule is limited to codex because ordinary text often starts with $ ("$5/month") (bin/fm-send.sh:1094-1108).
  • An explicit backend target names an endpoint, not a task, so it stays typed even if it happens to match local meta.

The text is typed once, then Enter is retried, never the text, until the backend confirms or reports an inconclusive send. Slash commands and codex $ invocations get a longer 1.2 s settle before Enter so a completion popup does not swallow it. agy targets get 20 retries instead of 3, because agy renders its busy footer late and the shorter budget reported real deliveries as failures (bin/fm-send.sh:1109-1123).

ExitTyped-plane meaning
0Submit confirmed (verdict exactly empty). Then a 1 s pause (FM_SEND_SETTLE) so an immediate peek sees the agent working, not the stale idle screen (bin/fm-send.sh:1194-1199).
3Text typed and Enter sent, but the read-back stayed pending. Do not retype: check the pane with fm-peek.sh and send --key Enter only if the text is still there. A reply expectation stays armed (bin/fm-send.sh:1150-1164).
otherFailed; per the header, nothing may be assumed delivered (bin/fm-send.sh:69-76).
Header and implementation disagree

The header says any typed-plane exit other than 0 or 3 means "the send failed and nothing may be assumed delivered" (bin/fm-send.sh:73-76). But after a confirmed submit, a failed pending-reply delivery commit exits 1 with the message "text was delivered … Do not resend" (bin/fm-send.sh:1175-1186), and a failed decision close after a confirmed submit also exits 1 (bin/fm-send.sh:1190-1193). So on the typed plane exit 1 can mean "delivered". The inbox plane made the opposite choice on purpose: bookkeeping trouble after a durable enqueue never exits nonzero, precisely so automated callers do not resend (bin/fm-send.sh:42-47, bin/fm-send.sh:1064-1072). Callers must read the message, not only the code.

The --key path

--key sends one special key and cannot carry --resolve-key or --fire-and-forget (bin/fm-send.sh:760-792). Which keys work depends on the backend: tmux and Herdr take Escape, Enter, and C-c; Orca takes Enter and C-c only (bin/fm-send.sh:14-16). After an Escape, two follow-ups run:

  • If the harness restores the cancelled prompt into its composer (muse does, and needs Ctrl+U), the composer is cleared, reading the clear key from the control plane's table rather than a second copy (bin/fm-send.sh:271-293). A failed clear is loud, because the next steer would otherwise be appended to the restored text.
  • For Claude, the interrupt is recorded in the task's busy state as idle (bin/fm-send.sh:302-320).

A remote --key crosses fm-on.sh to the remote leg's key subcommand (bin/fm-send.sh:774-786). Remote targets have no typed text plane at all (bin/fm-send.sh:81-86).

The remote leg

For a secondmate whose meta records remote_host, text goes through bin/fm-on.sh <id> fm-remote-secondmate-control.sh send <id> <message> [fire-and-forget] (bin/fm-send.sh:891-1006):

  • The parent meta is locked and revalidated first, as locally, and callers may pin FM_SEND_EXPECTED_SPAWN_GEN or FM_SEND_EXPECTED_REMOTE_HOST (bin/fm-send.sh:149-152).
  • Each attempt is bounded by FM_SEND_REMOTE_BUDGET, 30 s by default; it must be a positive integer.
  • ssh exit 255 means completion unknown, so the identical leg is retried once. This is safe because the remote write is idempotent.
  • A timeout (124) is also completion unknown, but is not retried, since a retry would only wait out the same busy queue.
  • If still unknown, a reply-bearing request's expectation moves to delivery_unknown and fm-send prints the exact FM_PENDING_REPLY_EXISTING_CORR=<corr> resend command, which reuses the correlation and lands on the same remote record. A fire-and-forget request exits 3 and says to retry only with the same delivery id.
  • Remote exit 0 means the remote record exists, which counts as delivery exactly as a local enqueue does.

The transport (ssh, fm-on.sh, the reply mirror) is covered in Remote.

Marking secondmate requests and tracking replies

When the resolved target's meta says kind=secondmate, the message gets the from-firstmate marker so the secondmate answers on its status channel rather than in a chat nobody reads (bin/fm-send.sh:96-103, bin/fm-send.sh:526-546). Crewmates, scouts, explicit backend targets, and --key are never marked. The marker is described on Operational-input markers.

Every newly marked request, except fire-and-forget, also gets a correlation id and a durable parent record before delivery (bin/fm-send.sh:105-118, bin/fm-send.sh:811-864). Delivery and reply are separate facts: delivery never resolves the expectation. The full lifecycle is on Pending replies. Two details belong here:

  • A correlation id already in the text, or given by FM_PENDING_REPLY_EXISTING_CORR, is reused if it is still open for this task. An explicitly requested id that is not reusable is refused rather than replaced (bin/fm-send.sh:819-844).
  • A local resend of a correlation whose previous delivery attempt is still unresolved is refused; a remote one is reset for an idempotent resend (bin/fm-send.sh:846-857).

Closing a decision in the same call

--resolve-key <key> (repeatable) makes this send the answer to an open keyed needs-decision: or blocked:, and fm-send itself writes the closing line. That mechanism is on Keyed decisions and --resolve-key.
