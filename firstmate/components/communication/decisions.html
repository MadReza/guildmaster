Keyed decisions and --resolve-key

A worker's question to a human is a needs-decision or blocked line with a key. It stays open until a resolved line with the same key appears, and the one who answers writes that line, so closing never depends on the busy worker remembering.

Read against Firstmate commit ada21f5b. Fold owner: bin/fm-classify-lib.sh:413-754. Answer-and-close: bin/fm-send.sh:154-208. Up: Communication.

The open/close rule

One function, _fm_decision_fold_line, states the per-line rule, and both the whole-file fold and the incremental cursor-backed fold call it, so the two cannot drift (bin/fm-classify-lib.sh:615-621, bin/fm-classify-lib.sh:678-723):

  • needs-decision or blocked opens the key, replacing any older record for that key.
  • resolved or captain-held closes it.
  • A done or failed line from a ship or scout task clears everything; from a secondmate it does nothing, because its terminal line may be about other work.
  • Any other line, including continuation prose, leaves the set alone.

Key grammar (bin/fm-classify-lib.sh:429-446):

needs-decision [key=api-shape]: <summary>     documented position
needs-decision: [key=api-shape] <summary>     accepted equivalent (issue #2109)
resolved       [key=api-shape]: <how it was decided>
needs-decision: <summary>                     no key: uses "default"

The misplaced form is accepted because it is common real worker output, and silently folding it into the shared default bucket would lose the stated key. A key with characters outside A-Z a-z 0-9 . _ - makes the line ignored, not rewritten to default. A keyless line keeps the historical rule of one open decision per task, and a bare resolved: closes default.

Unbracketed corr=<16 hex> tokens between the verb and the key are skipped, because secondmates echo them when answering a marked request. Recognition is deliberately narrow: exactly the token Firstmate writes, nothing else, so a prose word with an equals sign cannot turn a line into a transition (bin/fm-classify-lib.sh:451-500).

Who writes the closing line

"Who WRITES the closing line is owned elsewhere: the answering firstmate closes at answer time through fm-send's --resolve-key, and a worker self-closes only a blocker that cleared without an answer" (bin/fm-classify-lib.sh:424-427). The worker-facing half is in every brief: a decision "stays open until a resolved line carrying its exact key lands; a later done: or working: line never closes it", and the worker appends resolved itself only when a blocker cleared without a reply (bin/fm-brief.sh:444-446).

What --resolve-key checks, and in what order

Everything below happens before anything is sent; any failure prints the reason and "nothing was sent" (bin/fm-send.sh:616-687).

  1. The key uses only A-Z a-z 0-9 . _ - and is not repeated (bin/fm-send.sh:468-483).
  2. The target is a task selector with meta in this home. An explicit backend target has no decision ledger here. --key, an empty message, and --fire-and-forget are all refused alongside it.
  3. Each key is open right now, either in this task's status log (per status_open_decisions) or as a still-open captain-held task, looked up by the key as a task id or by the legacy <task>-decision-<key> id (bin/fm-send.sh:565-584). A key in neither is refused, so a typo cannot deliver an answer while leaving the decision silently open (bin/fm-send.sh:198-202).
  4. If any key is a needs-decision or a captain-held task, this is a decision answer, which is reserved for the main session while the captain is present. The Pi supervision branch is refused; under the away posture the rule moves to the branch (bin/fm-send.sh:180-186, bin/fm-send.sh:649-663). A blocked key is ordinary steering and takes no such guard.
  5. For each status-log key, the close note the send would write must be accepted by the fold. A reserved key (see below) with a plain answered: note would be a silent no-op, so it is refused (bin/fm-send.sh:664-678).
  6. The close line must fit the 220-character cap after its time stamp, without truncation eating the [key=…] delimiter (bin/fm-send.sh:679-686).

After the answer is durably delivered, all closes go through one self-announced append (bin/fm-send.sh:689-728). The line is resolved [key=<key>]: answered: <excerpt>, with the excerpt flattened to one line. Then fm-send re-folds the log: if the key is somehow still open, for example reopened concurrently, it exits nonzero and prints the exact printf … >> status command to close it by hand, adding "do not resend the answer". Keys that belong to captain-held tasks are fed as <task-id>\t<answer>\t lines to fm-captain-hold.sh answers, the one keyed-answer intake every channel uses (bin/fm-send.sh:730-746).

The close is always a local append, for every kind of target including a remote secondmate, because the open-decision ledger lives in this home's state/. A remote mate's escalations reach this ledger through the parent-replies mirror (bin/fm-send.sh:170-178). A failed or unconfirmed send never closes a key, and a send without the flag never closes anything: a routine steer, working:, or done: cannot clear a captain decision (bin/fm-send.sh:202-208).

Reserved keys

A key like pending-reply-<id> is raised by one library and only that library may close it. Every writer can reach the same status stream, local mates directly and remote mates through a verbatim mirror, so without a rule any writer could take over a reserved key or clear it with a bare resolved. The rule is generic: a reserved key opens or closes only on a line whose note begins with that namespace's own <prefix>…: token; otherwise the line is ordinary status (bin/fm-classify-lib.sh:622-656). Today the only reserved prefix is pending-reply-. For such a key, --resolve-key writes the owning library's note, pending-reply-resolved: task=… pending-reply-id=… via=operator-resolve-key (bin/fm-send.sh:586-596, bin/fm-pending-reply-lib.sh:1053-1071).

Where open decisions are shown

The wake digest prints "OPEN DECISIONS (still open, folded from the durable status logs - not just the latest line)", byte-capped with an "N more omitted" line (bin/fm-wake-drain.sh:429-482). A needs-decision key of the shape nm-<run-id>-<step> is how a worker tells Firstmate about a validation gate awaiting a human, and status_has_open_needs_decision looks for exactly that shape (bin/fm-classify-lib.sh:773-801).

A decision can move out of the status log into a durable captain-held backlog task. fm-captain-hold.sh complete writes the captain-held closing verb only after verifying that task exists, so "still open in status" and "already held" are two sides of one transfer (bin/fm-send.sh:555-560, bin/fm-classify-lib.sh:824-835). The hold lifecycle belongs to Backlog and decisions.
