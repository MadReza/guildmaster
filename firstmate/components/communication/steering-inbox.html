Steering inbox and doorbell

How Firstmate gets text to a running worker: the message becomes a numbered file in a per-task inbox, and the terminal only gets a short fixed "doorbell" line telling the worker to look there. The worker's acknowledgement is moving the file.

Read against Firstmate commit ada21f5b. Owner: bin/fm-task-inbox-lib.sh. Up: Communication. See also: fm-send, which writes records.

The problem it solves

Typing a whole message into an agent's terminal can fail in several ways. The message can be swallowed while the agent is busy, garbled by a completion popup, or pasted on top of text the operator is still typing. Before this design, "did the keystrokes land?" was the question every send had to answer, and there was often no reliable answer.

The library header states the adopted design (bin/fm-task-inbox-lib.sh:14-23):

  • The payload goes to the filesystem, which is reliable.
  • The terminal carries only a short constant doorbell line. That line does not need to be reliable, because ringing it again costs nothing.
  • A duplicated doorbell does nothing by construction: the worker finds the inbox empty or already handled.
  • A swallowed doorbell is noticed because no acknowledgement arrives, and the watcher rings again on a bounded schedule.
  • An endpoint that is positively dead or missing is not typed into at all. Its unhandled record surfaces through the ordinary stale wake into stuck-crewmate recovery.

So the question a sender asks changes from "did the doorbell land?" to "was the message acted on?". The second question is answered later, and only by the worker's acknowledgement (bin/fm-send.sh:47-50).

Record format

Written by _fm_task_inbox_write_record_locked (bin/fm-task-inbox-lib.sh:146-160) and read back by fm_task_inbox_body, which returns everything after the first -- line (bin/fm-task-inbox-lib.sh:241-251):

schema=fm-task-inbox.v1
at=2026-09-23T17:44:15Z
delivery=fire-and-forget        (only when the re-ring ladder must ignore it)
--
<exact message text; newlines are allowed; a marked secondmate request
 keeps its from-firstmate marker and corr token verbatim here>

Sequence numbers are never reused

fm_task_inbox_next_seq scans both the inbox root and handled/ and takes the highest number plus one, zero-padded to three digits (bin/fm-task-inbox-lib.sh:116-126). Because acknowledged numbers are counted, a number is never issued twice in one worker's lifetime. The header's conclusion: a message is processed at most once even if every doorbell is duplicated, and two racing writers can only change the order, never lose a message (bin/fm-task-inbox-lib.sh:42-45).

The lock is taken with a bounded wait, 5 seconds by default (bin/fm-task-inbox-lib.sh:128-142). A write that cannot get the lock fails, and fm-send then reports the steer as not sent.

The doorbell line

fm_task_inbox_doorbell_line builds this exact text (bin/fm-task-inbox-lib.sh:260-270):

: Firstmate instruction waiting: list '<abs inbox>'/*.msg and, in numeric order, read and act on each, then mv each handled file to '<abs inbox>'/handled/.
It is constant per inbox
It never carries the message, so ringing twice is harmless.
It explains itself
A worker whose brief is older than the inbox contract still gets the full instruction from the line alone (bin/fm-task-inbox-lib.sh:253-256).
It starts with :
That is the POSIX shell no-op. If the agent has exited and the pane is a bare shell, typing the line runs nothing.
It refuses unsafe paths
An inbox path with bytes outside printable ASCII produces no line at all, so terminal control bytes never reach the pane (bin/fm-task-inbox-lib.sh:61-62).

Ringing, and what its result means

fm_task_inbox_ring does one liveness check, one advisory composer check, then submits through the backend's shared submit core with a small retry budget (bin/fm-task-inbox-lib.sh:286-309). Its return code is advice for the log, never proof of delivery:

ReturnMeaningWhat happens next
0Rang.Nothing; wait for the acknowledgement.
1Skipped: the composer provably holds someone's unsent text (exact pending verdict).The watcher rings later.
2The backend send failed.The watcher rings later.
3Skipped: the agent is positively dead or the endpoint missing. Nothing typed.Recovery owns the record; the watcher escalates without ringing.

The skip is deliberately narrow. Only an exact pending verdict defers, because only then could the Enter submit someone's half-typed text. pending-unproven and unknown still ring: the worst outcome is a garbled constant line the worker can still understand, whereas skipping on vague verdicts would starve a harness whose idle screen the classifier cannot recognise (bin/fm-task-inbox-lib.sh:280-285).

Accepted race

Typing the line and pressing Enter are separate steps. If the agent exits between the liveness check and the keystrokes, a bare shell could receive only part of the line, and the : prefix protects only complete lines. The code accepts this and says not to add process-bound atomic delivery unless an incident reopens it (bin/fm-task-inbox-lib.sh:298-301).

The worker's side: read and acknowledge

Every brief, of every kind, carries the same receive-and-acknowledge section (bin/fm-brief.sh:248-258): when a terminal message says an instruction is waiting, and at any natural checkpoint, list *.msg, act on each in numeric order, and mv each one to handled/. The brief says plainly that without the move "firstmate rings again and eventually treats you as stuck". The brief's section is reinforcement; the doorbell alone already carries the instruction (bin/fm-brief.sh:249-252).

The re-ring ladder

The library owns the schedule; the watcher owns the checks of the pane (bin/fm-task-inbox-lib.sh:47-59). On each poll, for each recorded window, the watcher calls inbox_steer_check (bin/fm-watch.sh:450), which asks fm_task_inbox_due_action for one of three answers (bin/fm-task-inbox-lib.sh:341-394):

quiet
Nothing due: no unhandled record, the oldest is younger than the grace period, the last attempt was within the grace period, or this record was already escalated. An empty inbox also deletes .ring-state and .escalated, so the next message starts a fresh ladder.
ring <record>
One delivery attempt is due.
escalate <record> <count>
The attempt budget is spent.

The watcher then applies the pane checks (bin/fm-watch.sh:434-507):

  1. If the backend says the agent is dead or the endpoint missing, it skips the ladder entirely and queues one stale wake: "unread firstmate instruction … the worker's agent has exited or its endpoint is missing, so the doorbell was not typed; recover the worker" (bin/fm-watch.sh:419-432).
  2. If the pane is busy, it waits. The record is durable and the worker will reach a turn boundary.
  3. If it is idle and a ring is due, it rings and records the attempt. A failed ring and a composer-protected skip both count against the budget, so neither an unreadable pane nor a permanently full composer can retry silently forever (bin/fm-task-inbox-lib.sh:396-402).
  4. When the budget is spent it queues a stale wake: "unread firstmate instruction: <record> still unhandled after N doorbell delivery attempts with an idle pane; inspect the worker".

Two ordering rules matter for failure:

  • Wake before marker. The stale wake is queued before .escalated is written. A crash in between can produce a rare duplicate wake, never a lost one (bin/fm-task-inbox-lib.sh:56-59, bin/fm-task-inbox-lib.sh:421-424).
  • Unwritable bookkeeping is loud. If .ring-state cannot be written while the record is still unhandled, the watcher raises its own stale wake ("steering-inbox ladder bookkeeping unwritable") instead of re-ringing forever (bin/fm-watch.sh:483-492). A record that disappeared meanwhile, because it was acknowledged or torn down, makes this a quiet no-op.

Ordinary attempts are data-plane typing, not wakes, so they do not interrupt Firstmate. The check also runs for secondmates: their exemption from pane-staleness is about quiet panes being healthy, but an unacknowledged instruction is a stuck steer (bin/fm-watch.sh:444-449, bin/fm-watch.sh:2621-2623). How a stale wake is handled from there belongs to Supervision.

Fire-and-forget records

A record carrying delivery=fire-and-forget is skipped by fm_task_inbox_oldest_unhandled, so it never enters the ladder and never escalates (bin/fm-task-inbox-lib.sh:311-339). fm-send writes one only for a marked secondmate request sent with --fire-and-forget <16-hex-id>, which also creates no reply expectation (bin/fm-send.sh:119-124).

Plain and idempotent writes

There are two write functions, and the choice is deliberate (bin/fm-task-inbox-lib.sh:176-186):

fm_task_inbox_write
Always a new record. Used for local sends, whose outcome is known immediately, so an identical second send is a deliberate new instruction.
fm_task_inbox_write_idempotent
If a record with byte-identical body already exists, unhandled or in handled/, it returns that record's path instead of writing (bin/fm-task-inbox-lib.sh:187-238). This is for a transport that can fail with the outcome unknown, such as the ssh leg to a remote secondmate: re-running the same enqueue lands on the same record. Two different requests do not collapse in practice because a marked request carries a per-request correlation token in its body. Fire-and-forget and ordinary records are compared only with their own kind.

The remote leg's host-local side (bin/fm-remote-secondmate-control.sh:256-297) uses the idempotent write, and if the match is already in handled/ it rings nothing: "this steer was already delivered and acknowledged". The remote host runs no re-ring ladder of its own; a swallowed remote doorbell is caught by the parent's pending-reply recovery instead (bin/fm-send.sh:145-148). Cross-host transport itself is covered in Remote.

Failure behaviour at a glance

SituationResult
Inbox cannot be created or locked, or the record cannot be writtenNo partial record. fm-send exits nonzero: "steer not sent".
Doorbell swallowed or garbledWatcher rings again on an idle pane, up to the budget.
Worker never acknowledgesStale wake after the budget; stuck-crewmate recovery takes over.
Agent exited or pane goneNothing typed; one stale wake straight away.
Doorbell duplicatedNo effect: the worker finds nothing new.
Ladder file unwritableStale wake naming the unwritable file.

What it deliberately does not do

  • It never types the message body into the terminal.
  • It never treats a successful keystroke as delivery.
  • It never rings a pane whose agent is known to be gone.
  • It never interrupts a busy pane to ring.
  • It does not read the worker's conversation to decide whether the message was understood; only the file move counts.
