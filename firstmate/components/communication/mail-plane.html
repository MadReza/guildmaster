Mail plane

An ordinary mail client for Firstmate: it reads unseen mail over IMAP and sends over SMTP. Each new message becomes exactly one durable check wake, and a mail is never lost even if the poll is interrupted, at the cost of a rare duplicate.

Read against Firstmate commit ada21f5b. Owners: bin/fm-mail.sh (with bin/fm-mail.py for IMAP and SMTP), the standing check bin/fm-mail-check.sh, and the schema in docs/configuration.md:656-686. Up: Communication.

Not a source of authority

"This is an ordinary mail client surface, not an escalation of authority: every surfaced message is a notification firstmate reads before deciding, and firstmate still applies its own judgment exactly as it would for a TUI message" (bin/fm-mail.sh:5-8). The plane is off unless the home's gitignored .env supplies the connection values (docs/configuration.md:664).

(bin/fm-mail.sh:10-32.) Reads use BODY.PEEK, so no message is ever marked read before Firstmate actually answers it, and mail already marked seen in IMAP never wakes a poll.

Exactly-once, recovering

Each surfaced message is keyed by its immutable IMAP UID, together with the mailbox generation (UIDVALIDITY) when the server reports one, so expunge renumbering never re-wakes or loses mail, and a recreated mailbox cannot reuse a number to suppress a new wake (bin/fm-mail.sh:17-31). wake_for appends the wake first, then the durable records, all under one lock (bin/fm-mail.sh:338-409):

ReturnMeaning
0Wake appended and a durable uid record landed.
1Wake appended, then rolled back because no record could be written; retried next poll.
2Wake survived with no durable record (fail-closed); the drain delivers it and the next poll heals the uid.
3Wake never appended; retried next poll.
4Delivered, but clearing the retry entry failed.

The one residual the code accepts is a kill in the instant between the queue append and the journal write, followed by the drain acknowledging that row before the next poll heals it: that mail wakes twice. "A possible duplicate (never a missed mail) is the deliberate, bounded tradeoff" (bin/fm-mail.sh:351-356; docs/configuration.md:660-661).

  • Floods are bounded. One poll surfaces at most FM_MAIL_POLL_MAX_WAKES messages (default 20, clamped to 200); the rest stay unseen for the next poll, so the wake queue stays bounded (bin/fm-mail.sh:34-37, bin/fm-mail.sh:125-131).
  • Unreadable headers are not skipped. A message whose header fetch fails is woken once with placeholders, retried on later polls, and re-woken once with the real sender and subject when the fetch succeeds (bin/fm-mail.sh:37-39).
  • Overlapping polls are serialised on a mail-seen lock (bin/fm-mail.sh:27).

State files, all under state/ and written only by fm-mail.sh: .mail-seen (cursor), .mail-woken (emission journal), .mail-retry and .mail-retry-pos (retry set), .mail-turn, and .mail-seen.lock (AGENTS.md:131).

Running unattended

poll has no scheduler of its own. bin/fm-mail-check.sh arm writes state/mail.check.sh and registers its bytes with the watcher's check-trust mechanism, so the watcher runs it on its slow cadence (FM_CHECK_INTERVAL) (bin/fm-mail-check.sh:10-19). The check prints a line, which becomes a check: wake, whenever the poll is not a proven no-op. Silence is reserved for a successful poll with no new mail or a repeated identical failure that could not have queued mail; a timeout or a fail-closed poll that already queued a wake always prints (bin/fm-mail-check.sh:27-37). A home armed before its .env is complete is told once about the missing value, "which makes a partially configured channel a wake instead of a silent gap" (bin/fm-mail-check.sh:21-25). How the watcher runs and trusts checks belongs to Supervision.

Configuration

Environment values win over .env, matching Relay. FM_MAIL_PASS is never logged. Only implicit TLS is supported: STARTTLS and port 587 are not (bin/fm-mail.sh:41-62).

Open question

The sources read here say how mail is surfaced and sent, but not what rules govern Firstmate replying to a mail sender, or how mail bodies are treated as untrusted input once read. fm-mail.sh defers that to Firstmate's own judgement "exactly as it would for a TUI message" (bin/fm-mail.sh:7-8). Any skill-level policy would sit in Prompts and skills.
