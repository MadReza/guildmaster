End to end: a question to a secondmate

One realistic path through most of this area: the main firstmate asks a local secondmate for an audit, the secondmate answers on its parent channel, and the watcher matches the answer to the question. Then the two ways it goes wrong, and what catches each.

Read against Firstmate commit ada21f5b. Every step cites the code that performs it. Up: Communication.

The setting

A main home has a secondmate recorded as task sm-infra, with kind=secondmate in state/sm-infra.meta, running in a local tmux pane. Its home's .fm-secondmate-parent says route=local and names the main home, so its parent channel is the main home's state/sm-infra.status. (The id is illustrative; the file shapes are those documented on the linked pages.)

What if the doorbell is swallowed?

Say the secondmate's composer was mid-render and step 6 was lost. Nothing is typed again at once: the record exists and fm-send already exited 0.

  1. On each poll the watcher runs inbox_steer_check. After 90 s, with the pane idle, it rings again, and records the attempt in .ring-state (bin/fm-watch.sh:450-494).
  2. If three attempts go unacknowledged on an idle pane, it queues stale: … (unread firstmate instruction: …/001.msg still unhandled after 3 doorbell delivery attempts with an idle pane; inspect the worker) and writes .escalated (bin/fm-watch.sh:495-506).
  3. If the mate's agent had instead exited, nothing is typed at all and that stale wake is raised immediately (bin/fm-watch.sh:419-432).

The pending-reply guard runs independently and does not know the doorbell was lost. An idle pane observed after delivery counts as a completed request turn even without a busy phase first, an allowance meant for turns too fast to catch (bin/fm-pending-reply-lib.sh:729-737). So if the pane stays idle, after 120 s the guard sends its one recovery repost through fm-send, which lands as a second inbox record, 002.msg, and rings the doorbell again. The two mechanisms therefore overlap here: the worker can find both records when it finally looks. Neither loops: the ladder stops at its budget and the guard sends one recovery. See the ladder and recovery.

What if the secondmate answers only in chat?

This is the failure the parent channel and pending replies were built for (docs/secondmate-parent-channel.md:9-14). Steps 1–9 happen, but step 10 is missing: the mate wrote "Captain, the audit is clean" in its own conversation.

  1. The tick observes the secondmate's pane go busy after delivery, then idle, and records the request turn as completed (bin/fm-pending-reply-lib.sh:700-747). Only the pane's busy footer is read, never the conversation.
  2. Once 120 s have passed since delivery with no correlated line, it sends exactly one recovery through fm-send, reusing the same correlation: REPOST REQUIRED: previous marked request had no correlated parent report. Reply on the parent status channel including corr=<id>. … The phase goes recovery_sending → recovery_sent (bin/fm-pending-reply-lib.sh:909-977).
  3. If the mate now posts the line, the record resolves as in step 11.
  4. If the recovery turn also ends without it, the tick appends one escalation to the parent channel and the record becomes escalated: blocked [key=pending-reply-<corr>]: pending-reply-missed: task=sm-infra pending-reply-id=<corr> request=Audit the CI config and report (bin/fm-pending-reply-lib.sh:1209-1271). A blocked line is captain-relevant, so it wakes Firstmate and appears under OPEN DECISIONS.
  5. If the mate had appended its correlated line to its own home's state/sm-infra.status by mistake, the guard copies that one line onto the parent channel and resolves instead of escalating (bin/fm-pending-reply-lib.sh:1339-1359).
  6. A late correlated line still resolves an escalated record, and the library then closes its own escalation with resolved [key=pending-reply-<corr>]: pending-reply-resolved: …, written so it does not wake Firstmate again (bin/fm-pending-reply-lib.sh:1143-1185).

At no point does anything read the secondmate's chat, loop, or silently drop the expectation.
