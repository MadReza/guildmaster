Secondmate parent channel

A secondmate is a full firstmate in its own home, and nobody reads its chat. Everything it owes the captain travels up as lines appended to one status file in the parent home, and the scripts that record an outcome publish it there themselves, so delivery does not depend on the mate remembering.

Read against Firstmate commit ada21f5b. Owner: bin/fm-parent-channel-lib.sh; route record parser bin/fm-secondmate-parent-lib.sh; design note docs/secondmate-parent-channel.md. Up: Communication.

The problem it solves

On 2026-09-02 four outcomes across two mate homes never reached the captain. Each time the watcher had delivered the parent's request within a minute and the mate had done the work, but the mate then addressed "captain" in its own chat instead of appending to the channel (docs/secondmate-parent-channel.md:9-14). The design note calls the cause structural: the mate can obey the charter's rule about addressing the captain in local chat while missing the later rule about the return channel. A PR-ready report was the symptom, but findings, decisions, blockers, and failures all fail the same way because each depended on the model writing one line.

The goal adopted: "the parent channel must not depend on the model remembering to write to it" (docs/secondmate-parent-channel.md:16). The rule that delivers it: "the scripts report facts, the mate reports judgement" (docs/secondmate-parent-channel.md:20-21).

Where the channel is

The destination is resolved from the home's own durable identity, "never from a caller's choice" (bin/fm-parent-channel-lib.sh:31-41):

  • .fm-secondmate-home holds the mate's id in its parent home. No file means this is a main home and there is nothing to report. The id must be path-safe (bin/fm-parent-channel-lib.sh:69-93).
  • .fm-secondmate-parent names the route. A local route appends to <parent_home>/state/<mate-id>.status. A remote route appends to this home's own state/parent-replies.status, which the parent's remote reply adapter mirrors line for line into that same parent file.

The parent watcher classifies lines there "exactly as it classifies any crewmate's status stream", so everything on the status channel page applies. The secondmate brief says the same thing to the mate: "Nobody reads this chat … That file is your parent channel, and in this home it IS the captain" (bin/fm-brief.sh:303-307).

The parent binding record

schema=fm-secondmate-parent.v1
route=local
parent_home=/absolute/path/to/parent/home

schema=fm-secondmate-parent.v1
route=remote
parent_host=<ssh alias, diagnostic only; may be absent in legacy manifests>

Exactly one schema and one route. A local route needs exactly one absolute parent_home and no parent_host; a remote route has no parent_home. Unknown fields are allowed for later additions. Duplicates, a malformed binding, an unknown route or schema, a symlink, and any NUL byte all fail closed. The NUL check exists because different bash versions handle NUL differently and could resolve to a home the bytes never name (bin/fm-secondmate-parent-lib.sh:1-70). Writers publish this record before .fm-secondmate-home, so the identity marker is the "seed complete" point.

The ledger delivery reads files only and calls no harness, forge, or state reader, so it behaves the same on every harness and backend. Each delivery is keyed with the first eight hex characters of a receipt fingerprint, so a replayed poll or restart cannot deliver an event twice while a genuinely new terminal event is delivered again (docs/secondmate-parent-channel.md:35-37).

How one line is appended

fm_parent_channel_report <home> <state> <line> resolves the destination, stamps the line with its emission time, and appends it once (bin/fm-parent-channel-lib.sh:147-153). "Once" uses the status channel's retry rule: if the same event is already there, ignoring only a well-formed time tag, nothing is written (bin/fm-parent-channel-lib.sh:132-145). An existing destination must be a regular, non-symlinked file; a missing one is created with its directory. Notes copied from a child ledger are flattened to one line and cut at 1200 characters so they cannot break the line framing (bin/fm-parent-channel-lib.sh:126-130).

ReturnMeaning
0Resolved, or appended, or already present
1A main home: nothing to report
2Identity marker unusable (symlink, NUL, bad id)

"A caller that has already recorded the outcome locally must surface a non-zero return rather than treat it as delivered" (bin/fm-parent-channel-lib.sh:47-54).

What the mate still writes

The brief reserves the mate's own appends for judgement: the answer to a marked request, a recommendation or caveat on a delivered outcome, its own blocker or failure, and anything else it would say to the captain (bin/fm-brief.sh:306-307). A duplicate is harmless and a miss is not, so the mate may still comment on a delivered outcome; the parent reads the script's line as the fact and the mate's as commentary (docs/secondmate-parent-channel.md:37). Answers to marked requests carry a correlation token and are tracked by pending replies, which can also repair a correlated line the mate wrote into its own home's same-named status file by mistake (docs/secondmate-parent-channel.md:38-41).

The optional helper writes that answer without ever taking a path from the caller (bin/fm-secondmate-report.sh:10-23):

fm-secondmate-report.sh done abcdef0123456789 "audit clean"
fm-secondmate-report.sh --doc done abcdef0123456789 data/x/report.md "see report"

What was deliberately not built

  • No mirror of the mate's chat: picking which sentence is an outcome would itself be model behaviour, and every harness exposes turn text differently.
  • No automatic escalation of a child's open decision after a threshold: an escalated decision is a captain hold, which is already published.
  • No second watcher or standalone scanner: the ledger pass runs inside the existing inactive-outcome command on every watcher poll.
  • No orphan lifecycle: teardown refuses instead of removing an undelivered outcome.
