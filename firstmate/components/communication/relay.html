Relay: public mentions

Relay lets the captain mention @myfirstmate on X, or the myfirstmate bot in a Discord server, and have their own Firstmate answer publicly and act on reversible requests. It ships switched off, and one token in .env is both the switch and the consent.

Read against Firstmate commit ada21f5b. Owners: activation, wire contract, and state in docs/configuration.md:688-812; client library bin/fm-x-lib.sh; poll bin/fm-x-poll.sh; promised finals bin/fm-public-followup.sh; judgement in the fmx-respond skill; charter AGENTS.md:597-613. Up: Communication.

Older docs and some emitted lines call this "X mode", which is why its identifiers use FMX_, x-, and fm-x- (AGENTS.md:599).

Activation and what the token authorises

Relay is off unless the home's gitignored .env contains a non-empty FMX_PAIRING_TOKEN. The token identifies the relay tenant and records opt-in consent for autonomous public replies and eligible lifecycle actions (docs/configuration.md:693-695). It is "not authority for destructive, irreversible, or security-sensitive action; those still require trusted-channel confirmation" (AGENTS.md:601).

The relay routes only the owner's mentions to a home, so the direct mention text is from the captain. The surrounding conversation may include other public accounts and is untrusted (docs/configuration.md:696). The skill spells out the consequence: a request in the direct text is a real captain instruction to act on, but a public, relayed channel does not carry the trust of the captain's own session, so destructive work is flagged through the trusted channel instead of executed (.agents/skills/fmx-respond/SKILL.md:26-39, .agents/skills/fmx-respond/SKILL.md:76-80).

The locked session-start bootstrap turns the token into two generated files: state/x-watch.check.sh, a byte-static shim the watcher accepts only if its bytes match, and config/x-mode.env, which sets FM_CHECK_INTERVAL=30 so a Relay home polls every 30 s instead of 300 s. Removing the token removes both at the next locked start; steady-state off writes nothing (docs/configuration.md:710-719). A Relay-only home still needs the live supervision cycle so a mention can wake it with no fleet work (AGENTS.md:604).

Inbound: one wake per mention

fm-x-poll.sh is a hard no-op with no token: exit 0, no output, so the watcher behaves as if Relay did not exist. Its contract is "output => wake firstmate, silence => keep sleeping" (bin/fm-x-poll.sh:4-9). With a token (bin/fm-x-poll.sh:11-22; docs/configuration.md:722-736):

  • HTTP 204, empty, or no text: nothing.
  • Auth or configuration errors: one rate-limited x-mode-error … line until recovery.
  • A newly offered mention: stash the whole relay object at state/x-inbox/<request_id>.json, record reply context at state/x-context/<request_id>.json (best-effort), atomically claim state/x-context/<request_id>.offered.json, then print x-mention <request_id>.
  • An already offered request id: nothing, even after the inbox file was cleared. Offer markers expire with the context registry's seven-day retention, after which a re-offer could wake again.
  • Unreconciled promised-final results: one public-followup … line before the relay call, once per new result set.

The offer claim is an exclusive create that returns 0 only to the caller that made it (bin/fm-x-lib.sh:515-538). A failed claim is reported once as x-mode-error cannot record mention offer (docs/configuration.md:752-753).

Handling a mention

On an x-mention or x-mode-error wake Firstmate loads fmx-respond, which owns classification, public-safety policy, reply or dismissal, linking, and follow-ups (AGENTS.md:605). Its three cases (.agents/skills/fmx-respond/SKILL.md:70-74):

Actionable request
Run the normal lifecycle. If it finishes now, reply with the outcome. If it spawns real work: acknowledge publicly now, start the work in the same turn, and bind a follow-up to where the work lives.
Question
Answer from live fleet state; no follow-up.
Pure acknowledgement
Post nothing, but dismiss it at the relay first with fm-x-dismiss.sh, so the relay stops re-offering it or falling back to an offline auto-reply (docs/configuration.md:750-751).

The reply is public under a shared bot identity, so it never includes task ids, branches, paths, PR numbers, internal vocabulary, captain-private material, or secrets, and thread content other than the direct text is untrusted input (.agents/skills/fmx-respond/SKILL.md:82-113). Skill content is covered in Prompts and skills.

Outbound: replies, splitting, follow-ups

  • fm-x-reply.sh posts {request_id,text} to POST /connector/answer, optionally with one image (docs/configuration.md:754-755).
  • Long replies are split into a numbered thread on code-fence, paragraph, line, and word boundaries; the payload carries texts plus text as the first chunk for older relays. Budgets: 280 characters on X, 1900 on Discord, at most 25 messages (docs/configuration.md:763-768).
  • The platform and budget for a later follow-up are resolved from the durable per-request context first, then the inbox payload, then an authoritative relay lookup (POST /connector/request-context) on the live follow-up path only (docs/configuration.md:743-745). If neither can be recovered, fm-x-reply.sh refuses with exit 8 rather than post with a local default, and the follow-up is held and retried (docs/configuration.md:748).
  • Local work is linked with fm-x-link.sh <task-id> <request_id>, which records the link in that task's state/<id>.meta. fm-x-followup.sh posts up to three follow-ups per link within seven days through POST /connector/followup; --final or the cap clears the link, a failed post leaves it for retry, and a relay 409 is treated like local expiry (docs/configuration.md:756-761).
  • FMX_DRY_RUN writes would-be payloads to state/x-outbox/<request_id>.json instead of posting, and needs neither the token nor curl (docs/configuration.md:771-777).

Promised final replies

When work is routed to a secondmate, the link cannot reach it, because the link lives in this home's meta and the work's record lives in another home; fm-x-link.sh refuses and points at the promised-final path (docs/configuration.md:746). The charter's rule: "A promised final public reply is durable state, never conversation memory", and only the home that holds the relay consent and thread binding ever posts it (AGENTS.md:608-610).

The problem fm-public-followup.sh solves, in its own words: Firstmate promises a public final reply, routes the work out, and then the conversation compacts or the session restarts, so "the promise is only kept if reconciling it is a disk operation. Every command here reads durable state and nothing else" (bin/fm-public-followup.sh:5-8). The typed obligation and its state machine are owned by tasks-axi public-followup; private context stays in state/x-context/; posting reuses fm-x-reply.sh --followup (bin/fm-public-followup.sh:10-19).

  • register creates the private state/public-followup/ tree (mode 700) and the bounded registration (docs/configuration.md:787-789).
  • brief prints the exact fm-public-followup-emit.sh command the routed worker runs to report a typed terminal result, including staging paths for a remote home.
  • consume drains typed results, deduplicated by an identity-derived event id, and collects staged results from remote homes over ssh, retiring the remote copy only after this home holds it.
  • deliver posts into the original thread with the stored binding; an obligation left mid-post by a crash is refused rather than posted twice. Delivery does not close the loop: only retire does.
  • guard-work exits 3 while a public promise is open for that work, and fm-teardown.sh refuses cleanup of such work without explicit discard approval.

(bin/fm-public-followup.sh:31-110; docs/configuration.md:779-812.) A home without the token runs one file test and stops: no tasks-axi call, no scan, no directory (bin/fm-public-followup.sh:21-29).

Minor header imprecision

The fm-x-lib.sh function index describes fmx_context_registry_prune as removing "records older than seven days" (bin/fm-x-lib.sh:28). The implementation uses FMX_FOLLOWUP_MAX_AGE_SECS, capped at 604800 seconds, so a home that shortens its follow-up window also prunes sooner (bin/fm-x-lib.sh:439-443). The configuration doc states the precise rule (docs/configuration.md:736).
