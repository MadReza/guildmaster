Pending replies

When the main firstmate asks a secondmate something, it writes down that it expects an answer before sending, tags the request with a random correlation id, and waits for a status line carrying that id. If none comes, it asks exactly once more, then escalates exactly once. It never reads the secondmate's chat.

Read against Firstmate commit ada21f5b. Owner: bin/fm-pending-reply-lib.sh (header lines 1–106 are the contract). Up: Communication.

The problem it solves

A secondmate may ignore the marker and answer only in its own visible conversation, which the parent never reads. The captain's direction, dated 2026-07-22 in the header, sets the safety property (bin/fm-pending-reply-lib.sh:11-20): the parent must notice the missing correlated report without scraping that conversation, send exactly one automatic recovery request asking for a repost on the parent channel, and escalate once if the recovery turn also ends without a report. "Never loop, never repeatedly inject, never silently expire unresolved records, and never treat wrong-home or structured-home heuristics as acknowledgement."

Lifecycle

The record

One key=value file per request at state/pending-replies/<corr_id> in the parent home, directory mode 700 and file mode 600 (bin/fm-pending-reply-lib.sh:296-357). Notable fields from the schema (bin/fm-pending-reply-lib.sh:27-67):

corr_id
16 lowercase hex characters (64 bits), from openssl rand -hex 8 or a hash fallback (bin/fm-pending-reply-lib.sh:153-165). Called "privacy-safe" because it carries nothing about the request.
parent_status
Absolute path of the parent's state/<task_id>.status, the only place a reply counts.
request_summary
One line, printable ASCII, at most 120 characters, marker and token stripped (bin/fm-pending-reply-lib.sh:187-198).
delivered_epoch
Empty until delivery is confirmed. "Delivery never resolves."
phase
One of the eight phases above.
wrong_home_*
Sightings of the token in the secondmate's own home, recorded as evidence, never as acknowledgement.

The correlation token on the wire

fm_pending_reply_embed_corr puts the token right after the from-firstmate marker, replacing a different leading token if one is there (bin/fm-pending-reply-lib.sh:271-292):

[fm-from-firstmate]<U+2063>corr=0123456789abcdef <request text>

The secondmate's brief tells it to include that exact token in its parent status reply, or in the status line pointing at a detailed document (bin/fm-brief.sh:313-316).

Delivery is not a reply

fm-send creates the record before delivery (bin/fm-send.sh:811-864) and writes a sidecar .delivery-confirmed-<corr> saying attempted=<epoch> (bin/fm-pending-reply-lib.sh:395-405). After a durable enqueue it confirms, which writes confirmed=<epoch>, sets delivered_epoch, then removes the sidecar (bin/fm-pending-reply-lib.sh:407-432). The sidecar exists so a crash between those steps is repairable: the watcher's reconcile finishes a confirmed sidecar, and turns an attempted one older than the grace into delivery_unknown (bin/fm-pending-reply-lib.sh:448-486). A known failed send deletes the record entirely, "so transport failure does not masquerade as a missed report later" (bin/fm-pending-reply-lib.sh:552-563).

What counts as a reply

Any line in the parent status file that contains the exact corr=<id> token resolves the record, except the parent's own pending-reply-missed escalation, which names the request with pending-reply-id= instead (bin/fm-pending-reply-lib.sh:565-577). The match is on the token anywhere in the line; the verb does not matter. The record also notes how it was resolved, by a loose text heuristic: a line mentioning data/…report, report.md, document, or pointer is document; one mentioning via-helper or fm-secondmate-report is helper; anything else is status (bin/fm-pending-reply-lib.sh:614-628). The scan is skipped when the status file's stat signature has not changed since the last miss (bin/fm-pending-reply-lib.sh:672-684).

Knowing the turn ended, without reading chat

Recovery waits until the secondmate's turn on the request is over. The library prefers a busy-then-idle transition of the secondmate's endpoint, but also accepts a plain idle reading after delivery, for turns so fast the first observation missed the busy window (bin/fm-pending-reply-lib.sh:700-747). A consequence: a mate that never started its turn, for example because the doorbell was lost, still reads as "turn completed" once it is seen idle. The observation first asks the backend's native busy state, then falls back to matching the recorded harness's busy signature in the last few non-blank lines of the pane (bin/fm-pending-reply-lib.sh:772-802). This reads the pane's footer, not the conversation, and the comment is explicit that it is a delivery-confirmation signal, "never task state". A weak idle reading (fallback-idle) is accepted as idle only after the grace window (bin/fm-pending-reply-lib.sh:749-817). For a remote secondmate the observation runs on the remote host through fm-on.sh … observe (bin/fm-pending-reply-lib.sh:1532-1535).

The one recovery request

When the request turn completed, the grace (120 s by default) has passed since delivery, and no report arrived, fm_pending_reply_send_recovery sends exactly one repost through fm-send, reusing the same correlation so no second record is created (bin/fm-pending-reply-lib.sh:920-977):

REPOST REQUIRED: previous marked request had no correlated parent report. Reply on the parent status channel including corr=<id>. Original request: <summary>

(bin/fm-pending-reply-lib.sh:909-918.) The attempt is recorded before sending, with the sender's pid and a process identity string, so a sender that dies mid-send is detected later and the phase becomes recovery_unknown rather than hanging (bin/fm-pending-reply-lib.sh:979-1039). A second recovery is never sent: once recovery_attempted_epoch is set, the function only reconciles.

Remote secondmates and the mirror watermark

A local mate writes straight into the parent file, so an absent line is evidence. A remote mate's lines arrive through an asynchronous mirror, so absence proves nothing until the mirror has read past the turn that should have produced the report. The mirror publishes state/remote-replies/<task>.caught-up, and recovery and escalation both wait until that watermark is at or after the turn's completion (bin/fm-pending-reply-lib.sh:841-907). Without this, the guard would nag for replies that were written but not yet mirrored, "the common case, because the mirror's poll window is comparable to the recovery grace". A mirror that is behind or broken simply never advances the watermark, so the request stays open and un-nagged, and the mirror escalates its own continuity failures.

Escalation

An escalation opens a durable keyed decision in the parent status log, under a per-request key in the reserved pending-reply- namespace (bin/fm-pending-reply-lib.sh:69-83, bin/fm-pending-reply-lib.sh:1041-1046):

blocked [key=pending-reply-<corr>] [at=…]: pending-reply-missed: task=<id> pending-reply-id=<corr> request=<summary>

The token after the colon is one of pending-reply-missed, pending-reply-delivery-unknown, pending-reply-recovery-delivery-failed, or pending-reply-recovery-delivery-unknown (bin/fm-pending-reply-lib.sh:1073-1094). A missed-report escalation also names where the token was seen in the wrong home, as a readable path and line (bin/fm-pending-reply-lib.sh:1255-1260). It is written once; status_event_recorded prevents a duplicate (bin/fm-pending-reply-lib.sh:1263-1266). Just before escalating, a late report still wins (bin/fm-pending-reply-lib.sh:1244-1247).

Because the library opened the decision, it also closes it. When an escalated record later resolves, it appends resolved [key=pending-reply-<corr>]: pending-reply-resolved: task=… pending-reply-id=… via=… through the self-announced append, and only while that exact decision is still open (bin/fm-pending-reply-lib.sh:1119-1185). The watcher's tick retries this close on every poll until it lands (bin/fm-pending-reply-lib.sh:1452-1456). An operator can close it too with fm-send --resolve-key, which writes the same vocabulary.

A delivery_unknown escalation is different: the request may never have arrived, so the owner may resend under the same correlation. That resets the record to awaiting_report and leaves the published escalation open, because only a correlated report settles the request. A delivered record is never reset (bin/fm-pending-reply-lib.sh:85-96, bin/fm-pending-reply-lib.sh:513-550).

Replies written to the wrong home

A local secondmate is itself a firstmate, so it can append to its own home's state/<id>.status when it meant the parent's file with the same name. The library handles this narrowly (bin/fm-pending-reply-lib.sh:1273-1359):

  • Every correlated line found in the mate home's status files is recorded as a sighting, never as acknowledgement. The remote route's parent-replies.status is skipped, because that is the channel.
  • Only the file with the same base name as the task, <mate-home>/state/<task_id>.status, is copied: its correlated line is restated onto the parent channel, which then resolves normally. The header calls this "a repair of the FM_HOME-relative mixup, not acknowledgement of an arbitrary mate-home file" (bin/fm-pending-reply-lib.sh:18-20).

Who drives it

The watcher calls fm_pending_reply_tick "$STATE" on every poll (bin/fm-watch.sh:2322-2326). The tick walks every record, caches one endpoint observation per task per tick, and runs the per-record step: reconcile delivery, try to resolve, reconcile recovery, check wrong-home, observe the turn, try to resolve again, send recovery if due, escalate if due (bin/fm-pending-reply-lib.sh:1434-1548). Resolved records are kept, not deleted; an escalated record is "retained; never auto-delete" (bin/fm-pending-reply-lib.sh:1394-1395).
