Learnings and captain preferences

Three curated files hold what a home has learned and how the captain likes to work; they are printed into every session start, kept under a token budget, and may only be changed by reading the whole file first and replacing what a new fact supersedes.

The three files

FileHoldsOwner and scopeDefault tier
data/captain.md"this home's domain-local captain preferences and working style"The home itself; "canonical even if harness memory mirrors it" (AGENTS.md:94)pinned
data/captain-shared.md"main-authoritative shared captain preferences propagated read-only to secondmate homes"The primary home, under secondmate-provisioning (AGENTS.md:95)pinned
data/learnings.md"fleet-local operational facts and gotchas"The home itself; "dated, evidence-backed, curated ... rewrite and prune rather than append forever"; created lazily (AGENTS.md:96)aging

All three are local and gitignored with the rest of data/ (AGENTS.md:92). The rule that makes them authoritative regardless of any harness-level memory feature: "Treat data/captain.md as the domain-local record of captain preferences, optional data/captain-shared.md as the main-authoritative shared captain-preference file for secondmate inheritance, and data/learnings.md as curated home-local knowledge, regardless of harness memory" (AGENTS.md:164). Terminology note for Guildmaster readers: these are what TERMINOLOGY.md calls the Lorebook and Standing Orders.

How they are read

The locked session start prints them in its context digest, "the full contents of data/projects.md, data/secondmates.md, data/captain.md, data/captain-shared.md, and data/learnings.md, each clearly delimited" (AGENTS.md:205, bin/fm-session-start.sh:949-951). A missing file prints as ABSENT, meaning built-in defaults, no shared preferences, or "no captured learnings" (AGENTS.md:177). The agent is told to trust that digest and not re-read those inputs "unless a source was reported absent or corrupt, older history is specifically needed, or a targeted workflow must inspect before writing" (AGENTS.md:176). That last exception is inspect-then-update.

Because they are loaded every session, their size is bounded. config/startup-memory-budget is a per-home budget, "materialized as 7,500 estimated tokens by locked primary bootstrap and inherited into secondmate homes" (AGENTS.md:80). bin/fm-startup-memory-budget.sh report gives the estimate, which the stow skill calls "the documented conservative local approximation, not provider-exact accounting" (.agents/skills/stow/SKILL.md:80-83).

Where a fact belongs

Before anything is written, it is routed to "its most specific owner" (AGENTS.md:273-280):

  • Home-domain captain preferences go to data/captain.md "after inspect-then-update".
  • Preferences shared across secondmate domains go to the primary's data/captain-shared.md.
  • Fleet-local operational facts go to data/learnings.md.
  • Task notes go with the backlog item; investigation findings go in the scout report.
  • Knowledge for almost every contributor to one project goes in that project's committed AGENTS.md, written only by a crewmate through the delivery path.
  • Knowledge for every Firstmate user goes in the Firstmate repository itself.

A secondmate that discovers a shared preference does not edit the inherited file; it routes the finding to the main firstmate through marked status or a document pointer (.agents/skills/stow/SKILL.md:222).

The inspect-then-update discipline

docs/architecture.md states it in one line: "Memory writes use inspect-then-update rather than blind append" (docs/architecture.md:448). The stow skill defines what that means for every retained fact: "ask which current statement it supersedes, whether it can be a one-sentence rewrite, and whether a stale entry should be refreshed, archived, or routed to an existing stronger owner" (.agents/skills/stow/SKILL.md:230-231). Concretely:

  1. Measure first. Run the budget report before any write (.agents/skills/stow/SKILL.md:80).
  2. Read every file completely, treating an absent file as absent "not as an invitation to manufacture content" (.agents/skills/stow/SKILL.md:86-87).
  3. Plan the whole file before editing, ordered by how likely each entry is to inform a future session (.agents/skills/stow/SKILL.md:92-95).
  4. Reinforce only on evidence. An entry's date is refreshed only when this session exercised or confirmed it; "plausibility, importance, prior knowledge, and the entry's own text are not evidence" (.agents/skills/stow/SKILL.md:96-99).
  5. Consolidate every editable file, preferring "one concise current rule or authoritative pointer over duplicate prose" (.agents/skills/stow/SKILL.md:108-109).
  6. Measure again and finish at or below budget, or open a concrete captain decision (.agents/skills/stow/SKILL.md:118-119).

The same rule reaches beyond memory files. A task-scoped note is updated by showing the item in full, classifying the change as "new, duplicate, superseding, or obsolete", and replacing the body; "Never append" (.agents/skills/stow/SKILL.md:226-228).

What inspect-then-update protects against

An always-loaded file that only grows fills the startup budget with stale and contradictory lines, and a new line that silently contradicts an old one leaves the next session two rules to choose from. Reading first turns every write into a supersession decision. The allowed exits are fixed: promotion to shared tracked material by PR, folding a learning into captain preferences, archiving, offload to an existing owner, or deleting a true duplicate. "A stale unique fact is never deleted, only archived" (.agents/skills/stow/SKILL.md:232-233).

Tiers, markers and decay

Entries carry compact trailing HTML comments whose bytes count against the budget (.agents/skills/stow/SKILL.md:17-47):

MarkerTierRule
none in a pinned-default file, or <!--P-->pinnedNo clock; changed only through inspect-then-update "when the captain or reality changes it"
<!--a:YYYY-MM-DD-->agingStale at 30 days since last reinforced; re-validated or archived
<!--p:YYYY-MM-DD-->perishableStale at 7 days; must name a checkable expiry condition in its prose
<!--g-->legacy graceAn unmarked learning that has used its one grace cycle

Captain files default to pinned "because preferences and authority boundaries do not age", learnings to aging "because operational facts must re-prove themselves" (.agents/skills/stow/SKILL.md:45). Decay only advances when a pass runs (.agents/skills/stow/SKILL.md:55). Pruned entries move to data/memory-archive.md, "this home's append-only, never-injected cold tier", with their provenance under a dated heading (.agents/skills/stow/SKILL.md:132-135). The skill text is "the single owner of tier semantics, marker spellings, and clocks", and a memory file header may carry at most a one-line pointer to it (.agents/skills/stow/SKILL.md:48-49). The memory mechanics as a persistent store are covered under Persistence, and the skill as a prompt artefact under Prompts and skills.

Failure behaviour

  • If the budget helper rejects the setting or a file, the pass must "not infer a default or silently continue" and must not declare the session reset-safe (.agents/skills/stow/SKILL.md:84-85).
  • A pass may not end over budget "as an accepted exception"; it must open a captain decision naming the shortfall (.agents/skills/stow/SKILL.md:126).
  • A secondmate whose inherited shared file alone exceeds its allowance reports primary-owned-shared-file-alone-exceeds-budget and routes it to the primary (.agents/skills/stow/SKILL.md:120).
