Dispatch audit

What Firstmate keeps so that someone can later check which agent, model and effort a task was dispatched with, and why; there is no dedicated audit log, so the trail is assembled from the task record, the spawn output and the optional resolver's evidence block.

No single "dispatch audit" artefact

A search of bin/, docs/, .agents/ and AGENTS.md at the pinned commit finds no file, log or command named as a dispatch audit. The source uses the word once in this sense: unsupported effort values are recorded in task meta "while preserving the requested profile for later audit" (docs/architecture.md:302). This page therefore documents the pieces that together make a dispatch auditable, and says where each one stops.

The pieces

1. The task record

Every fresh spawn or relaunch writes state/<id>.meta with window, endpoint_task_id, worktree, project, harness, kind, mode and yolo for ship tasks, tasktmp, model (or default), effort (or default), spawn_gen, and backend for a non-tmux backend (bin/fm-spawn.sh:4461-4479). spawn_gen is "a new spawn_gen= incarnation token so durable consumers can distinguish a replacement worker that reuses the same task id" (bin/fm-spawn.sh:385-386), and when trace context is on, traceparent= ties the task to one trace (Trace context).

The record keeps what was asked for, not only what the harness accepted: "an effort value the chosen harness does not accept is recorded as effort= in task meta for traceability but omitted from the launch flags" (docs/configuration.md:504). Publishing the record and moving the backlog item to In flight "are one step, not two", and a dispatch refuses up front unless the backlog holds an eligible item for that id (bin/fm-spawn.sh:366-379), so every record corresponds to a tracked work item.

2. The spawn line

On success fm-spawn.sh prints spawned <id> harness=<name> kind=<ship|scout|secondmate> [mode=<mode> yolo=<on|off>] window=<backend-target> worktree=<path> (bin/fm-spawn.sh:381-384). It goes to the calling session's output.

3. The brief

data/<id>/brief.md is the per-task brief (AGENTS.md:99). It is the input both firstmate's own rule matching and the resolver read. No teardown code path found removes data/<id>/, so the brief survives the task; it does not itself record the chosen profile.

4. The resolver's evidence block

When a home opts in with TYPESAFE_API_KEY, bin/fm-dispatch-resolve.sh <brief> --project <name> asks a model one Choice question over the rules' when texts, then does every eligibility and ranking step in jq (bin/fm-dispatch-resolve.sh:16-31). Its output is built to be inspected: status, model, latency and tokens, the matched rule and confidence, every option's probability, the reason when the status is not clear, and one candidate: line per profile with provider, scope, remaining percentage, spendPriority, runway and an eligibility verdict (bin/fm-dispatch-resolve.sh:34-44). Its authority line: "this tool never replaces firstmate's judgment ... it publishes one inspectable answer plus every candidate's evidence, in code" (bin/fm-dispatch-resolve.sh:53-55). The model "never sees quota, catalogs, approvals, why, or use" (bin/fm-dispatch-resolve.sh:28-29).

Every outcome exits 0 so an intake is never blocked, and only a usage or configuration error exits 2 (bin/fm-dispatch-resolve.sh:45-48). The key is never written or logged; it reaches curl through a file descriptor, never on argv (bin/fm-dispatch-resolve.sh:12-14).

The agent contract: run it on the written brief "and on clear pass its profile: line to fm-spawn unless you state a reason to override" (AGENTS.md:235). The rule matching and profile-array selection it can replace are owned by config/crew-dispatch.json and the quota-array-dispatch skill, documented under Crew.

Where the trail stops

Question an auditor might askWhere the answer livesHow long
Which harness, model and effort was this task launched with?state/<id>.metaUntil teardown removes it (bin/fm-teardown.sh:986)
Was this the same worker or a replacement?spawn_gen= in the metaUntil teardown
What was the worker told?data/<id>/brief.mdSurvives teardown
Which rule matched, and why was a candidate ineligible?The resolver's stdout blockOnly the session transcript; the tool writes nothing
Why did firstmate override a clear answer?The stated reason, in conversationOnly the session transcript
Open question

Nothing read for this page persists the resolver's evidence or an override reason beyond the session, and the task record is deleted at teardown. Whether a finished task's dispatch profile is recoverable later, for example from the backlog's Done row, is not settled by the source examined here.

Configuration

config/crew-dispatch.json
Natural-language rules and profiles; when present, fm-spawn.sh refuses a crewmate or scout without an explicit harness (docs/configuration.md:453-456).
TYPESAFE_API_KEY
Environment or .env; absent means one dispatch-resolve: off line and no network call (bin/fm-dispatch-resolve.sh:8-13).
