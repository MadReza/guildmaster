Trace context propagation

When enabled, every spawned agent receives one W3C traceparent value in its environment and the same value is recorded in its task metadata, so an outside observer can treat each task as exactly one trace.

Why it exists, and why so little

Firstmate's durable records already let an observer work out task identity and lifecycle after the fact. The one thing an observer cannot reconstruct is "a task-scoped trace id delivered in the agent's environment before launch and recorded under the same identity in task metadata. This feature adds only that carrier seam" (docs/trace-context.md:8-12). It is "default-off, source-owned, vendor-neutral, and deliberately narrow" (docs/trace-context.md:5). Lifecycle-event emission, extra ids and any embedded OTLP export are "deliberately deferred until a running observer demonstrates a concrete fidelity gap" (docs/trace-context.md:113-114).

Ownership of the contract is split three ways: docs/configuration.md owns the configuration schema, the header of bin/fm-trace-context-lib.sh owns the mechanics, and docs/trace-context.md is the rationale (docs/trace-context.md:6).

What a spawn does when enabled

  1. Read the frozen decision. fm_trace_context_session_effective returns on only when the effective-state record's session binding matches the current lock; absent, stale or invalid state reads as off (bin/fm-trace-context-lib.sh:35-37, bin/fm-spawn.sh:4428).
  2. Resolve the carrier. fm_trace_context_resolve reuses a valid traceparent= already in the task's meta, otherwise mints 00-<32 hex>-<16 hex>-01 from /dev/urandom. It always returns 0 and prints nothing on failure: "telemetry is omitted safely and never aborts the spawn" (bin/fm-trace-context-lib.sh:38-43).
  3. Export, then record. The value is sent into the pane as export TRACEPARENT=... through the same channel that ships GOTMPDIR, then written to the meta. If the record fails, the launch command is prefixed with unset TRACEPARENT "so the child never receives an identity absent from its metadata". If the export fails in a way the backend cannot clear, the launch is refused rather than risk a partial carrier (bin/fm-spawn.sh:4739-4755, docs/trace-context.md:98-105).

Because the export sits at the unconditional pre-launch site, coverage is every ship and scout spawn on every harness and backend, and every secondmate spawn on the backends that accept one (docs/trace-context.md:26-28). On a relaunch, traceparent= is one of the keys the new meta regenerates rather than copies (preserve_relaunch_meta excludes it, bin/fm-spawn.sh:4452-4459); the identity survives because resolution reads the carrier from the existing meta before that rewrite (bin/fm-spawn.sh:4430), and a disabled relaunch therefore drops it.

One trace per task

"The point of these rules is one trace per task: never merge unrelated tasks, and never mint a second identity for the same task" (docs/trace-context.md:42).

Root
A task with no valid recorded carrier gets a fresh trace id, span id and sampled flag. The spawner's ambient TRACEPARENT is never adopted: a persistent secondmate keeps its own launch carrier for life, and adopting it "would chain every routed task into one ever-growing trace per Secondmate" (docs/trace-context.md:44-47).
Recovery
A valid recorded carrier is reused verbatim, flags included, so a relaunched task keeps its identity. A corrupt one is re-minted as a fresh root, not propagated (docs/trace-context.md:48-49).
Boundary
Disabling is an intentional trace boundary: a disabled home injects nothing even when the meta already holds a carrier, and a disabled relaunch regenerates the meta without traceparent=, so a later enabled relaunch starts a new trace (docs/trace-context.md:52-53).

Enablement is frozen per home session

Inputs: the presence flag config/trace-context, and FM_TRACE_CONTEXT, where 1, on, true or yes enables, any other non-empty value disables, and unset or empty defers to the file (bin/fm-trace-context-lib.sh:46-49). Each locked bin/fm-session-start.sh run resolves them once into state/.trace-context-effective, published atomically and bound to state/.lock (bin/fm-session-start.sh:658, bin/fm-trace-context-lib.sh:50-55). Later edits take effect only at the next session start (docs/trace-context.md:55-62).

A secondmate inherits the decision, not the identity. The primary copies config/trace-context into the secondmate home and passes its frozen decision as a non-empty FM_TRACE_CONTEXT=on|off at launch; the secondmate agent gets its own task carrier, and each worker it spawns roots its own trace (docs/trace-context.md:63-70). For a remote secondmate the parent, which holds the task's metadata, resolves the carrier and passes it with --traceparent; the remote host validates it, exports it, and reports back what the endpoint actually holds, which the parent records (docs/trace-context.md:30-38, bin/fm-spawn.sh:973-978, bin/fm-spawn.sh:1029-1030). --traceparent is refused for any other kind of spawn (bin/fm-spawn.sh:711-720).

"Changing the setting across the whole fleet requires a manual full fleet restart"; Firstmate does not detect drift, refuse launches, or restart homes itself (docs/trace-context.md:71-72).

Sampling and exposure

A new root sets flags 01 (sampled), because the feature is opt-in and an unsampled root "would produce a trace id that most downstream parent-based samplers drop". Firstmate emits no spans of its own; it only sets the flag (docs/trace-context.md:74-86). A minted root reads no prompt, path, prose, credential or environment key, and the carrier is fixed-width, so it cannot carry a tracestate or an OTEL_* variable (docs/trace-context.md:88-97).

A convention, not a standard

"W3C Trace Context standardizes the traceparent HTTP header, not an env var, and OpenTelemetry SDKs do not read it from the environment automatically". An observer must read the environment variable or the meta field explicitly (docs/trace-context.md:22-24, bin/fm-trace-context-lib.sh:13-18).

Relationship to the rest of this area

The carrier lives only in the ephemeral pane shell and in state/<id>.meta; teardown removes it with the rest of the task's state, so "there is no new durable surface" (docs/trace-context.md:106-107). Unlike contribution records or scout reports, it does not outlive the task. It is the one observability feature aimed at an outside observer rather than at firstmate or the captain.
