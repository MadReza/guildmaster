Observability

How Firstmate knows what happened and reports it: an append-only event log per task, a classifier that folds it into what is still owed, surfaces that make sure nothing owed is lost between wakes, a bounded fleet snapshot for the captain, and a few durable records that outlive the tasks that made them.

Read against Firstmate commit ada21f5b. Terms are Firstmate's own (captain, crewmate, scout, secondmate, status log), because this site documents Firstmate as it is.

The principle running through all of it

Every part of this area repeats one rule: a status line records that something happened; it does not say what is true now. The home layout states it for the log itself, "append-only wake events, not current-state truth" (AGENTS.md:103), and the operating contract repeats it where it matters most, before re-escalating: "use bin/fm-crew-state.sh when current state matters, especially before re-escalating an old decision, blocker, or pause" (AGENTS.md:434). The fold, the drain sections, the snapshot's history fields, the away-mode checks and the contribution classifier each exist partly to stop an event being mistaken for a state. Event is not state collects every instance with the concrete wrong action each one prevents.

End to end: one decision, from question to landed work

A realistic path through the area. A crewmate on a ship task needs the captain to choose an API shape, gets an answer, and finishes.

  1. The worker asks. Following its brief, it appends needs-decision [key=api-shape] [at=1788576000]: REST or gRPC? and stops (bin/fm-brief.sh:534-536). The fold now holds api-shape open (bin/fm-classify-lib.sh:678-723).
  2. The watcher classifies the append. A span containing a captain-relevant event is surfaced as a signal: wake; a no-verb append would need positive evidence before being absorbed (bin/fm-watch.sh:21-23, bin/fm-classify-lib.sh:1919-1942). The watcher itself is Supervision.
  3. The wake is queued durably and firstmate is woken.
  4. The drain presents it twice over: the queued row with its unread status annotation, and the fleet-wide OPEN DECISIONS section listing <task> [key=api-shape] needs-decision: REST or gRPC? with the closing command hint (bin/fm-wake-drain.sh:444-489). Even if a later working line followed, the section would keep listing it.
  5. Firstmate asks the captain, who answers (6).
  6. Firstmate answers and closes in one act: bin/fm-send.sh <task> --resolve-key api-shape 'use REST'.
  7. fm-send.sh appends resolved [key=api-shape]: answered: use REST to the task's status log, then re-folds and fails loudly if the key is still open (bin/fm-send.sh:154-176).
  8. The answer reaches the worker. On the inbox plane the close happens at enqueue time, because the durable enqueue is delivery (bin/fm-send.sh:170-172).
  9. The worker finishes and appends done: PR https://.... On a ship task this terminal line would also have cleared any key still open (bin/fm-classify-lib.sh:700-702), which is where the brief's wording and the fold disagree (see the finding on Status events).
  10. The next drain presents the done event; OPEN DECISIONS prints nothing. Before re-escalating anything, firstmate reads bin/fm-crew-state.sh <task> rather than trusting the last line (AGENTS.md:434).
  11. Afterwards, the landed PR appears under Recently Landed in Bearings; if the PR is upstream work the home owns, contribution tracking keeps watching it after teardown.
