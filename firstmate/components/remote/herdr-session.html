fm-remote session and guard

Every remote secondmate agent runs in one dedicated Herdr session, fm-remote, whose server must be born in the account's GUI login session; fm-remote-herdr-guard.sh is the launchd program that makes that true and keeps it true.

Read against Firstmate commit ada21f5b.

The dedicated session

"The remote second-mate agent itself always runs on the Herdr backend in the shared fm-remote session, and every path that provisions or launches one refuses a host that is not ready for it. fm-remote is reserved for remote fleet work and must not be used for personal work. The user's interactive Herdr session remains default and is not a remote-secondmate prerequisite" docs/remote-secondmates.md:7-9. All remote secondmates on one host share fm-remote and keep separate 2ndmate-<id> workspaces inside it docs/remote-secondmates.md:163. The dedicated launch agent "owns only the remote-secondmate fm-remote server and does not inspect, rewrite, start, stop, or require the user's interactive default session or its dev.firstmate.herdr launch agent" docs/remote-secondmates.md:107.

Only the remote secondmate agent itself is pinned to Herdr. The workers that the remote secondmate supervises inside its own home keep their ordinary backend and session selection docs/remote-secondmates.md:11 bin/fm-remote-secondmate-control.sh:17-22.

How the control plane enforces the session

  • Launch. launch refuses any backend but herdr, runs the host-local fm-spawn.sh with HERDR_SESSION=fm-remote, and verifies the endpoint it recorded is in fm-remote bin/fm-remote-secondmate-control.sh:168-211. The primary checks the returned session and target prefix again before recording anything bin/fm-spawn.sh:1016-1022.
  • Every later access. An endpoint record whose backend is not herdr, whose herdr_session is not fm-remote, or whose target is outside fm-remote: is refused "until it is explicitly migrated" bin/fm-remote-secondmate-control.sh:86-112. state reports such an endpoint as unverified rather than alive or dead bin/fm-remote-secondmate-control.sh:118-128.
  • No live cutover. An existing remote endpoint recorded in another Herdr session, including default, "is classified as unverified and left untouched; launch, liveness recovery, control, and retirement refuse it until an operator explicitly migrates it instead of attempting a live cutover" docs/remote-secondmates.md:165.
  • Retirement scope. Retirement "closes only the retiring secondmate's panes or 2ndmate-<id> workspace in fm-remote; it never stops the shared session or removes a sibling secondmate's workspace or panes" docs/remote-secondmates.md:258.

Why the server's birth matters

This is a macOS-specific constraint that the source records with dated evidence. "A herdr server, and every pane and agent it later spawns, keeps the macOS audit session of whatever started it. Only the Aqua login session (the gui/<uid> launchd domain) can read the login keychain without a UI prompt." A server started over SSH runs in sshd's audit session, where security find-generic-password -w exits 36, "and every claude pane silently falls back to a stale plaintext credentials file and reports 'Login expired'" bin/fm-remote-herdr-owner-lib.sh:10-20 docs/remote-secondmates.md:102. The evidence is in docs/verification/runtime-backends.md:1049.

The race that makes a guard necessary: "Herdr's own SSH remote attach starts such a server when it finds none, and at boot it wins the fm-remote socket because sshd accepts connections before the login session exists" docs/remote-secondmates.md:103.

The guard's decision

Details the diagram compresses:

  • After stopping a foreign server, the guard execs the new server "at once so the socket is rebound before a reconnecting SSH attach can start another foreign server" bin/fm-remote-herdr-guard.sh:25-31.
  • The release wait is FM_REMOTE_HERDR_GUARD_STOP_WAIT_TENTHS tenths of a second, default 50 bin/fm-remote-herdr-guard.sh:36-37 bin/fm-remote-herdr-guard.sh:55.
  • The guard itself needs an executable herdr path and jq; otherwise it exits 1 bin/fm-remote-herdr-guard.sh:52-54.
  • A takeover "closes every pane in that session; the parent firstmate's secondmate liveness sweep relaunches its mates into the Aqua-born server" bin/fm-remote-herdr-guard.sh:33-34. The doctor's action text warns the operator of this before a --fix that would trigger one bin/fm-remote-doctor.sh:682-687.

Owner discovery and birth classification

bin/fm-remote-herdr-owner-lib.sh is "the single owner of the socket-owner discovery and birth classification shared by" the guard and the doctor bin/fm-remote-herdr-owner-lib.sh:5-8.

  • Owner. Read lsof -U -a -c herdr -F pn and match the socket path, literal or physical. When several herdr processes list it, the one whose argv contains server wins. On macOS pgrep -f cannot see the server's argv, which is why lsof is the source; without lsof the function returns 2 and the caller decides bin/fm-remote-herdr-owner-lib.sh:23-29 bin/fm-remote-herdr-owner-lib.sh:53-78.
  • Environment. ps -Eww on macOS (own-uid processes only), /proc/<pid>/environ elsewhere bin/fm-remote-herdr-owner-lib.sh:30-34.
  • Birth, strongest marker first bin/fm-remote-herdr-owner-lib.sh:37-51 bin/fm-remote-herdr-owner-lib.sh:124-150:
    1. ssh if SSH_CONNECTION, SSH_CLIENT, or SSH_TTY is in the environment;
    2. launchd if XPC_SERVICE_NAME=<label> and launchctl proves that job owns the pid in gui/<uid>, or is loaded only in that domain;
    3. worker if FM_REMOTE_JOB_ACTIVE=1 and dev.firstmate.remote-job is loaded only in gui/<uid>;
    4. ssh if an ancestor's argv[0] is sshd or sshd-session, or is herdr with the whole argument remote-client-bridge. Only argv[0] and whole arguments count, so an agent whose brief merely mentions those words does not match bin/fm-remote-herdr-owner-lib.sh:152-171;
    5. otherwise unknown. XPC_SERVICE_NAME alone, including value 0, proves nothing.
  • Aqua test. Only launchd and worker are Aqua. "unknown is deliberately not Aqua: a server that cannot prove its birth is treated like a foreign one, because leaving it in place silently reproduces the keychain failure" bin/fm-remote-herdr-owner-lib.sh:48-51 bin/fm-remote-herdr-owner-lib.sh:173-176.

On Linux the doctor treats any running server as ready, since there is no Aqua session to be born in bin/fm-remote-doctor.sh:194-202. The guard itself is only installed as a macOS launch agent; on Linux the doctor starts the server through the Herdr adapter bin/fm-remote-doctor.sh:863-874.

Open on Linux

The document says --fix "starts the same workers directly on Linux" docs/remote-secondmates.md:105. For the Herdr server that means the adapter's fm_backend_herdr_server_ensure, which starts herdr server as a plain background job of whoever called it, with no nohup or session detach bin/backends/herdr.sh:1656-1672. Called from the doctor's --fix, that caller is the SSH bootstrap; called during a launch, it is a worker job. The source does not say how such a server is meant to outlive the SSH session on Linux, or whether a job-worker process-group stop on timeout could reach it. The survival argument in the document is stated only in terms of the macOS GUI login session.
