Readiness doctor

fm-remote-doctor.sh is the single owner of what "ready for a remote second mate" means: it checks one remote account, repairs only what can be repaired safely, and names every remaining gap as either fixable or human-only, with the exact step to take.

Read against Firstmate commit ada21f5b.

One owner, many gates

"bin/fm-remote-doctor.sh is the single owner of what 'ready for a remote second mate' means" docs/remote-secondmates.md:81. Nothing else restates its checks. The gate library that callers use says so directly: the doctor "remains the single owner of every check, every repair, and every message; nothing here restates them" bin/fm-remote-readiness-lib.sh:10-12. An operator runs it through the ordinary transport, where the entrypoint execs it in the plain SSH bootstrap rather than through the worker it inspects bin/fm-remote-doctor.sh:4-10 bin/fm-remote-entrypoint.sh:154-173:

bin/fm-on.sh <secondmate-id|ssh-alias> fm-remote-doctor.sh         # read-only
bin/fm-on.sh <secondmate-id|ssh-alias> fm-remote-doctor.sh --fix   # repair automatable gaps

A third, internal mode --worker-tool-probe exists only for the doctor to ask the worker which tools it resolves, and refuses to run unless FM_REMOTE_JOB_ACTIVE=1 bin/fm-remote-doctor.sh:90-94.

Where the document and the code differ

The document lists lsof as part of "the required remote tool set" on macOS docs/remote-secondmates.md:115. In the code lsof is not in REQUIRED_TOOLS and never gets a required line; its absence surfaces only as a herdr-server=human: gap, and only while a server is running bin/fm-remote-doctor.sh:70 bin/fm-remote-doctor.sh:676-679. A host without lsof and without a running server is reported as fixable, not as missing a tool.

The host-local control plane accepts cursor as a remote secondmate harness bin/fm-remote-secondmate-control.sh:160-163, but the doctor's harness list does not include it bin/fm-remote-doctor.sh:71. A host whose only harness is cursor would fail readiness even though launch would accept it. The source does not say which list is intended.

What --fix does

--fix first tries owned tool wrappers (see wrappers), then walks the recorded checks and repairs each fixable one at most once bin/fm-remote-doctor.sh:833-878:

Any remote-job checkfm_remote_job_ensure_worker: write and reload the job LaunchAgent, or start the Linux worker bin/fm-remote-doctor.sh:554-561
launchagent, launchagent-scopeRender and atomically publish the Herdr plist; if a GUI session exists, reload it at once bin/fm-remote-doctor.sh:740-766
launchagent-loadedlaunchctl bootout, bootstrap gui/<uid>, kickstart -k, then wait up to 10 s for an Aqua-owned server bin/fm-remote-doctor.sh:768-805

It then "re-derive[s] every check from the host itself, so what prints below is the state after repair rather than the intent of a repair" bin/fm-remote-doctor.sh:903-908. The header's never-list: it "never installs packages, creates a login session, writes an auto-login password, changes FileVault, stores an account password, or replaces a non-Firstmate wrapper; those remain reported gaps" bin/fm-remote-doctor.sh:48-54.

The gaps only a person at that machine can close

These are "never automated and are always reported rather than silently attempted, because SSH cannot create a GUI session from nothing" docs/remote-secondmates.md:110-118:

  • The first console login on that Mac, and automatic login in System Settings › Users & Groups when the machine runs headless and must come back on its own after a reboot. The doctor's action text for a missing session says the same and adds that Firstmate "never writes an auto-login password or changes FileVault" bin/fm-remote-doctor.sh:602-603.
  • FileVault, which holds a reboot at pre-boot authentication before any login session exists.
  • Installing any missing required tool that no safe wrapper can resolve.
  • Each worker runtime's own /login, and any keychain password prompt that login needs.
  • A file at ~/.local/bin/fm-remote-entrypoint.sh that is not Firstmate's symlink, which is reported for inspection and never overwritten docs/remote-secondmates.md:119.

How far the tests reach

The doctor tests use a controlled account fixture. "The account-level checks the doctor performs - a real Aqua login session, a real launchctl domain, and a real herdr server - are only ever exercised against fixtures here, so the readiness gate's behavior on a genuine Mac remains an operator-run smoke test" docs/remote-secondmates.md:286. The audit-session facts the guard and doctor rely on are recorded with their commands in docs/verification/runtime-backends.md under "fm-remote server birth and login-keychain access" docs/verification/runtime-backends.md:1049.
