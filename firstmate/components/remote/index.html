Remote

How Firstmate places a whole persistent secondmate home on another SSH-reachable machine, and the narrow, argv-only transport that is the only way the primary ever reaches it.

Read against Firstmate commit ada21f5b. Every citation links to that commit.

The placement decision: whole homes, never single workers

Firstmate's remote unit is a complete operational home, not an individual worker. "Remote second mates place a whole persistent Firstmate home on another SSH-reachable host. The primary still owns routing and supervision, while the remote home owns its own projects, backlog, and workers." The same document rules out the two alternatives explicitly: Firstmate "does not support placing an individual worker remotely or failing a remote route over to a local replacement" docs/remote-secondmates.md:3-5.

What the source gives as the reasons, and what follows from them in the code:

  • The far side must be self-sufficient between contacts. The remote home clones its own projects from their origins on that host (docs/remote-secondmates.md:42, bin/fm-remote-home-provision.sh:224-238), keeps its own backlog (bin/fm-remote-home-provision.sh:188-194), and supervises its own workers with their ordinary backend selection (docs/remote-secondmates.md:11). The primary crosses the link only for routing, steering, reply mirroring, and lifecycle.
  • The remote agent must outlive every SSH disconnection. The remote secondmate agent always runs on Herdr in the dedicated fm-remote session, because "Herdr's remote-session server belongs to the host's own GUI login session rather than to the SSH connection, so the agent's endpoint survives every disconnection the primary's supervision depends on" docs/remote-secondmates.md:7-10. The control plane restates this as a hard requirement, not a preference bin/fm-remote-secondmate-control.sh:168-171.
  • Unreachable is never the same as dead. Because a whole home carries durable state on its own disk, an unavailable remote home "is projected as unknown and is never replaced by a local second mate" docs/remote-secondmates.md:219. Failing over would fork that state; see Recovery.
Open question

The source states the decision and its mechanical consequences but does not record a comparative argument against remote workers (for example, cost or latency figures). The reasons above are the ones the documents and headers actually give; anything beyond them is not in the source.

Component view (C4 Level 3)

The remote area spans two machines. On the primary, every semantic caller reaches the far side only through fm-on.sh. On the remote account, one fixed entrypoint accepts that call and hands it either to the readiness doctor (a plain SSH bootstrap) or to the account-owned job worker, which runs the tracked target script in the account's GUI session.

Where Remote meets other areas

  • Communication owns the steering inbox, doorbell, marked requests, and pending-reply model; Remote only carries them across the link.
  • Supervision owns the startup liveness sweep and process-event sources that call into the remote readiness gate and the reply adapter.
  • Crew owns what a secondmate is, the Herdr backend adapter, and the local control plane that a remote relaunch reuses on the far host.
  • Persistence owns the secondmate registry, task metadata, and home layout that remote routes extend with host:, root:, and home:.
  • Backlog and decisions owns backlog handoff and the open-decision fold; Remote adds the outbox transfer.
  • Observability owns fleet snapshots and home summaries, which read a remote home's summary over the confined file reader.
