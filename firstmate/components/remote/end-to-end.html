End-to-end trace

One remote secondmate, followed from the seed command to retirement, with a steer out and a correlated reply back in between. Every step names the script and line that performs it.

Read against Firstmate commit ada21f5b. The scenario matches the real-host smoke test the document describes docs/remote-secondmates.md:289.

Scenario

The primary home on a laptop routes iOS work to a secondmate ios on a Mac reachable as the SSH alias build-mac. The Mac's account has a Firstmate clone at /Users/ops/firstmate with the entrypoint on its non-interactive PATH, and the home will live at /Users/ops/fm-homes/ios. (The names are illustrative; the shapes come from the usage lines cited below.)

The same trace with the link failing

If build-mac reboots during step 8, the ssh keepalives turn the half-open connection into exit 255 within about 45 s at the defaults bin/fm-on.sh:28-34 bin/fm-on.sh:107-108. fm-send retries the leg once; if that also fails it exits non-zero, keeps the pending-reply expectation, and prints the FM_PENDING_REPLY_EXISTING_CORR=<id> resend bin/fm-send.sh:133-141. fm-crew-state.sh reports unknown-remote, not dead bin/fm-crew-state.sh:273-275. At the Mac's next GUI login the two LaunchAgents start; if an SSH attach won the fm-remote socket first, the guard takes the session over and the panes close bin/fm-remote-herdr-guard.sh:18-34. The primary's next startup liveness sweep sees missing or dead and relaunches through fm-spawn, passing the same readiness gate bin/fm-bootstrap.sh:790-800.
