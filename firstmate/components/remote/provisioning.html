Provisioning and launch

How a remote route is registered, how the remote host builds the secondmate home itself from a bounded manifest, and how every launch converges that home on the primary's code and inherited settings before the agent starts.

Read against Firstmate commit ada21f5b.

Operator prerequisites

  1. An SSH alias in the primary account's normal OpenSSH configuration, with public-key authentication, strict host-key verification, a dedicated remote account where practical, and no agent forwarding docs/remote-secondmates.md:15-17.
  2. A Firstmate clone on the remote host at an absolute code-root path, with its entrypoint symlinked onto the non-interactive SSH PATH docs/remote-secondmates.md:20-26.
  3. The toolchain, runtime, backend, and credentials that work on that host, and project origins the remote account can reach, "because projects are cloned on that host rather than copied from the primary" docs/remote-secondmates.md:41-42.
  4. A filled secondmate charter in the primary home docs/remote-secondmates.md:123. Charter authoring belongs to the secondmate-provisioning skill.

Seeding a route

bin/fm-remote-home-seed.sh <id> <ssh-alias> <remote-root> <remote-home> {<project>[=<origin-url>]...|--no-projects}

<remote-root> is the remote Firstmate code clone that supplies tracked scripts; <remote-home> is a separate absolute path for the persistent home and "must not overlap the code root" docs/remote-secondmates.md:126-130. The seed enforces: a safe id, a safe alias, absolute paths without the registry delimiters ; or ), no control characters, no traversal, no empty components, and neither path inside the other bin/fm-remote-home-seed.sh:70-80.

Project origins

Each project is named as <project>=<origin-url>. "Resolve the concrete origin from the captain, the project registry, an existing clone anywhere, the forge, or an explicit paste rather than imposing one URL template." A bare <project> is accepted only when this machine already has projects/<project>, whose origin is then read docs/remote-secondmates.md:132-135 bin/fm-remote-home-seed.sh:183-190. bin/fm-project-origin-lib.sh owns which URLs are accepted, "on structure and safety alone, so no forge, domain, or host is privileged"; the primary validates every origin before transport and the remote host validates it again before cloning docs/remote-secondmates.md:136-137 bin/fm-remote-home-provision.sh:221. The project's delivery mode still comes from this machine's data/projects.md: no-mistakes and direct-PR are provisioned, local-only and any unregistered project are refused bin/fm-remote-home-seed.sh:174-194. Seeding "writes nothing under projects/ and needs no fleet sync first" bin/fm-remote-home-seed.sh:21.

What the seed does, in order

  1. Acquire the secondmate registry lock; refuse if the id is already registered to a different local or remote home bin/fm-remote-home-seed.sh:107-123.
  2. Use data/<id>/brief.md, or scaffold one with fm-brief.sh --secondmate when FM_SECONDMATE_CHARTER is set; refuse a charter still containing {TASK}, or with an empty summary or scope bin/fm-remote-home-seed.sh:125-143.
  3. Rewrite the charter for the far side. The parent's state/<id>.status becomes <remote-home>/state/parent-replies.status, and the parent's state/<id>.inbox becomes <remote-home>/state/parent-route/<id>.inbox, as two whole-string substitutions so every mention lands host-local bin/fm-remote-home-seed.sh:149-166. This is how the remote agent learns where to write replies and where steers arrive.
  4. Build one base64 record per project (name, origin, registry line, mode) and the manifest; refuse a manifest over 1 MiB bin/fm-remote-home-seed.sh:168-219.
  5. Write the route line - <id> - <summary> (host: …; root: …; home: …; scope: …; projects: …; added YYYY-MM-DD) and validate the registry's home bindings, keyed as ssh:<host>:<home> for remote routes bin/fm-remote-home-seed.sh:221-230 bin/fm-secondmate-registry-lib.sh:219.
  6. Run the readiness gate. On a known failure restore the registry and remove a newly scaffolded brief; on 255 keep both bin/fm-remote-home-seed.sh:237-253.
  7. Send the manifest: fm-on.sh --stdin <id> fm-remote-home-provision.sh < manifest. Same failure split: a known failure rolls back, 255 preserves the route "because remote completion is unknown and must be reconciled on the same host" bin/fm-remote-home-seed.sh:255-270 docs/remote-secondmates.md:145.

In the primary home the durable effects are limited to the route line and the charter brief under data/<id>; launch records appear only at launch. The seed "does not copy project trees or the primary process environment" docs/remote-secondmates.md:141-144.

What the remote host does

fm-remote-home-provision.sh runs as a worker job with FM_HOME set to the configured remote home bin/fm-remote-home-provision.sh:2-19:

  1. Serialize. A lock keyed by the SHA-256 of the home path, under a .firstmate-provision-locks directory next to the home; the home's parent must already exist and be canonical bin/fm-remote-home-provision.sh:121-146.
  2. Existing or new. An existing home must be a real Firstmate checkout with real operational directories; its owned files are snapshotted; its .fm-secondmate-home marker must name this id, and an unmarked home that already holds operational data is refused. An absent home is created by git clone of the remote code root, not of any forge origin bin/fm-remote-home-provision.sh:148-178.
  3. Layout. Create data, state, config, projects, and an empty backlog skeleton with ## In flight, ## Queued, ## Done bin/fm-remote-home-provision.sh:179-194.
  4. Projects. Re-validate each origin and mode; an existing clone must have the same origin; a new one is cloned, and a no-mistakes project gets no-mistakes init and no-mistakes doctor on that host bin/fm-remote-home-provision.sh:196-240.
  5. Publish. Atomically write data/charter.md (mode 600), data/projects.md, .fm-secondmate-parent, and finally .fm-secondmate-home, which "commits the complete seed last" bin/fm-remote-home-provision.sh:242-255.

On any failure before that last write, a newly created home is removed entirely; an existing home has newly cloned projects removed and its owned files restored from the snapshot bin/fm-remote-home-provision.sh:72-93. Rerunning the seed for the same route converges, which is what makes preserving the route on 255 safe bin/fm-remote-home-seed.sh:23-24.

The parent record

.fm-secondmate-parent holds schema=fm-secondmate-parent.v1, route=remote, and parent_host=<alias> when known bin/fm-remote-home-provision.sh:247-252. Its purpose: "The promised-public-reply subsystem is same-filesystem by construction, so a remote route can never carry a delegated public-reply promise; bin/fm-teardown.sh's cleanup gate reads this record to treat a remote parent as out of scope rather than an unresolved binding" docs/remote-secondmates.md:147-148.

Launching or recovering the agent

Launch and recovery use the same command as a local route, bin/fm-spawn.sh <id> --secondmate docs/remote-secondmates.md:156-162. For a remote route fm-spawn.sh:

  1. Resolves the verified harness and optional model and effort; refuses an invalid configured effort bin/fm-spawn.sh:880-890.
  2. Refuses when existing task metadata does not identify this exact remote route (kind, host, root, home) bin/fm-spawn.sh:891-903.
  3. Runs the readiness gate "before anything is published or transferred" bin/fm-spawn.sh:904-924.
  4. Syncs the remote home to this primary's default-branch commit; a skipped sync warns and launches the home unchanged bin/fm-spawn.sh:925-939.
  5. Pushes the inherited-material allowlist under a per-route lock with a fresh generation; a failure refuses the launch, and 255 preserves the route bin/fm-spawn.sh:940-968.
  6. Resolves a trace-context carrier against this home's own task metadata when tracing is on bin/fm-spawn.sh:969-979.
  7. Calls fm-on.sh <id> fm-remote-secondmate-control.sh launch <id> <harness> <model> <effort> herdr [traceparent] bin/fm-spawn.sh:980-997.
  8. Rejects a reply whose backend is not herdr, whose harness differs, or whose session is not fm-remote bin/fm-spawn.sh:998-1022.
  9. Writes the parent's task record with window=remote:<id>, kind=secondmate, home, remote_host, remote_root, remote_backend, remote_herdr_session, remote_target, and the carrier the endpoint actually holds bin/fm-spawn.sh:1023-1050.

"Raw launch commands are not accepted for remote secondmates", an explicit request for any other backend is refused on both sides, and backends that already refuse secondmate launch (currently Orca and cmux) stay unsupported docs/remote-secondmates.md:164-168.

The host-local half

fm-remote-secondmate-control.sh launch validates the home marker, the harness (claude codex opencode pi pi-signed grok kimi cursor), the effort, and the backend bin/fm-remote-secondmate-control.sh:154-171. If an endpoint record exists it asks the backend for the agent's state: alive returns the existing route without relaunching, dead removes the agent-less endpoint first, missing proceeds, and anything else refuses a duplicate launch bin/fm-remote-secondmate-control.sh:174-189. It then runs the ordinary fm-spawn.sh … --secondmate --backend herdr on that host with HERDR_SESSION=fm-remote, state and data redirected into the home's private state/parent-route and data/.parent-route, the home's own config, and inheritance and sync skipped, because "the parent owns both convergence legs before it asks for this launch" bin/fm-remote-secondmate-control.sh:190-205. Keeping the agent's own endpoint record under state/parent-route leaves the home's state/*.meta for the workers the secondmate supervises bin/fm-remote-secondmate-control.sh:35-37.

Code convergence

"Session start and every remote launch converge the persistent remote home on the primary's own default-branch commit rather than on the Firstmate copy that host keeps" docs/remote-secondmates.md:246. sync <id> <40-hex commit> first makes the commit readable in the home's own object store, cheapest first: already present, then a read-only fetch of that one commit from the host's code root (which never moves that copy's HEAD), then a fetch from the home's origin bin/fm-remote-secondmate-control.sh:328-345. The fast-forward itself is the shared ff_target, so the clean, ancestry, and branch guards have one owner bin/fm-remote-secondmate-control.sh:26-34. The result line is synced: <commit> instr=<changed watched instruction paths> or current: <commit> bin/fm-remote-secondmate-control.sh:347-375; the instr= suffix exists because "the primary cannot diff a checkout it cannot read" and must decide whether the running agent needs replacing to reload docs/remote-secondmates.md:249. An older host omits it, which a parent must read as unknown rather than "nothing changed" bin/fm-remote-secondmate-control.sh:360-363.

/updatefirstmate is the one path that follows the host's own copy: update runs fm-update.sh on the remote code root, requires a safe origin update, then syncs the home to that refreshed code-root HEAD bin/fm-remote-secondmate-control.sh:377-395. The guarded convergence contract belongs to the secondmate-provisioning skill docs/remote-secondmates.md:247-248.
