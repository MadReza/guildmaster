Remote job worker

A long-lived, account-owned process on the remote host that runs every non-doctor fm-on command from a file-based queue, so remote commands execute in the account's GUI session rather than in the SSH process or a Herdr pane.

Read against Firstmate commit ada21f5b.

Why a worker at all

After the doctor bootstrap, "every non-doctor fm-on.sh target runs through that worker in the remote account's GUI session, never in the SSH process or a Herdr pane" docs/remote-secondmates.md:34. On macOS the reason is the audit session: only a process born in the gui/<uid> launchd domain can read the login keychain without a prompt, which the Herdr session needs for every agent it spawns bin/fm-remote-herdr-owner-lib.sh:10-18. A Herdr server started by the worker counts as Aqua-born (birth marker worker) exactly because the worker itself is an Aqua LaunchAgent bin/fm-remote-herdr-owner-lib.sh:44-45. Linux uses the same queue and worker protocol without the Aqua requirement docs/remote-secondmates.md:39.

Two files own it. bin/fm-remote-job-lib.sh is sourced by the entrypoint, the worker, and the doctor, and owns "the per-account queue at ~/.firstmate/remote-job …, the bounded job record, worker installation, and the remote runtime PATH" bin/fm-remote-job-lib.sh:4-8. bin/fm-remote-job-worker.sh is the serving loop bin/fm-remote-job-worker.sh:2-8.

State on disk

All state lives under ~/.firstmate/remote-job; FM_REMOTE_JOB_STATE_ROOT overrides it only for isolated tests bin/fm-remote-job-lib.sh:5-6. Every directory is created through a safe-child helper that refuses symlinks bin/fm-remote-job-lib.sh:395-444.

jobs/job-XXXXXX/
One published job record, mode 0700. Staging happens in jobs/.stage.XXXXXX and is renamed into place.
.seq-claims/<n>/
One directory per reserved staging sequence number; mkdir is the atomic reservation.
seq
A forward-moving allocation hint only, never the source of truth bin/fm-remote-job-lib.sh:16-21.
worker.lock/
Worker ownership: pid, start, command, and an optional quarantine marker.
worker.pid, worker.ready, worker.identity
Published pid, heartbeat (rewritten every loop), and code identity of the running worker.
logs/
Linux worker log. On macOS the LaunchAgent logs to ~/Library/Logs/dev.firstmate.remote-job.log bin/fm-remote-job-lib.sh:824-830.

Ordering: FIFO within a home, concurrency across homes

seq is reserved by mkdir .seq-claims/<n>, walking up from the hint. If 100 000 attempts in a row find the number taken, allocation rescans the claims for the maximum and continues above it, once bin/fm-remote-job-lib.sh:543-583. The FIFO contract is defined over completed stagings only: "a stage that returns before another begins executes first; concurrently overlapping stagings have no relative ordering contract", with the job id as the deterministic tiebreak bin/fm-remote-job-lib.sh:21-25. The serving loop sorts candidates by seq numerically, then id; a record staged by an older library without seq sorts as 0, ahead of sequenced work bin/fm-remote-job-worker.sh:965-969 bin/fm-remote-job-worker.sh:997.

The worker "serves one lane per staged home: jobs for the same home run strictly FIFO in seq order while lanes for different homes run concurrently, so one home's long job never delays another home's commands" bin/fm-remote-job-lib.sh:32-35. In each pass the loop skips a home that already has a lane, and also skips a home that has a queued job whose claim owner is still alive (a reserved home), then starts at most one lane per remaining home in sorted order bin/fm-remote-job-worker.sh:931-998.

Each lane is a separate top-level fm-remote-job-worker.sh --lane <job-id> process rather than a backgrounded subshell, because "a bash subshell does not reliably reap its dead children, and a zombie group leader keeps its process group signalable", which could make a finished command look alive until its deadline bin/fm-remote-job-worker.sh:904-919.

Preemption of the reply long-poll

The reply mirror keeps a blocking delta read of the remote status log open (default wait window 55 s bin/fm-remote-delta-read.sh:116). Within one home's lane that poll would otherwise serialize every short interactive command behind it bin/fm-remote-job-lib.sh:35-36. The preemptible class is exactly one command, fm-remote-delta-read.sh bin/fm-remote-job-lib.sh:119-121. While a preemptible job runs, the lane checks about once a second whether any non-cancelled queued job for the same home is not itself preemptible; if so it sends TERM, waits up to about one second, sends KILL, and publishes 76 with empty output bin/fm-remote-job-worker.sh:615-625 bin/fm-remote-job-worker.sh:646-661. Only a same-home waiter may preempt, since other homes have their own lanes.

Nothing is lost, because the delta read is non-destructive and cursor-anchored, "so the caller's normal re-arm re-reads the same data and a preempted poll loses nothing" bin/fm-remote-job-lib.sh:41-43. The distinction between 76 and 75 matters to the parent: only a genuinely quiet window (75) proves the mirror is caught up, while either outcome can re-arm docs/remote-secondmates.md:37. See reply mirroring.

Cancellation

"A caller that disconnects before its job completes cancels it instead of abandoning it" bin/fm-remote-job-lib.sh:45-54. fm_remote_job_cancel atomically writes a cancel marker and never rewrites state; if the record is already done it reaps instead, and cancelling a vanished job is a no-op bin/fm-remote-job-lib.sh:585-611. The worker then skips a cancelled queued job (publishing 130 and reaping), or, for a running one, notices within about a second, sends TERM to the group, waits up to about one second, sends KILL, and publishes 130 bin/fm-remote-job-worker.sh:603-614. The document's summary: "cancelled queued work is skipped, cancelled running work is stopped, and the finalized record is cleaned up, so retries never convoy behind abandoned work" docs/remote-secondmates.md:38. The triggers on the entrypoint side are on the transport page.

How one command is executed

  1. Re-validation. The lane re-reads root, home, argv, stdin, and deadline, and refuses with 126 unless the root equals the worker's own FM_ROOT and the command is a genuine executable bin/fm-remote-job-worker.sh:683-709.
  2. Tracking check under the deadline. git -C <root> ls-files --error-unmatch bin/<command> runs through the same timed, group-isolated runner, using the operator git only bin/fm-remote-job-worker.sh:710-725.
  3. Bounded output capture. stdout and stderr go through two private FIFOs; each reader keeps the first 1 MiB and discards the rest, so a noisy child cannot block and cannot exceed the bound bin/fm-remote-job-worker.sh:671-677 bin/fm-remote-job-worker.sh:730-745.
  4. Clean environment. The child runs as /usr/bin/env -i PATH=<child PATH> HOME=<account home> FM_HOME=<home> FM_ROOT_OVERRIDE=<root> FM_REMOTE_JOB_ACTIVE=1, with its captured stdin bin/fm-remote-job-worker.sh:746-766. The PATH is described on the tool contract page.
  5. Process-group isolation. Job control places the child in its own process group. The child waits for an armed marker before it execs, so the group id and start time are durably recorded before any work begins; if recording fails the group is killed and 125 published bin/fm-remote-job-worker.sh:537-593. Timeout, cancel, and preemption all signal the whole group.

Worker ownership, heartbeat, and identity

Exactly one serving worker owns an account's queue. It takes worker.lock by mkdir and records its pid, start time, and command line. A competing start that finds a live owner exits 0; a lock whose owner is dead and whose heartbeat is stale is cleared and retried bin/fm-remote-job-worker.sh:160-184 bin/fm-remote-job-worker.sh:1008-1015. The worker then publishes its code identity and pid and, on every loop, rewrites worker.ready as a heartbeat bin/fm-remote-job-worker.sh:1017-1020.

Readiness is a fresh heartbeat (no older than 10 s) with no quarantine marker bin/fm-remote-job-lib.sh:1087-1099. Staleness of the code is detected separately: the identity is three git hash-object values, of the root path, the library, and the worker script, joined by colons bin/fm-remote-job-lib.sh:1048-1062. When the running worker's published identity differs from what the current checkout computes, fm_remote_job_ensure_worker reloads the LaunchAgent (macOS) or stops and restarts the worker tree (Linux), then waits up to 20 s for a matching probe bin/fm-remote-job-lib.sh:1101-1109 bin/fm-remote-job-lib.sh:1186-1241.

Shutdown and quarantine

On HUP, INT, or TERM the worker ignores further copies of those signals, writes a quarantine marker into the lock, stops every tracked lane and its recorded command group, verifies they are gone, and only then clears the marker and exits bin/fm-remote-job-worker.sh:391-418. The comment explains the ignored signals: a replacement stops a Linux worker by signalling its whole group, and the supervisor forwards a second signal to the same child, which previously killed the shutdown half way and left a lock no later worker could clear. If execution cannot be confirmed stopped, the marker stays; a later worker only clears it after proving no recorded supervisor or group is alive, and otherwise refuses to start (exit 75) bin/fm-remote-job-worker.sh:136-158 bin/fm-remote-job-worker.sh:1013. Jobs interrupted by a clean shutdown stay running with a dead owner for the replacement's orphan recovery bin/fm-remote-job-worker.sh:18-23.

Abandoned code roots

A worker is bound to one code root, and roots can disappear: a pruned no-mistakes gate worktree, a returned pooled worktree, or a removed test fixture bin/fm-remote-job-worker.sh:25-29. Once the root has stopped being a real checkout (no AGENTS.md or no worker script) for FM_REMOTE_JOB_ORPHAN_GRACE_SECONDS (5), the serving loop and the Linux supervisor both stop bin/fm-remote-job-lib.sh:935-941 bin/fm-remote-job-worker.sh:223-236. bin/fm-remote-job-reap-orphans.sh [--dry-run] clears workers already orphaned by older builds; its whole test is that the root named in the worker's own command line fails the same liveness predicate, so a healthy LaunchAgent worker or any worker whose checkout still exists is never a candidate. It inspects only the user's own processes, never signals itself, its group, or an ancestor, and exits 0 unless the process scan itself fails bin/fm-remote-job-reap-orphans.sh:2-33.

Observation: the stale sweep runs every loop

The serving loop resets worker_reap=0 immediately before testing it, so fm_remote_job_reap_stale runs on every iteration, about every 50 ms bin/fm-remote-job-worker.sh:1027-1031. The variable reads like a once-only guard but does not act as one. The sweep's own internal bounds still hold (records must be older than 3600 s, the sequence-claim sweep is rate-limited to once an hour by its marker file bin/fm-remote-job-lib.sh:789-811), so this is a cost question, not a correctness one. The source does not say whether the per-loop scan is intended.
