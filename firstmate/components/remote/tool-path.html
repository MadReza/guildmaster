Non-interactive tool contract

Remote jobs never run a login or interactive shell, so the job library composes the runtime PATH itself by looking at the filesystem, in one fixed order, and every remote child sees exactly that PATH and nothing else.

Read against Firstmate commit ada21f5b.

The problem

A remote Firstmate home needs git, jq, herdr, tasks-axi, treehouse, and at least one agent harness docs/remote-secondmates.md:115. On a developer account those usually come from version managers (nvm, asdf, mise), Nix, or Homebrew, which a person's interactive shell puts on PATH through startup files and shell hooks. The job worker is launched by launchd or a detached supervisor, and each child runs under env -i bin/fm-remote-job-worker.sh:746-753, so none of that happens: "Remote job execution never runs a login or interactive shell, so ~/.profile, ~/.bashrc, and ~/.zshrc never contribute to the job worker's runtime PATH" docs/remote-secondmates.md:46.

Firstmate's answer is not to source those files but to discover the tools' directories directly: "bin/fm-remote-job-lib.sh is the single owner of the worker PATH and builds it by filesystem discovery rather than by evaluating shell startup files" docs/remote-secondmates.md:47 bin/fm-remote-job-lib.sh:58-66. The result is the same on every call, independent of what an account's dotfiles do, and it never executes account-controlled startup code inside a Firstmate job.

Why not source the startup files

The source states the rule and its determinism benefit (the composed order, not the filesystem or shell, decides which install wins bin/fm-remote-job-lib.sh:63-66). It does not spell out a further rationale, such as avoiding arbitrary code in startup files or interactive prompts under launchd. Those would be reasonable readings but are not stated.

The composed order

Rules that shape the list

  • Existence and symlinks. A directory is added only if it exists and is not itself a symlink; that excludes a symlinked ~/.local/bin too bin/fm-remote-job-lib.sh:153-156 docs/remote-secondmates.md:54. The three Nix locations are the exception: a final bin symlink is resolved to its physical directory, while a path reached through symlinked ancestors stays in its documented position bin/fm-remote-job-lib.sh:158-169 docs/remote-secondmates.md:53.
  • Deduplication. An entry already present is not appended again bin/fm-remote-job-lib.sh:148-151.
  • Sorted globs. Multi-version install directories are passed as already-expanded globs, because only the shell's own pathname expansion sorts matches. The comment records the bug this avoids: compgen -G on macOS's bash 3.2 returned raw readdir order, so which install of a multi-version tool a job resolved depended on the filesystem bin/fm-remote-job-lib.sh:171-183.
  • The system tail is unconditional bin/fm-remote-job-lib.sh:278-281.

nvm version selection without nvm

nvm is never run. The library follows the filesystem ~/.nvm/alias/default chain (up to 8 hops, rejecting absolute paths, .., and unsafe characters, allowing lts/<name>) to a selector bin/fm-remote-job-lib.sh:185-207. Then it scans ~/.nvm/versions/node/*/bin:

  • system adds no nvm directory, so Node comes from later system directories bin/fm-remote-job-lib.sh:214 docs/remote-secondmates.md:50.
  • node, stable, unstable match every installed version; a version selector matches installed versions it prefixes on a dot boundary, so 20 matches 20.11.1.
  • The highest matching semantic version wins; if the alias is absent or matches nothing installed, the highest installed version is used bin/fm-remote-job-lib.sh:209-256 docs/remote-secondmates.md:49.

Operator PATH and child PATH

There are two lists. The operator PATH is everything above except the remote root's bin. The child PATH is <remote-root>/bin followed by the operator PATH bin/fm-remote-job-lib.sh:285-296. git and other required tools are resolved only from the operator portion, and the resolved path must sit in a directory of that portion bin/fm-remote-job-lib.sh:298-308. That is the property the entrypoint relies on: "a checkout-local bin/git therefore cannot authorize an untracked command, and a host with no operator git receives an install-or-wrapper diagnostic before command execution" docs/remote-secondmates.md:56-57.

The doctor prints the child PATH its own entrypoint launch produced as its path= line, and reports entrypoint=yes only when the first PATH entry is the configured root's bin bin/fm-remote-doctor.sh:888-895. It then runs its required-tool probe as a worker job, so the tool report reflects what the worker actually resolves bin/fm-remote-doctor.sh:452-496 docs/remote-secondmates.md:89.

A consequence the source calls out

Because ~/.local/bin precedes the package-manager directories, a stale self-updated herdr there shadows the one the account's login shell would find. The Herdr adapter steps around a client the running server refuses, and the doctor names which client it selected docs/remote-secondmates.md:55 bin/fm-remote-doctor.sh:565-581. Client selection belongs to the Herdr backend adapter, documented under Crew.

When discovery is not enough: wrappers

If a required tool is discoverable only in a version-manager directory that is not on the composed PATH (for example an unselected nvm version), fm-remote-doctor.sh --fix may create a Firstmate-owned wrapper in ~/.local/bin docs/remote-secondmates.md:59-61. The mechanics:

  • A tool that already resolves is left alone bin/fm-remote-doctor.sh:509-510.
  • The target is the first regular, non-symlink executable of that name found under the nvm version bins, asdf shims and installs, and mise shims and installs, scanned in glob order bin/fm-remote-job-lib.sh:310-327.
  • An existing file at the wrapper path is replaced only if its first two lines are exactly #!/usr/bin/env bash and # Firstmate remote tool wrapper v1; anything else is reported as a failed fix and left untouched bin/fm-remote-doctor.sh:498-518.
  • The wrapper body is a single exec <quoted target> "$@", written to a temporary file, made mode 0700, and renamed into place bin/fm-remote-doctor.sh:525-536.
  • All five required tools are attempted; for harnesses, the fix stops as soon as one harness resolves or one wrapper lands, satisfying "at least one" bin/fm-remote-doctor.sh:539-552.
  • It "never installs a package" docs/remote-secondmates.md:61.

The document also gives a manual wrapper recipe for tools that need a hand-picked version: it sets tool_bin to the selected version's absolute bin, prepends it to PATH, and execs the absolute target, never re-resolving its own name through ~/.local/bin docs/remote-secondmates.md:62-77.

Two differences between the automatic and manual wrappers

First, the doctor's target is the first match in glob order across all nvm versions bin/fm-remote-job-lib.sh:312-319, not the nvm default selection used for PATH, so it is lexical order of version directory names that picks the version. Second, the doctor's wrapper does not prepend the tool's bin directory to PATH bin/fm-remote-doctor.sh:529, while the documented manual recipe does docs/remote-secondmates.md:68-70. The source does not say whether either difference is deliberate or what it means for tools whose own interpreter must come from the same directory.

The doctor must work on a bare host

The doctor resolves its own directory with shell builtins only, because "a host missing a required tool must still reach the report that names it, not die on a bare PATH" bin/fm-remote-doctor.sh:57-62, and it loads the Herdr adapter only when both herdr and jq resolve bin/fm-remote-doctor.sh:149-161. The same concern explains the entrypoint's git-less doctor bootstrap on the transport page.
