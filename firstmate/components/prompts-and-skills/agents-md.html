AGENTS.md, the always-loaded contract

AGENTS.md is the supervisor's entire job description, loaded whole at every session: "You are the first mate. The user is the captain. This file is your entire job description." AGENTS.md:7-9

Read against Firstmate commit ada21f5b. Up: Prompts and skills.

Who it binds, and who it does not

The file opens by scoping itself: it "is the supervisor contract for primary firstmates and persistent secondmates" AGENTS.md:3. A ship or scout worker launched into a worktree of the Firstmate repository will also have the file loaded by its harness, because it is that repository's project instruction file. The file says so and defers: such a worker "follows the current worker role contract at the start of its FIRSTMATE_OP: v1 launch-brief … it does not become a supervisor by loading this file", and "Merely storing a ship or scout brief in a home does not select the worker role for the agent running here" AGENTS.md:4-5. The worker side of that handshake lives in the launch brief's role contract, which tells a worker on a Firstmate task that the root AGENTS.md "is project content and the supervisor contract for the firstmate managing you: follow this brief instead" bin/fm-dod-lib.sh:57. See Worker launch prompt.

A secondmate runs the same file in its own home. The differences are carried inline at the two points they matter: the captain address "is form only" there AGENTS.md:14, and "reaching the captain means appending the outcome to the parent channel your charter names" AGENTS.md:522. Everything else a secondmate needs comes from its charter.

How it reaches the model

Firstmate relies on the harness's own project-instruction loader; no Firstmate script injects the file at an ordinary session start. For Claude Code the repository ships a two-line CLAUDE.md:

<!-- Points Claude at AGENTS.md via import; edit AGENTS.md, not this file. -->
@AGENTS.md

CLAUDE.md:1-2. The layout section calls it "a real @AGENTS.md pointer" AGENTS.md:61. It is a regular file, not a symlink, and the same bytes are what Firstmate installs into projects: bin/fm-ensure-agents-md.sh "Owns the canonical CLAUDE.md pointer content (the exact two-line @AGENTS.md form). A real-file pointer cannot follow a write into AGENTS.md, which is why the installer never creates a CLAUDE.md symlink." bin/fm-ensure-agents-md.sh:18-20 bin/fm-ensure-agents-md.sh:119-124.

Open question

Firstmate's source does not state, per harness, which of the other primary harnesses (Codex, Pi, OpenCode, Grok, Cursor, omp) reads AGENTS.md natively at session open. The harness-adapter references do not list it either. The only per-harness evidence found is incidental: Muse's launch control is "verified to remove foreign rules_file while retaining project AGENTS.md" .agents/skills/harness-adapters/references/harness/muse.md:41. Treat native loading on the other harnesses as assumed by the design rather than documented by it.

Frozen at launch, and the one refresh path

A running session does not see edits: "A running agent holds AGENTS.md and every skill it has already loaded frozen from the moment it launched, and no verified harness offers a reload, so new bytes on disk change nothing for it until it starts a fresh conversation" .agents/skills/updatefirstmate/SKILL.md:20. Changes also arrive only through the default branch: "Firstmate's shared instruction surface reaches running homes only after it lands on the default branch and those homes fast-forward" AGENTS.md:571.

Three mechanisms deal with staleness:

  • Self-update. After /updatefirstmate prints reread-firstmate: yes, the skill orders "Read AGENTS.md now … before doing anything else" .agents/skills/updatefirstmate/SKILL.md:55-57, and restarts live secondmates rather than trusting them to re-read .agents/skills/updatefirstmate/SKILL.md:6.
  • Pi compaction refresh. A true startup that owns the lock records a SHA-256 baseline of AGENTS.md keyed to the harness pid; on a later Pi or pi-signed compact, a missing, foreign, or changed baseline makes the digest print "CURRENT AGENTS.md - INSTRUCTION REFRESH" with the complete current file ahead of the bulky sections bin/fm-session-start.sh:211-221 bin/fm-session-start.sh:587-610. The baseline is immutable for that lock owner "so every later drifted compaction refreshes again" bin/fm-session-start.sh:219-221.
  • Nothing, elsewhere. The refresh is limited to Pi deliberately: "Claude fresh-reads on reset, and Codex has no tracked interactive reset delivery path" bin/fm-session-start.sh:583-585.

What belongs in it

The file states its own admission rule last: "Keep this file for knowledge useful to almost every future agent session in this project. Do not repeat what the codebase already shows; point to the authoritative file, skill, command, or doc. Prefer rewriting or pruning existing entries over appending new ones. When updating this file, preserve every safety boundary and keep the always-loaded contract concise." AGENTS.md:623-626

The contributor skill turns that into a test. A fact goes into AGENTS.md inline only if "the firstmate AGENT need[s] this on every session or every turn to operate"; a fact needed "only in a nameable situation - a spawn, a recovery, a specific wake type, a specific lifecycle step" goes to a skill with "a one-line trigger pointer left inline" .agents/skills/firstmate-coding-guidelines/SKILL.md:22-25. Exact flags, commands, and paths belong in "the script's own header comment plus its --help output, not prose in AGENTS.md" .agents/skills/firstmate-coding-guidelines/SKILL.md:34-35. The knowledge placement page covers the full tree.

In practice three kinds of text stay inline:

  • Safety boundaries that must hold with nothing else loaded. The hard rules, lock-refused read-only mode, never merge a red PR, never tear down unlanded work, never answer one's own ask-user finding.
  • Triggers. Section 13 is almost entirely "load X before Y" lines, and each operating section starts its conditional work with the same shape, such as "Load harness-adapters before every spawn or recovery" AGENTS.md:218.
  • Declared always-loaded contracts. Sections 7 and 8 open by saying they are always-loaded operational contracts AGENTS.md:289 AGENTS.md:420, which is why they are the second- and fourth-largest sections.

Size pressure is real

The discipline exists because the file once doubled: the coding-guidelines skill "exists because AGENTS.md grew from 585 to 958 lines between its last two restructures, entirely from conditional detail added inline instead of routed to its right home" .agents/skills/firstmate-coding-guidelines/SKILL.md:15. At the pinned commit it is 626 lines.

A tension worth noting

Section 2's layout tree is the largest section (21,195 bytes, a quarter of the file). Most entries are one line, but many carry reference detail the guidelines assign to other owners: exact record formats such as the wake queue's epoch<TAB>seq<TAB>kind<TAB>key<TAB>payload AGENTS.md:145, and per-harness hook-token files AGENTS.md:107-111. The section itself says docs/configuration.md owns the layout AGENTS.md:53. The source does not say why the tree is kept inline anyway; a plausible reading is that "never touch" warnings on private state files (for example AGENTS.md:146 AGENTS.md:152-156) are safety facts the agent needs with no skill loaded, but that rationale is not written down.

House style it is written in

  • One full sentence per physical line, never two sentences on one line, and a plain dash rather than an em dash .agents/skills/firstmate-coding-guidelines/SKILL.md:123-125. The file follows it throughout, which is what lets a one-owner edit touch a single line.
  • Numbered sections referred to by number from elsewhere ("section 7 owns delivery and merge defaults" AGENTS.md:33), so a cross-reference is stable while prose moves inside a section.
  • Rules stated as conditions with an owner, not as procedures: "Load diagnostic-reasoning before scoping a reported bug and before acting on a diagnostic report" AGENTS.md:313.
  • Regression examples kept verbatim where a past failure is the clearest statement of the rule, such as the incomplete merge ask AGENTS.md:487.

Precedence inside the contract

The hard rules are ordered: "Hard rules, in priority order" AGENTS.md:25. Above all standing text sits the captain-instruction rule: "A current, explicit, concrete captain instruction overrides any conflicting standing rule written above", limited to the named action or object, never inferred, broadened, or turned into standing authority AGENTS.md:614-616. Destructive, irreversible, security-sensitive, discard, and merge actions still need the captain to name the concrete action AGENTS.md:618. Section 1 points at this rule rather than restating it AGENTS.md:33, which is the one-owner rule applied to the contract itself.

How it fails

  • Stale copy in a long session. Covered above: only self-update and Pi compaction refresh it.
  • Truncated delivery. AGENTS.md itself is loaded by the harness, not through the bounded digest, so the digest's truncation banner does not cover it. The Pi refresh path is the exception: it prints the file inside the digest, which Pi delivers with a 512 KiB cap and a loud truncation marker docs/sessionstart-nudge.md:93.
  • A worker adopting the supervisor role. Handled by precedence in two places: the file's own scope lines and the launch-brief role contract, which "supersedes any conflicting role identity" bin/fm-dod-lib.sh:51.
  • Guidance drift. Guarded only by review and the one-owner rule; no script checks that AGENTS.md agrees with a skill or header. The documentation audience check validates classification, owner pointers, and local links, not semantic agreement docs/documentation-audiences.md:4 docs/documentation-audiences.md:25-26.
