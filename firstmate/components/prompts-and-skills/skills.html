The skills system

Skills are Firstmate's deferred instructions: procedures that matter only in a nameable situation, stored as SKILL.md files that the harness indexes by name and description and loads in full only when a trigger fires.

Read against Firstmate commit ada21f5b. Up: Prompts and skills.

Why skills exist

A skill is the second tier of the knowledge-placement tree: anything the agent needs "only in a nameable situation - a spawn, a recovery, a specific wake type, a specific lifecycle step" goes to "an agent-only skill under .agents/skills/, plus a one-line trigger pointer left inline in AGENTS.md" .agents/skills/firstmate-coding-guidelines/SKILL.md:24-25. The reason is cost: "A skill's cost is paid only by the sessions that actually load it" .agents/skills/firstmate-coding-guidelines/SKILL.md:63. At the pinned commit the 21 tracked skill bodies total 292,155 bytes, three and a half times AGENTS.md; loading them all every session would cost more than the whole contract they serve. See Prompt economy.

Where skills live

  • One tree for every harness. .agents/skills/ holds "firstmate-loaded internal skills, committed; each carries metadata.internal=true for installers", and .claude/skills is a "symlink to .agents/skills for claude compatibility" AGENTS.md:66-67.
  • metadata.internal is for installers only. "That flag hides them from installer discovery … without affecting how firstmate itself loads them - frontmatter metadata is inert to the agent's own skill loader." README.md:207
  • Public skills are a separate product. skills/ is "standalone public installer-facing skills, committed; not loaded by firstmate" AGENTS.md:69. The internal stow carries a maintainer comment that the public counterpart is "deliberately a separate file with no shared code or environment branching" .agents/skills/stow/SKILL.md:9.
  • A mod is a skill-shaped entry with no SKILL.md. "each is reached through an .agents/skills/<mod> symlink because Claude Code adopts project plugins only from .claude/skills, carries no SKILL.md so every other harness's skill loader ignores that entry" CONTRIBUTING.md:58.

Anatomy of a SKILL.md

Every tracked internal skill uses the same four frontmatter keys:

---
name: ask-user-authority
description: >-
  Agent-only decision procedure for ask-user findings.
  Use before deciding any ask-user finding.
  This skill is the single owner of finding-decision policy: …
user-invocable: false
metadata:
  internal: true
---

.agents/skills/ask-user-authority/SKILL.md:1-10. The conventions visible across the 21 files:

description states the trigger as a condition
Agent-only skills begin "Agent-only …" and then say "Use before …", "Use when …", or "Use on …", matching the trigger-hygiene rule that a trigger is stated as a condition, "never as a vague pointer" .agents/skills/firstmate-coding-guidelines/SKILL.md:70. Several also declare ownership in the description itself, so the index entry tells the agent what the body is authoritative for.
user-invocable separates the two kinds
true for the six skills the captain may type as commands, false for the fifteen that only the agent loads. AGENTS.md section 13's heading states the agent-only meaning: "These skills are not captain-invocable; load them only at their precise triggers." AGENTS.md:578
The body opens with its ownership and its boundary
For example: "This skill is the single owner of the decision policy … AGENTS.md section 7 points here and does not restate this procedure." .agents/skills/ask-user-authority/SKILL.md:15-16
Relative links resolve against the skill directory
"Resolve on-demand reference links and relative links … against the skill directory" .agents/skills/harness-adapters/SKILL.md:21-22, which is why skill bodies write ../../../bin/fm-control.sh.

A trigger declared nowhere in AGENTS.md

ahoy is user-invocable and absent from AGENTS.md; the only trigger is its description, "when the captain explicitly invokes /ahoy" .agents/skills/ahoy/SKILL.md:3. That fits a captain-typed command, which the harness routes by name, but it is an exception to trigger hygiene's "declared inline" rule .agents/skills/firstmate-coding-guidelines/SKILL.md:69. The source does not say whether captain-typed skills are meant to be exempt.

How a skill is triggered, and why at the trigger

Firstmate does not load skills itself. It relies on the harness's skill mechanism, whose behaviour the repository records empirically: a verification probe put a sentinel "only in the skill body below the frontmatter, so returning it required the fresh session to load the excluded skill rather than merely see its indexed name or description" docs/verification/stow-memory.md:13. So at session open the agent sees each skill's name and description; the body enters context only when the agent chooses to load it.

That choice is steered from two sides. AGENTS.md names the condition in the always-loaded text, and the description repeats it in the index. The body is then loaded at the trigger rather than always, for three stated reasons:

  • Cost. Sessions that never hit the situation never pay for the procedure .agents/skills/firstmate-coding-guidelines/SKILL.md:62-63.
  • One owner. The procedure lives in exactly one place, and AGENTS.md keeps only the stub that "must survive with no skill loaded" .agents/skills/firstmate-coding-guidelines/SKILL.md:51-52.
  • Precision. Some triggers are mechanical strings, so the agent loads the right procedure at the right moment: bootstrap-diagnostics fires on any of seventeen named digest prefixes such as TANGLE: or STARTUP_MEMORY_BUDGET:, and explicitly not on silence or other BOOTSTRAP_INFO: facts AGENTS.md:580.
Open question

Whether each harness exposes the whole frontmatter, just the description, or a truncated description in its index is harness behaviour that Firstmate's source does not record. The repository only establishes that name and description are visible before loading docs/verification/stow-memory.md:13.

The router pattern: harness-adapters

The largest reference set is split further so that one operation loads only what it needs. harness-adapters is "the one skill, trigger, and routing owner for harness-specific Firstmate operations. Load this router first, then exactly the common reference and one harness reference selected below. When an action spans rows, load the union once rather than every reference. Files under references/ are resources of this skill, not additional catalogued skills." .agents/skills/harness-adapters/SKILL.md:14-17

The selection is a machine-readable object in the skill body, harness-adapter-routing-v1: an operation (start, trust, skill, interrupt, exit, resume, recovery, primary, model-effort, verify), a scenario within it, and then one harness file (thirteen harness names map onto twelve files) .agents/skills/harness-adapters/SKILL.md:55-100. A Claude spawn therefore loads the 101-line router, common/dispatch.md, common/model-and-effort.md, and harness/claude.md, and none of the other twelve harness files. The router keeps its non-negotiable safety rules inline, such as "Never dispatch a crewmate or secondmate on an unverified adapter" .agents/skills/harness-adapters/SKILL.md:27, applying the inline-stub rule one level down.

Skills and workers

Skills are a supervisor surface. A worker in a project worktree does not have Firstmate's .agents/skills/ in its tree, so the brief reaches the skills it needs by absolute path. The scout scaffold says "Before reporting done, read and follow $FM_ROOT/.agents/skills/captain-hold-lifecycle/SKILL.md" bin/fm-brief.sh:466, and the secondmate charter says "load captain-hold-lifecycle from this home's .agents/skills/" bin/fm-brief.sh:319.

The other direction is a worker's own harness skill, such as the external no-mistakes skill. Firstmate triggers it by typing the harness-native form into the worker through fm-send: "Conversation and harness-native skill invocation use ../../../bin/fm-send.sh" .agents/skills/harness-adapters/references/common/control-and-recovery.md:8. The form differs by harness, /<skill> on Claude and $<skill> on Codex, where "/<skill> is Claude-only and Codex rejects it" .agents/skills/harness-adapters/references/harness/claude.md:12 .agents/skills/harness-adapters/references/harness/codex.md:12. A successful send is not proof: "require the tool-specific postcondition" .agents/skills/harness-adapters/references/common/control-and-recovery.md:27-28.

Home-local skills

A home can hold skills that are not part of the template. They are created only through /stow's over-budget offload, for conditional memory that is too expensive to keep in the always-injected files. The rules are strict: "the stow process never creates or writes a firstmate-repo-tracked skill", and every such skill "is user-owned and local, excluded through that active home's repository-local exclude file" .agents/skills/stow/SKILL.md:170-171. The skill "stays per-home and untracked, and the harness still lists and JIT-loads it because skill discovery scans the filesystem and ignores git status" .agents/skills/stow/SKILL.md:178, which is the guarantee the verification record exists for docs/verification/stow-memory.md:5. Because such a skill cannot be declared in shared AGENTS.md, "Its precise, condition-stated description line is its entire trigger" .agents/skills/stow/SKILL.md:179.

The operator checkout studied here carries one such untracked, excluded skill. Its contents are private and are not described.
