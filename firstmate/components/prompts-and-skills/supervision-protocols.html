Supervision protocol text

The harness-specific half of the supervision instructions: one Markdown snippet per primary harness, rendered into the session-start digest with the session's current posture, plus a one-line repair instruction that guards and hooks reuse.

Read against Firstmate commit ada21f5b. Up: Prompts and skills. What the watcher, hooks, and extensions actually do is documented under Supervision; this page covers the words the agent is given about them.

Why the text is split out of AGENTS.md

AGENTS.md section 8 is harness-neutral: "keep exactly one live supervision cycle using the emitted protocol for this primary harness … Do not substitute another harness's wait shape, use shell &, or create a second cycle when a healthy one already exists." AGENTS.md:422-424 The harness-specific recipe varies a lot (a Claude Stop hook, a Codex foreground checkpoint, a Pi extension tool, a Grok background task), and a session only ever needs its own. Loading all eight in AGENTS.md would charge every session for seven recipes it cannot use, so section 3 says instead that bin/fm-supervision-instructions.sh "renders the emitted supervision block from docs/supervision-protocols/" AGENTS.md:170 and section 8 names "the emitted session-start block" as a mechanism owner AGENTS.md:420.

The snippets are classified agent-runtime, not documentation: they are prompt text that happens to live under docs/ docs/documentation-audiences.md:14.

The renderer

The header states the whole purpose: "Render the primary-harness supervision operating block for session start and the short repair line used by guards and turn-end hooks." bin/fm-supervision-instructions.sh:2-3

What the full block says

The block always opens with the same three current-state lines before any harness text bin/fm-supervision-instructions.sh:221-240:

  • Lock. "held by this session; this session owns normal supervision unless away mode says otherwise", or "read-only; do not drain, arm, spawn, steer, merge, or repair fleet state here".
  • Away or quiet mode. Inactive, or active with the instruction to load /afk or /quiet "and keep normal harness supervision paused while the daemon owns the watcher".
  • Relay ("X mode"). Inactive, or active with "source … before launching any watcher process so the 30s cadence is inherited".

Then one harness-specific "Ordinary wake:" sentence bin/fm-supervision-instructions.sh:183-210, then the snippet. The ordinary-wake sentence exists because the most common mistake it guards against differs by harness: on Claude it is arming a second cycle ("do not arm another cycle yourself"), on Codex it is forgetting to start the next foreground checkpoint.

The repair line

--repair-line prints one sentence and exits bin/fm-supervision-instructions.sh:212-215. Its precedence mirrors the full block: read-only first ("Watcher repair belongs to the session holding the fleet lock"), then away or quiet ("load /afk and ensure the daemon is running instead of starting normal supervision directly"), and only then the harness recipe, optionally prefixed with "After draining queued wakes," and "source … first" bin/fm-supervision-instructions.sh:133-181. That is how a guard banner such as the turn-end guard's "TURN WOULD END BLIND - SUPERVISION IS OFF" bin/fm-turnend-guard.sh:238 carries the correct recipe for the running harness without the guard owning any harness knowledge. Every caller supplies its own fallback sentence if rendering fails, for example "Repair missing watcher supervision according to the session-start operating block." bin/fm-guard.sh:227

The trend across the snippets is to move the arm out of the model entirely: on five of the seven named harnesses a hook, extension, or plugin owns every re-arm, and the text's main job becomes telling the agent not to act. Only Codex and Grok still ask the model to take the next cycle each time.

Placeholders

Snippets never hard-code the home's absolute paths. The renderer replaces six tokens line by line: __FM_PI_EXT__, __FM_PI_TURNEND_EXT__, __FM_OMP_EXT__, __FM_OMP_TURNEND_EXT__, __FM_X_MODE_ENV_SH__ (shell-quoted), and __FM_X_MODE_ENV__ bin/fm-supervision-instructions.sh:120-131. So the text a Pi primary reads contains the exact -e paths for its own clone docs/supervision-protocols/pi.md:6, and Grok's arm command carries the quoted Relay env path docs/supervision-protocols/grok.md:10.

Findings

Kimi: listed as verified, rendered as unknown

AGENTS.md lists kimi among the verified harnesses and puts only muse, gemini, rovo, and agy in the "for crewmates and scouts only" group AGENTS.md:219, which reads as if Kimi could be a primary. The renderer has no Kimi snippet, so a Kimi primary falls through to unknown.md bin/fm-supervision-instructions.sh:94-98, and the Kimi harness reference says "Kimi is outside the primary turn-end guard scope" .agents/skills/harness-adapters/references/harness/kimi.md:45. The router skill settles it against a Kimi primary: "Kimi establishes its unsupported primary boundary in its selected harness reference" .agents/skills/harness-adapters/SKILL.md:57. The always-loaded list and the implementation disagree on this point.

Cursor's step 1 omits unread status

Six named snippets say to acknowledge only after "reconciling open decisions and unread status lines". Cursor's says only "reconciling open decisions" docs/supervision-protocols/cursor.md:5, and its later step also omits UNREAD STATUS where Claude's includes it docs/supervision-protocols/cursor.md:11 docs/supervision-protocols/claude.md:11. AGENTS.md section 8 requires reconciling both on every harness AGENTS.md:431-433, so the harness-neutral contract still covers it; the source does not say whether the omission is deliberate.

A smaller one: the harness-adapter router's safety paragraph names "Muse, Gemini, and AGY" as crew-only .agents/skills/harness-adapters/SKILL.md:38 while AGENTS.md also puts rovo there; the Rovo reference agrees with AGENTS.md that it is "Not verified … as a secondmate or primary" .agents/skills/harness-adapters/references/harness/rovo.md:4.

Adding a harness

The unknown snippet ends with the promotion rule: "Record new verification evidence before promoting an unknown harness to a named snippet." docs/supervision-protocols/unknown.md:13 The renderer's case list is the second place a new name must land bin/fm-supervision-instructions.sh:94-98, and the harness-dependent-check policy requires a portable regression plus a live guard for anything whose verdict comes from vendor output .agents/skills/firstmate-coding-guidelines/SKILL.md:86-104.
