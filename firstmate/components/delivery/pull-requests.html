Pull request flow

When a PR-based task is ready, firstmate registers its PR against the task, which records a validated canonical identity and arms a byte-static merge poll that the watcher runs until the forge reports the PR merged.

Read against Firstmate commit ada21f5b. Up: Delivery overview.

The ready signal and the non-draft requirement

The two PR-based modes signal readiness differently: "no-mistakes reports done [at=<epoch>]: PR <url> checks green after CI is green, while direct-PR reports done [at=<epoch>]: PR <url> after opening the PR, each only for a non-draft PR" AGENTS.md:394.

The non-draft rule exists because "a draft cannot be merged, so a done report on one leaves the merge unasked" bin/fm-dod-lib.sh:258. Both PR-based definitions of done make the worker read the PR back from the forge before reporting (gh pr view <url> --json isDraft must print false), mark a draft ready with gh-axi pr ready, and declare paused: {why the draft is held} instead of done when a draft is kept on purpose bin/fm-dod-lib.sh:13-16 bin/fm-dod-lib.sh:256-261 bin/fm-dod-lib.sh:308-311. The rule is enforced twice more on firstmate's side: bin/fm-pr-check.sh refuses to arm monitoring on a draft, and bin/fm-pr-merge.sh refuses to merge one. Both read draft state through the one function fm_pr_json_draft_state, which prints true, false, or nothing; the check refuses only on true, the merge proceeds only on false bin/fm-pr-lib.sh:219-229.

The supervisor then runs bin/fm-pr-check.sh <id> <PR url> "with the URL copied from that ready signal", and tells the captain the full https:// URL copied from the ready line or the task's pr= record, never one assembled from memory AGENTS.md:395-396 AGENTS.md:529.

The canonical PR identity

bin/fm-pr-lib.sh is the shared record, validation, and atomic-artifact library for merge polling. Its stored identity is provider-tagged: provider, url, host, path, number. On GitHub the path is owner/repository; on GitLab it is the whole nested group path, and the host is part of the identity because GitLab is often self-hosted. "Every consumer re-derives the identity from the stored URL and refuses any record whose parts do not reconstruct that exact URL" bin/fm-pr-lib.sh:1-18.

Two URL shapes are accepted, strictly and per provider bin/fm-pr-lib.sh:163-211:

https://github.com/<owner>/<repo>/pull/<n>
https://<host>/<group>/…/<project>/-/merge_requests/<n>

GitHub owners follow GitHub's username rules (no leading, trailing, or double hyphen) and repositories may not be . or ..; GitLab hosts and namespaces get their own validators rather than "a loosened GitHub rule". Anything else, including a PR number in place of a URL, is refused with the deliberately uninformative "invalid PR check request" and exit status 2 bin/fm-pr-check.sh:31-40.

What bin/fm-pr-check.sh does

Its header: "Record a PR-ready task: store one validated canonical pr=<url> and the forge's exact pr_head=<sha> when available, then atomically arm a static merge poll" bin/fm-pr-check.sh:2-3. In order:

  1. Validate the task id and URL; require state/<id>.meta to be a regular, non-symlinked, single-link file bin/fm-pr-check.sh:37-52.
  2. Finish any interrupted merged-poll retirement for this task before publishing a replacement bin/fm-pr-check.sh:54-60.
  3. For a GitLab URL, refuse when glab is not on PATH: the poll is silent on every error, so without the CLI a watch "would be indistinguishable from a merge request that is never merged" bin/fm-pr-check.sh:62-69.
  4. For a GitHub URL, when gh and jq exist, refuse a positively draft PR and arm nothing. An unreadable draft state does not refuse bin/fm-pr-check.sh:71-79.
  5. For GitHub, read the head commit with gh pr view --json headRefOid and keep it only if it is a full 40- or 64-hex SHA. GitLab records no pr_head, since plain glab exposes it only inside JSON "which would need a JSON processor firstmate does not require"; every consumer treats it as optional bin/fm-pr-check.sh:83-99.
  6. Prepare the poll artifacts in temporary files bin/fm-pr-check.sh:120-121.
  7. Under the task's metadata lock, rewrite the record with every old pr=/pr_head= line dropped and the new ones appended, as a 0600 file on the state device, re-parse its identity before and after the atomic mv, and refuse any mismatch bin/fm-pr-check.sh:123-155.
  8. Under a per-task publish lock, publish the prepared poll generation bin/fm-pr-check.sh:157-168.
  9. Arm the separate contributions observer when jq exists, reporting "coverage is unconfirmed" otherwise bin/fm-pr-check.sh:169-177.
  10. In a secondmate home, publish done [key=child-pr-<id>]: child <id> PR ready: <url> mode=… yolo=… on the parent channel; a main home has no channel and this is a no-op bin/fm-pr-check.sh:178-195.
  11. Print armed: state/<id>.check.sh.

bin/fm-pr-merge.sh also records through this script before merging, with FM_PR_CHECK_MERGE=1 so the draft refusal is skipped in favour of the merge's own authoritative one bin/fm-pr-check.sh:14-15. That is why a PR can be merged even when no ready line ever arrived: the merge itself arms the poll that later detects its landing.

The merge poll

bin/fm-pr-poll.sh is a "Static watcher program for a validated PR/MR poll sidecar. It emits exactly one merged line for a merged PR or MR and stays silent otherwise, including on every error, so a failed lookup can never be read as a merge" bin/fm-pr-poll.sh:2-6. Its bytes are "identical for every task"; the identity is data in the sidecar, never interpolated into shell source. It revalidates every component and requires the stored URL to be reconstructible from them, "so a doctored sidecar cannot redirect this poll at another host or project" bin/fm-pr-poll.sh:7-11. GitHub is read with gh pr view <url> --json state and prints merged only for MERGED; GitLab is read with glab and prints only for merged bin/fm-pr-poll.sh:66 bin/fm-pr-poll.sh:105-106.

The watcher sweeps state/*.check.sh every FM_CHECK_INTERVAL seconds (default 300), each check bounded by FM_CHECK_TIMEOUT (default 30) bin/fm-watch.sh:232-233. The sweep runs before the signal scan, because otherwise "the slow poll (e.g. merge detection) would then never run until the fleet went quiet" bin/fm-watch.sh:2364-2371. For a PR poll it captures a snapshot of the three artifacts, takes the task's control lock, rechecks the snapshot, and then runs the repository's fm-pr-poll.sh --validated <provider> <url> <host> <path> <number> rather than the state file bin/fm-watch.sh:2388-2406. Any check file that is neither a validated PR poll nor a registered custom check is rejected without execution bin/fm-watch.sh:2407-2415 AGENTS.md:117. What happens on merged is on After the merge.

Reviewing the PR's diff

When a delivery path calls for a diff, bin/fm-review-diff.sh <id> compares against a freshly fetched origin/<default> (the local default branch for local-only), and with pr= recorded "the compare side is ALWAYS a freshly fetched refs/pull/<n>/head by default so review stays current after no-mistakes fix rounds push to the PR". A recorded pr_head= is only an offline fallback bin/fm-review-diff.sh:2-14.

Observations

  • The draft refusal at registration is GitHub-only by its own header bin/fm-pr-check.sh:8-13. A GitLab draft merge request is armed normally; whether the merge-time GitLab gate (detailed_merge_status must be mergeable) rejects a draft is a property of GitLab's API that the Firstmate source does not state.
  • A silent poll cannot distinguish "not merged yet" from "closed without merging" or "credentials expired". The poll never wakes on a closed PR; that case surfaces only through the heartbeat's whole-fleet PR review AGENTS.md:443 or crew-state's bounded forge read for a passed run bin/fm-crew-state.sh:17-21.
