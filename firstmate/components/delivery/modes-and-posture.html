Delivery modes and project posture

Every ship task leaves by exactly one of three delivery modes, chosen per task at intake and written into the brief, the spawn, and the task record, so that nothing downstream ever has to guess how a change is meant to land.

Read against Firstmate commit ada21f5b. Up: Delivery overview.

The three modes

The supervisor contract names three delivery paths and one shared rule for all of them: after the path's own work, each "waits for the configured merge authority" AGENTS.md:351-355. The mode decides what the worker does before that wait. It does not decide who may merge; that is the separate yolo axis described below.

The first safety rule of the brief also changes with the mode bin/fm-dod-lib.sh:62-81: a direct-PR worker may push only its own fm/<id> branch; a local-only worker may push nowhere and open no PR; a no-mistakes worker may not push to the default branch. All three forbid the worker from merging. A no-mistakes brief also gets a setup step that runs no-mistakes doctor and, if the repository is not initialised in the worktree, no-mistakes init bin/fm-brief.sh:480-491.

Notice that a no-mistakes worker reports two done lines. The first, done: {summary}, only says the implementation is committed; the definition of done then says "Firstmate will then instruct you to run /no-mistakes" bin/fm-dod-lib.sh:280-281, and the supervisor triggers validation "on the same worker after its implementation commit" AGENTS.md:368. The second done line, with checks green, is the PR-ready signal. The validation pipeline page follows the run in between.

The conditional policy: no-mistakes-prod-only

A fourth word can appear in the registry but never on a task. no-mistakes-prod-only "is a conditional policy rather than one flat mode": internal-only tooling, automation, contributor or operator process, and release or submission work ships direct-PR, while product-facing, mixed, and uncertain work ships no-mistakes .agents/skills/project-management/SKILL.md:44. The supervisor applies that classification to each task at intake and must "never infer internal-only from file location or project name" AGENTS.md:318. Registering the policy is a one-time choice and does not itself classify any change .agents/skills/project-management/SKILL.md:49.

Every command that consumes a task mode refuses the policy word outright, with the same message: "no-mistakes-prod-only is a registry policy, not a task mode; classify this task's surface and resolve it to no-mistakes or direct-PR at intake" (bin/fm-brief.sh:184-186, bin/fm-spawn.sh:767-770, and the same case in bin/fm-promote.sh:80-94).

Mode and yolo are orthogonal

"Delivery mode and yolo are orthogonal. yolo governs merge authority only" AGENTS.md:357-358. With it off, the captain approves every PR merge and every local-only landing; with it on, firstmate merges green, in-scope work itself. The worker is never told its task's yolo value: bin/fm-brief.sh has no --yolo flag, because "the worker never owns merge decisions, so yolo is a spawn-time and firstmate-side input only" bin/fm-brief.sh:57-58. What yolo does and does not allow is on the merge authority page.

The project registry and its parser

Each project's standing posture lives on its line in the home's private registry, data/projects.md AGENTS.md:97. The registry is the captain's default for the project's work, "rather than any task's answer" .agents/skills/project-management/SKILL.md:38. Its one mechanical parser is bin/fm-project-mode.sh.

Line format

- <name> - <desc> (added <date>)                 -> no-mistakes off   (legacy default)
- <name> [<mode>] - <desc> (added <date>)          -> <mode> off
- <name> [<mode> +yolo] - <desc> (added <date>)    -> <mode> on

That grammar is quoted from the script header bin/fm-project-mode.sh:14-17. The parser matches the first line whose first two fields are - and the project name, reads a bracketed annotation if the third field opens one, takes the first non-+yolo word as the mode, and sets yolo on when any word is +yolo bin/fm-project-mode.sh:59-72. It prints two words, <mode> <yolo>.

What it guarantees when the registry is wrong

The parser never fails closed into "no gate". A missing registry, a project not listed, and an unknown mode word each print a warning to standard error and answer no-mistakes off, "so a typo never silently drops the gate" bin/fm-project-mode.sh:35-36 bin/fm-project-mode.sh:52-56 bin/fm-project-mode.sh:74-85. An unrecognised yolo token cannot occur through the grammar, but any value other than on or off is forced to off bin/fm-project-mode.sh:86.

The conditional policy maps to its most rigorous leg, no-mistakes, "so sync, seeding, and init treat such a project as the remote-backed pipeline project it is". Only --raw returns the annotation unmapped, for a caller that must tell the policy apart from a flat mode bin/fm-project-mode.sh:23-33 bin/fm-project-mode.sh:87-91.

Mechanical consumers only

The header is explicit that this answers "what posture did the captain register for this project", "never 'how does this task ship'" bin/fm-project-mode.sh:6-9. Its callers are the ones that have no task in hand:

  • bin/fm-fleet-sync.sh skips a local-only clone when refreshing project clones bin/fm-fleet-sync.sh:327-331.
  • bin/fm-home-seed.sh refuses to route a local-only project to a secondmate ("secondmate routes support only no-mistakes and direct-PR projects") and runs no-mistakes init and no-mistakes doctor for a newly created no-mistakes clone bin/fm-home-seed.sh:460-470 bin/fm-home-seed.sh:709-730.
  • bin/fm-spawn.sh reads it with --raw only to print an advisory deviation notice (below) bin/fm-spawn.sh:2799-2803.

Resolution at intake

The whole rule is six sentences in the supervisor contract AGENTS.md:315-320:

  1. Resolve every ship task's concrete mode and yolo posture at intake.
  2. Pass the mode explicitly to the brief, and both values to the spawn and any scout promotion; "each command refuses to guess the values it consumes".
  3. A current explicit captain instruction wins; otherwise the registry entry is the standing posture, "and dropping below its rigor needs a reason you can state".
  4. On a no-mistakes-prod-only project, classify the task's surface as above.
  5. An unregistered project or absent registry resolves to no-mistakes with yolo off, and the registration gap goes to the captain.
  6. Record the mode, the yolo posture, and a one-line reason for any deviation in the backlog item note.

This is judgment, not code: no script performs step 3 or 4. The scripts only make sure the result of that judgment is supplied, is one of the legal values, and stays consistent everywhere it is copied.

How the decision is carried, and why nothing infers it

The brief
bin/fm-brief.sh <id> <repo> --mode <mode> is required for a ship brief and refused for a scout or secondmate brief bin/fm-brief.sh:175-191. The header states that the script "never reads" the registry bin/fm-brief.sh:41-43. The mode selects the Setup step, rule 1, and the definition of done, all rendered from bin/fm-dod-lib.sh bin/fm-brief.sh:475-493. The rendered block opens with the fixed line Delivery contract: mode=<mode> bin/fm-dod-lib.sh:11-12. An include file that tries to carry its own such line is refused, because the mode is "a per-task --mode decision" bin/fm-brief.sh:214-216.
The spawn
--mode and --yolo are "REQUIRED for every ship spawn and refused on --scout and --secondmate spawns" bin/fm-spawn.sh:7-8; both are closed-set validated bin/fm-spawn.sh:752-790. Before any endpoint exists, the spawn reads the brief's Delivery contract line and refuses a mismatch with "delivery mismatch for <id>: the brief says mode=… but this spawn passed --mode …" bin/fm-spawn.sh:2782-2792. A brief older than that line only warns and launches on the flag. The spawn then records mode= and yolo= in the task record bin/fm-spawn.sh:4468-4469 and prints them on its success line bin/fm-spawn.sh:381-383.
The deviation notice
The spawn ranks modes no-mistakes 3, direct-PR 2, local-only 1 bin/fm-spawn.sh:2772-2779. If the task's mode ranks below the registered one, it prints "notice: <id> ships mode=… while the standing posture for <project> is … - less rigor than the captain's standing posture; proceed only on a current explicit captain instruction or an intake judgment you can state", and continues. A registered no-mistakes-prod-only is excluded, because "both of its legs are legitimate classifications" bin/fm-spawn.sh:2794-2804.
Relaunch
A --relaunch reuses the recorded mode and yolo; passing either flag is refused bin/fm-spawn.sh:743-750.
Promotion
A scout records no delivery posture, "so promotion is where this task's delivery contract is decided" bin/fm-promote.sh:21-26. bin/fm-promote.sh <id> --mode … --yolo … requires both, renders the same definition of done from bin/fm-dod-lib.sh into data/<id>/ship-instructions.md, appends it to the brief for future relaunches, and rewrites kind=, mode=, yolo= in the record bin/fm-promote.sh:1-14 bin/fm-promote.sh:261-265. The single renderer exists because "a promoted no-mistakes worker that never received the ask-user escalation rule or the --yes ban is the exact delivery hole this single owner exists to close" bin/fm-dod-lib.sh:2-7.

The reason for all this explicitness is stated in each header in slightly different words: the registry is "the captain's standing posture as context, not as this task's answer, so a spawn never looks the mode up" bin/fm-spawn.sh:9-11, and the brief/spawn agreement exists so "the worker's instructions and the recorded task delivery cannot drift apart" bin/fm-spawn.sh:12-14. A task that silently inherited its mode from a registry line could change delivery when the registry changed under it, and a brief whose definition of done disagreed with the recorded mode would have the worker stop at one gate while firstmate waited at another.

Choosing a project's posture

The project-management skill owns the choice when a project is added .agents/skills/project-management/SKILL.md:36-53. A newly added or created remote-backed project defaults to no-mistakes-prod-only when the captain says nothing; a project with no remote defaults to local-only. Existing lines "are never migrated or reinterpreted, so a legacy entry with no bracket stays no-mistakes". The +yolo flag defaults off for every project and is enabled "only on the captain's explicit instruction". A no-mistakes or no-mistakes-prod-only project needs an origin remote and must run no-mistakes init && no-mistakes doctor; a direct-PR project needs origin but no initialisation; a local-only project may have no remote .agents/skills/project-management/SKILL.md:57-61 .agents/skills/project-management/SKILL.md:75-81. Per AGENTS.md:267, local-only work also stays in the main home rather than being routed to a secondmate.

Observations

  • The spawn looks the registry up by the basename of the project directory it was given bin/fm-spawn.sh:2786, while fleet sync uses the clone's label. A clone whose directory name differs from its registry name reads as unregistered, which answers no-mistakes and so can produce a deviation notice for a correctly classified task. The notice is advisory, so the effect is noise rather than a wrong landing.
  • Two scripts decide the same "is this local-only" question from different sources. Teardown skips the post-teardown clone refresh from the task record's mode bin/fm-teardown.sh:3701-3703; fleet sync skips from the registry bin/fm-fleet-sync.sh:327-331. They agree whenever the task mode matches the registry, and the source does not say which should win when they differ.
