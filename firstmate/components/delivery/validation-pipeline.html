Validation pipeline

For a no-mistakes task, an external pipeline reviews, tests, documents, fixes, pushes, and opens the PR; Firstmate's part is to start it on the right worker, keep that worker answering gates instead of editing, and read the pipeline's own run step as the truth about where validation stands.

Read against Firstmate commit ada21f5b. Up: Delivery overview.

In flux: the pipeline may be absent

The code treats no-mistakes as a standard tool, but at least one estate has withdrawn it: an operator-private, git-excluded home-local skill in the studied home records that one work estate ships direct-PR because the pipeline was removed organisation-wide. Firstmate's tracked code has no switch for "pipeline withdrawn"; the supported way to live without it is to register projects and resolve tasks as direct-PR or local-only. The section Where the code assumes the tool lists every place that breaks, degrades, or keeps working when the binary is missing.

What no-mistakes is, as Firstmate describes it

No-mistakes is a separate project, not part of this repository. Firstmate's own contributing guide describes it: it "puts a local git proxy in front of your real remote. Pushing through it runs an AI-driven review/test/lint pipeline in an isolated worktree, forwards the push upstream only after every check passes, and opens a clean PR automatically" CONTRIBUTING.md:8-9. Initialising a repository adds a git remote named no-mistakes, which is what bin/fm-home-seed.sh checks for to decide a clone is already initialised bin/fm-home-seed.sh:714. Bootstrap installs it with the upstream install script bin/fm-bootstrap.sh:880.

The pipeline is driven through a CLI surface Firstmate calls axi: no-mistakes axi run, axi respond, axi status, axi abort --run <id>, plus no-mistakes daemon status and the ledger no-mistakes runs. Everything Firstmate knows about those commands' output shapes is encoded in bin/fm-nm-run-lib.sh and bin/fm-crew-state.sh. The mechanics of each gate are deliberately not restated by Firstmate: a worker is told to follow "the guidance no-mistakes itself provides", with no-mistakes axi run --help and each response's help lines "authoritative and version-matched to the installed binary" bin/fm-dod-lib.sh:284.

One shared daemon serves every lane and every home. The brief's rule 7 forbids a worker to stop, restart, or update it, "because restarting it kills other lanes' in-flight pipeline runs; only firstmate manages the daemon" bin/fm-brief.sh:538-540.

How a worker drives a run

Ownership is single and explicit: "The task worker that starts a no-mistakes run drives the pipeline and owns every no-mistakes axi run and no-mistakes axi respond call through the next gate or outcome. Firstmate never invokes no-mistakes axi respond for a crew-owned run" AGENTS.md:369-370. The definition of done a no-mistakes worker receives spells out the rest bin/fm-dod-lib.sh:275-311:

Trigger
The worker first reports done: {summary} for the committed implementation and stops. Firstmate then triggers validation on the same worker with the harness's skill invocation AGENTS.md:368, which is /no-mistakes on Claude and most harnesses and $no-mistakes on Codex (the harness-adapters skill's references/harness/codex.md, line 12). Rovo cannot invoke Firstmate skills at all, so a no-mistakes-mode Rovo ship worker is blocked (references/harness/rovo.md, lines 69-70) .agents/skills/harness-adapters/.
--intent
The run's intent is only the brief's ## Captain's intent body plus later words the captain actually said: never the Firstmate spec, never the worker's own tradeoffs, and self-sufficient enough that "that string plus the codebase must let a reader reconstruct roughly the same specification" bin/fm-dod-lib.sh:285-292. A legacy brief with no provenance-marked captain words stops and asks instead of starting the run bin/fm-dod-lib.sh:288. The launch overlay repeats this as a superseding section bin/fm-dod-lib.sh:187-202.
Gates, not edits
"You drive no-mistakes by responding to its gates, not by implementing fixes." "Do not hand-edit, commit, or fix findings yourself while a run is active - the pipeline applies every fix" bin/fm-dod-lib.sh:283 bin/fm-dod-lib.sh:293. Firstmate treats a worker that hand-edits, commits, aborts, or restarts during a run as duplicating pipeline ownership, and steers it back to the gate response AGENTS.md:388-389.
Background and poll
"One drive call blocks until the next gate or outcome", and a fix round is capped around thirty minutes with up to three chained, while Claude Code kills a command at ten minutes. So the worker backgrounds the drive call and polls no-mistakes axi status. "A killed or timed-out call is never evidence the daemon died" bin/fm-dod-lib.sh:295-299.
The --yes ban
"NEVER pass --yes (or -y) … It is banned fleet-wide. It auto-resolves every gate including ask-user findings with no escalation" bin/fm-dod-lib.sh:305-306.
Return point
"After /no-mistakes reports CI green (the CI-ready return point - do not wait for it to keep monitoring in the background until merge)", the worker confirms the PR is not a draft and reports done: PR {url} checks green bin/fm-dod-lib.sh:308-310. The supervisor contract says the same: "The worker reports the PR when CI first becomes green rather than waiting for merge monitoring to finish" AGENTS.md:390.

The gates a run can park at

Firstmate recognises a parked run by one shared set of patterns so that the two readers can never disagree bin/fm-nm-run-lib.sh:329-347:

  • a gate: line;
  • an awaiting_agent: field;
  • a status: or state: scalar of awaiting_approval or fix_review;
  • a steps-table row whose status column is awaiting_approval or fix_review.

The run's top-level status: word does not decide it: "the CLI leaves it at running while a run waits at a gate, so the word and the gate markers routinely disagree" bin/fm-nm-run-lib.sh:340-343. Who owes the answer is a separate question. A gate is reported parked in every case; only a findings row whose action column is exactly ask-user marks the gate as owed by a human, and crew-state then appends the fixed component ask-user: authority decision bin/fm-crew-state.sh:500-505 bin/fm-classify-lib.sh:2159. That column is located positionally from the table header and guarded by a whitelist of the columns before it, because the free-text description column routinely quotes other findings' actions bin/fm-crew-state.sh:507-537. Ask-user findings are the one gate outcome a worker may never answer itself.

Replacing a run the captain invalidated

Once validation starts, new requirements normally go to follow-up work AGENTS.md:373. Only "a current, explicit captain instruction that completely invalidates the work being validated" keeps the task on the same worker, and then the order is fixed AGENTS.md:375-380:

  1. The worker cancels the active run through axi's supported abort and confirms through axi status that it stopped, before changing any code.
  2. It follows branch_sync.next_action from structured status: axi sync's guarded recovery only when the code is recover_custody, otherwise proceed only when status confirms branch ownership is back.
  3. Custody recovery "settles branch ownership, not content": the replacement is built from the correct pre-invalidation base, keeping the obsolete run's own fix commits out.
  4. Nothing else is hand-edited, committed, restarted, or re-run while the obsolete run owns the branch; then validation runs exactly once against the final head.

Judging validation state from the run step

The supervisor must "Judge validation by the resolved state line from bin/fm-crew-state.sh … never by shell liveness, the last status event, or a raw run record" AGENTS.md:387. The helper's header explains why: the task's .status file is an append-only event log, and crews append nothing when they silently resume, "so tail -1 of that log reports the last EVENT, not the current STATE" bin/fm-crew-state.sh:4-12. The pane is no better: a worker whose pipeline is fixing in the daemon's own checkout looks idle.

Its output is one line bin/fm-crew-state.sh:25:

state: <working|parked|done|blocked|paused|failed|unknown> · source: <run-step|pane|status-log|remote-endpoint|none> · <detail>

Which run belongs to this task

A branch name is not enough, because a reused branch can carry historical runs whose heads were rewritten bin/fm-crew-state.sh:36-40. The rules, owned by bin/fm-nm-run-lib.sh:

  • An executing run (pending, running, fixing, or ci) on the task's branch is authoritative regardless of head, because "the pipeline rebases the branch and commits fix rounds in its own checkout, so a live run's head routinely differs from the task worktree's local head" bin/fm-nm-run-lib.sh:349-371. That exemption is withdrawn once an explicit probe has answered that the daemon is down, because a record still saying running after its daemon died "is evidence from a dead instrument" bin/fm-crew-state.sh:44-53.
  • While branch_sync.state=pipeline_owned, any active run, executing or parked, binds on the pipeline's own custody attribution, never a terminal one bin/fm-nm-run-lib.sh:315-324.
  • Every other run matches only when its head equals the worktree HEAD or the worktree HEAD is its ancestor; local work that advanced past the run head, or diverged, invalidates it bin/fm-nm-run-lib.sh:79-94.
  • A parked run whose head commit the task copy never fetched is recognised only as a provable continuation anchored in the runs ledger bin/fm-crew-state.sh:66-72.
  • More than one run can bind at once (a crashed run at the worktree's commit and its live successor), so fm_nm_select_run takes the newest same-branch row and reports all candidate ids as unknown when two live runs compete bin/fm-nm-run-lib.sh:95-103 bin/fm-nm-run-lib.sh:145-158.

Two deliberate exceptions keep an instrument from reading as work. While the step is ci, axi status alone cannot tell "still waiting on checks" from "checks green, waiting on merge", so a green ci log turns working into done. And a terminal failed run whose only failure is the ci monitor step, after every substantive step completed and the ci log's last marker reads green, reads done (held for merge), because "a monitor whose only remaining job is to observe a human merge decision must not convert the absence of that decision into a failure verdict" bin/fm-crew-state.sh:100-110 bin/fm-crew-state.sh:660-705.

Daemon trouble versus work trouble

The daemon probe is no-mistakes daemon status, bounded like every other call bin/fm-crew-state.sh:708-717. Crew-state separates two questions: "not provably up", which is enough to downgrade a terminal record to unknown, and "answered down", which alone may suppress a live record, so a slow probe cannot make a working crew flap to failed bin/fm-crew-state.sh:719-729. The status log reconciliation then keeps a genuine daemon blocker: a blocked: line reporting a refused or missing daemon socket stays blocked for as long as it is the latest event, while other "daemon, timeout, or unreachability claims are superseded BECAUSE THE RUN IS ALIVE" and answered by steering the worker to reattach bin/fm-crew-state.sh:115-132. The same line is drawn in the worker's own rule 7: a refused or missing socket, or a run failed with a daemon error, is a real block; "a drive-call error, timeout, slow read, or generic unreachability is NOT a daemon error" bin/fm-brief.sh:538-548. A live worker that claims its pipeline is dead or unreachable is a stuck-crewmate-recovery trigger for the supervisor AGENTS.md:588.

Concluding a parked run at teardown

A worker can be torn down while its run is still parked at a gate that nobody will ever answer; such runs were observed holding a fleet slot for hours. Teardown therefore aborts the task's own run with no-mistakes axi abort --run <id> when, and only when, it can prove the run is this worktree's and parked; a run with an autonomous step under way is left alone because the daemon works against its own clone bin/fm-teardown.sh:229-254. If the run is still parked after the abort, teardown refuses bin/fm-teardown.sh:1935-1958.

The gate's own authority boundary

When no-mistakes validates Firstmate itself, its gate agents run inside a checkout whose AGENTS.md installs the fleet-captain identity. Two independent layers stop a gate agent from acting as firstmate docs/architecture.md:280-286:

  • The tracked .no-mistakes.yaml sets disable_project_settings: true, honoured only from the trusted default-branch copy so "a pushed branch cannot turn this off" .no-mistakes.yaml:3-10. The same file pins lint to bin/fm-lint.sh and stores test evidence on an orphan evidence branch.
  • bin/fm-gate-refuse-lib.sh, sourced by fm-spawn.sh, fm-send.sh, fm-control.sh, and fm-teardown.sh, exits with status 3 before any fleet mutation when NO_MISTAKES_GATE is set or the checkout's git common directory lies under a gate repository bin/fm-gate-refuse-lib.sh:1-29.

Firstmate's own repository also requires the pipeline of its human contributors: a Require no-mistakes Actions check demands a structured attestation from no-mistakes v1.46.0 or newer, bound to the current PR head CONTRIBUTING.md:5-14.
