Merge authority and the PR merge gate

Who may say "merge" is a rule for the supervisor's judgment; whether a particular merge is allowed to happen is a set of live checks in bin/fm-pr-merge.sh, which refuses anything it cannot prove green, current, and unheld, and records the authority it merged under so the landing can be reported truthfully later.

What the scripts do not check

No merge entrypoint reads the task's yolo value. bin/fm-pr-merge.sh contains no reference to it, and bin/fm-merge-local.sh mentions it only in its header ("only after the captain approves (or yolo=on auto-approves)" bin/fm-merge-local.sh:8-9). Whether a merge is authorised by the captain's word or by yolo is entirely the supervisor's judgment. The scripts enforce what can be proved without reading words: the PR's live state, a still-open captain hold, the away-posture record, and the refused flags. The recorded yolo= is used only for reporting: it is echoed on the secondmate PR-ready line and in fleet snapshots bin/fm-pr-check.sh:186-189 bin/fm-fleet-snapshot.sh:758.

The merge gate, step by step

Usage: bin/fm-pr-merge.sh <task-id> <pr-url> [--attended-override] [--allow-red <check-name>] [-- <extra forge merge args>] bin/fm-pr-merge.sh:103. The supervisor must use it for "every task PR merge so merge metadata is recorded and an unproved merge is refused instead of reported as landed", and never "call a lower-level merge command around their guards" AGENTS.md:363.

GitHub conditions

One live gh pr view --json state,isDraft,mergeable,mergeStateStatus,headRefOid,baseRefName,statusCheckRollup read supplies every condition, "each read live at merge time rather than taken from recorded metadata": the PR is open, not a draft, MERGEABLE, not DIRTY, and "every unwaived check is green at the exact current head commit". Every failing condition is reported, not just the first. Reading needs gh and jq; either missing stops the merge before any state is recorded bin/fm-pr-merge.sh:11-21 bin/fm-pr-merge.sh:574-668.

A check is green when it is a status context in SUCCESS, or a check run completed as SUCCESS, NEUTRAL, or SKIPPED; a pending check is not green. Because GitHub leaves a cancelled run in the rollup beside the passing re-run it triggered when the base advanced, a check is judged by its current run: a name leaves the red set only when every non-green run completed, has a whole-second startedAt, and started strictly before a green run. Status contexts are never superseded, and an unnamed check run can neither supersede nor be superseded bin/fm-pr-merge.sh:495-518. The reported name is what --allow-red matches, and it waives only checks with exactly that name.

The verified head is passed as --match-head-commit, "so a push that lands between that read and the merge fails the merge instead of landing commits nothing verified". The method defaults to --squash when the caller passes none bin/fm-pr-merge.sh:9-21. After the command returns, the script reads GitHub's queue-aware state through GraphQL, falling back to gh-axi's view, and accepts only merged or in merge queue; "every outcome it cannot prove refuses" bin/fm-pr-merge.sh:26-31. A base branch with a merge-queue rule is refused in attended posture with the exact --attended-override -- --auto --<method> retry flags, and no method is chosen for the caller bin/fm-pr-merge.sh:32-48.

GitLab conditions

For a merge request the live read must show it open, detailed_merge_status mergeable, has_conflicts false, blocking_discussions_resolved true, and the head pipeline succeeded at the exact current head. The verified head goes to glab mr merge as --sha; no method flag is added because the project's own merge method applies, and --yes only skips an interactive confirmation "which no supervised run can answer". A recorded pr_head that disagrees with the live head "is reported rather than trusted" bin/fm-pr-merge.sh:53-67 bin/fm-pr-merge.sh:1190-1210. --allow-red is refused on GitLab, "where a merge already requires the head pipeline to have succeeded" bin/fm-pr-merge.sh:176-179. An accepted but unconfirmed or auto-merge-queued request leaves the poll armed and records no landing bin/fm-pr-merge.sh:105-108.

Refused flags and the attended override

Extra arguments may not carry --repo/-R in any form, including bundled short options such as -yR, because the repository comes only from the URL; nor --sha or --match-head-commit, because the head comes only from the live read. --auto, --admin, and branch deletion (--delete-branch, -d, GitLab's --remove-source-branch) are refused unless --attended-override is passed "for an explicit captain instruction", and the override "never skips the live green check, the away-record read, or a captain hold" bin/fm-pr-merge.sh:91-101.

Captain holds

Before either forge call, the per-task control lock serialises the captain-hold check through the forge command. "A still-held or unreadable row refuses before that command, so a captain approval must be recorded as an answer --release before this entrypoint is invoked" bin/fm-pr-merge.sh:69-72 bin/fm-pr-merge.sh:875-895. The hold mechanism itself belongs to Backlog and decisions.

Away posture

While state/.afk-contract exists, "any green merge may proceed under away authority: the record's presence is the whole mechanical fact, and which merge the captain's away words meant is the supervision session's reading" bin/fm-pr-merge.sh:73-78. The authority read and the synchronous forge command share the away record's lock, so the record cannot be archived or replaced between them; failing to take that lock refuses. While away, --auto, GitLab auto-merge, --allow-red, and any GitHub base whose rules cannot prove the absence of a merge queue are refused, and a GitLab merge is forced immediate with --auto-merge=false bin/fm-pr-merge.sh:79-89 bin/fm-pr-merge.sh:920-980 bin/fm-pr-merge.sh:1204-1206. The supervision branch's prompt states the same boundary from the other side: "A red pull request is never merged while away, whatever the words say" bin/fm-branch-prompt.sh:109-110.

Two limitations are accepted in the open rather than hidden: a queue rule or PR base change after the preflight can still enqueue a merge that lands after away authority lapses, and killing the lock-owning shell while its forge child lives lets stale-lock recovery admit archive or replacement first bin/fm-pr-merge.sh:82-86 docs/architecture.md:368-370.

The retired values yolo and away-grant are still accepted when read, so a record written before the current model "is still consumed, but they are never written again" bin/fm-merge-authority-lib.sh:14-19.

The record exists so the later merged poll can say who merged. When the watcher sees merged, it reads the record and uses it only if every identity field matches its own validated snapshot; "Missing, malformed, or mismatched state means external; it is never resolved again from a later away-posture record" bin/fm-merge-authority-lib.sh:24-26 bin/fm-watch.sh:2439-2459. "Resolution authorizes nothing by itself": only the merge path gates on the answer, and the watcher and teardown consume or remove the record under the same task lifecycle lock bin/fm-merge-authority-lib.sh:28-34.

Merge-outcome publication

A confirmed merge must not live "only in the merging agent's memory" docs/architecture.md:380. fm_merge_outcome_report <home> <state> <task-id> <pr-url> <origin> [authority] is shared by the merge entrypoint (origin=self) and the watcher's poll (origin=poll) bin/fm-merge-outcome-lib.sh:1-25 bin/fm-merge-outcome-lib.sh:36-56:

  • The destination is the home's role, never the caller's choice. A secondmate home appends done [key=merged-<id>]: merged <id> <url>[ <authority>] to its parent channel; a main home appends a wake check: merge landed: <id> <url>[ <authority>] to its durable wake queue. A poll observed in a secondmate home also gets a local wake after the upward write bin/fm-merge-outcome-lib.sh:79-107.
  • away and external (and the retired tags) are appended to the line; attended stays untagged bin/fm-merge-outcome-lib.sh:44-49.
  • Duplicates are suppressed through the task's .pr-poll-merge-notified marker under its own lock. "The outcome is published before the marker is committed, so a failed commit stays eligible for at-least-once retry and may rarely duplicate rather than leave a merge silent" bin/fm-merge-outcome-lib.sh:18-23.
  • It returns 0 recorded (or already recorded), 2 invalid request, 3 when the home's own role or parent binding cannot be read, 1 otherwise. "A caller that has already merged must report a non-zero return rather than treat it as success: the merge landed and the record did not" bin/fm-merge-outcome-lib.sh:51-55. The merge entrypoint prints an actionable: line in both non-zero cases bin/fm-pr-merge.sh:1232-1244.

Observations

  • The merge-authority record distinguishes only away from attended. A yolo-authorised merge and a captain-worded merge are both attended, so after the fact the ledger cannot say which of the two authorised a given landing. The yolo tag that once said so is retired bin/fm-merge-authority-lib.sh:14-19.
  • The away record is mechanically broader than yolo: while it exists "any green merge lands under away authority, yolo or not", as the runtime verification log records docs/verification/runtime-backends.md:2192. The policy bound is not in the script but in judgment: the always-loaded contract says away mode "never expand[s] approval authority for merges" AGENTS.md:473, and the branch prompt limits action to what the captain's recorded away words call for bin/fm-branch-prompt.sh:107-109. The two agree only if the away words are read as the explicit captain instruction for that merge.
