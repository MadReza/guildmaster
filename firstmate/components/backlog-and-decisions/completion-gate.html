Completion gate

An investigation or visual review often surfaces questions only the captain can answer. It cannot count as complete until every such question is carried by a captain-held task. The supervisor attests that inventory with complete, and scout teardown refuses to erase the source until verify passes.

Read against Firstmate commit ada21f5b. Up: Backlog and decisions.

Why a gate

A scout's report and a Lavish review are temporary. Teardown removes the task's metadata, and a review session ends. A captain question that lives only in that prose is lost when it goes. The policy: "Every unresolved question that belongs to the captain and is discovered while producing, reading, presenting, or ending an investigation or visual review must be carried by a captain-held task in the authoritative backlog of the home that owns the originating work before that work or review may be treated as complete." .agents/skills/captain-hold-lifecycle/SKILL.md:19 "A completed investigation and an ended visual review use this same owner and completion command; a visual tool, including Lavish, never owns a parallel completion policy." .agents/skills/captain-hold-lifecycle/SKILL.md:24

Deciding what counts as a captain question is the agent's job, because "scripts must not infer captain calls from report prose, visual-review artifacts, terminal output, or chat" .agents/skills/captain-hold-lifecycle/SKILL.md:15. The gate checks only that the agent recorded an inventory and that every entry in it is durable. AGENTS.md sets the trigger: "Before treating the investigation or any visual review as complete, load captain-hold-lifecycle; teardown enforces that shared completion gate." AGENTS.md:413

The flow

complete <origin-id> (--none | <task-id>...)

Contract: bin/fm-captain-hold.sh:131-142. Implementation: bin/fm-captain-hold.sh:1623-1702.

  1. Ownership. The origin must belong to this home: a task record, a data/<origin>/report.md, or a backlog row. Otherwise: "origin $origin is not owned by the active home" bin/fm-captain-hold.sh:426-430 bin/fm-captain-hold.sh:1638.
  2. Union. The supplied ids are unioned, sorted, with the existing decision_keys=. "Later review passes may add ids." bin/fm-captain-hold.sh:439-445
  3. Durability. Every entry is resolved (exact, legacy, or migrated) and must be "actively captain-held, or closed with a recorded answer" bin/fm-captain-hold.sh:513-529 bin/fm-captain-hold.sh:795-811. A task closed by a bare tasks-axi done fails here. "the completion gate keeps failing until answer records the decision the captain actually gave" .agents/skills/captain-hold-lifecycle/SKILL.md:47.
  4. --none. This is "an explicit semantic attestation that the just-reviewed surface has no unresolved captain call". It is refused while the origin's status log still has an open keyed decision: "hold a captain task for what remains, or answer them, before attesting --none" bin/fm-captain-hold.sh:1667-1671.
  5. Attest. Under the task metadata lock, it appends decisions_reviewed=1 and decision_keys=<sorted,comma,list>, but only when they change bin/fm-captain-hold.sh:1673-1678. The metadata reader takes the last value of a key bin/fm-captain-hold.sh:447-449.
  6. Transfer. For every still-open keyed status decision, it appends captain-held [key=<key>]: tracked by <keys>. This is one guarded self-announced append, so it "do[es] not wake this same session" bin/fm-captain-hold.sh:1680-1698. The transfer stops the status fold from duplicating a Captain's Call item. It is also why the divergence guard treats captain-held as a verified close rather than a contradiction.
  7. Report. It prints complete: <origin> captain-call inventory reviewed (<keys>), plus [attested through the configured prefix: …] for any Beads id resolved by name alone, "so the guess stays auditable" bin/fm-captain-hold.sh:1700-1701.

After teardown. When the origin's metadata is already gone, complete still verifies every listed task, then prints its line. It writes no metadata and makes no transfer. "A post-teardown visual review can complete against the surviving report and durable tasks without recreating volatile task metadata." docs/captain-hold-lifecycle.md:26 bin/fm-captain-hold.sh:1630-1636

verify <origin-id>

This subcommand is read-only. Scout teardown calls it after checking that the report exists and before removing any source state, "so teardown cannot erase a source before this gate has succeeded" bin/fm-captain-hold.sh:143-145. It fails if:

  • the metadata is absent, or lacks decisions_reviewed=1: "origin $origin has no completed captain-call inventory";
  • any inventory entry is no longer durable;
  • any keyed status decision is open. It "fails on any keyed status decision that opened after the last complete, which makes re-running complete the repair" docs/captain-hold-lifecycle.md:31.

bin/fm-captain-hold.sh:1704-1730

Teardown's refusal reads: "REFUSED: scout task $ID has not passed the captain-call completion gate. Inventory its report and any visual review through bin/fm-captain-hold.sh before teardown." bin/fm-teardown.sh:3287-3292 "The --force path remains the explicit captain-approved discard escape hatch." docs/captain-hold-lifecycle.md:32

A worked example

Suppose a scout sample-scout reports two open questions, and both gate the same follow-up work item sample-fix. Following the skill, the supervisor holds that one work item and gives its reason both questions:

bin/fm-captain-hold.sh hold sample-fix --reason "choose approach A or B; also confirm scope X"
bin/fm-captain-hold.sh complete sample-scout sample-fix
# complete: sample-scout captain-call inventory reviewed (sample-fix)
bin/fm-teardown.sh sample-scout      # verify passes; the report link is recorded

The call stays on Captain's Call until an answer records the captain's words. The ids are illustrative. The command shapes come from bin/fm-captain-hold.sh:23-32 and the policy lines .agents/skills/captain-hold-lifecycle/SKILL.md:20-23.
