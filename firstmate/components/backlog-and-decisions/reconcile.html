Reconcile requests

A captain call can stop being a question without the captain ever answering it. "Reconcile" is the standing third choice for that case. It does not answer the call. It asks Firstmate to check the current state first, then either close the call with evidence or keep it open with a note.

Read against Firstmate commit ada21f5b. Up: Backlog and decisions.

The problem it solves

"A captain call can stop being a question without the captain ever answering it because the subject lands, the premise turns out to be false, or the choice becomes a matter of fact rather than the captain's to make. reconcile is the standing third option for that case, and its whole point is that it is NOT an answer. It means 'go verify the latest state', and it resolves in exactly one of two ways once that verification has actually been done: close the call with the evidence that made it moot, or leave it open with a note recording that it is genuinely still active." docs/captain-hold-lifecycle.md:66-68

Every decision card on the board carries this option. The board injects it "so the guarantee does not depend on the composer's memory" bin/fm-bearings-board.sh:57-59.

The flow

Why reconcile is reserved at the intake

"The value remains reserved at the shared keyed-answer intake, which visibly refuses it from every channel and never passes it to answer. A reconcile value delivered through chat or any ordinary keyed-answer caller therefore cannot complete a task, lift a hold, write a resolution record, or create a reconcile request." docs/captain-hold-lifecycle.md:70-71 The script header says: "RECONCILE IS RESERVED AT THIS INTAKE, NOT FILTERED IN A CHANNEL." bin/fm-captain-hold.sh:96-102 The check runs before the close mode is read, "so no channel and no card-declared mode can turn it into a close, release, or request".

Board requests use "a separate captured-source seam". The board emits the selected option and the freeform note in separate fields, "so annotating Reconcile cannot turn it into an ordinary answer value". The Lavish adapter's answers command emits only non-reconcile selections, and its reconciles command emits only task ids whose structured selection is Reconcile docs/captain-hold-lifecycle.md:73-75. The payload validator reserves the value "across every card type because the captured payload carries no card type" bin/fm-bearings-board.sh:60-62.

Rollout branch

"Current rows require the versioned shape and the choice tag; a time-limited rollout branch accepts ordinary answers from the old question/answer shape but refuses its bare and separator-annotated reconcile values from both intakes because those rows do not separate the selected option from its note." docs/captain-hold-lifecycle.md:76

Recording the request

fm-captain-hold.sh reconcile-requests --source-id <source-id> --source <provenance>
# stdin: <task-id>[\t<captain note>]

bin/fm-captain-hold.sh:27 bin/fm-captain-hold.sh:1412-1469

  • It verifies the binding again: "source $source_id is not bound; no reconcile requests were created" bin/fm-captain-hold.sh:1424-1425.
  • Per id, under the task's control lock, it refuses an invalid or over-long id, an absent task, a closed task, or one "not held for the captain". A read that hits its time bound stops the command.
  • It writes one request per task, atomically, with mode 0600: 
    schema=fm-reconcile-request.v1
task=<task-id>
requested=<UTC timestamp>
source=<provenance>; captain note: <note>
    "Idempotent per task: a repeated reconcile keeps the one request and its original timestamp, so a re-delivered board answer never resets the clock on an obligation that is already open." bin/fm-captain-hold.sh:1363-1383

The record's purpose: "so the obligation to re-check cannot be lost between the wake that carried the answer and the turn that acts on it" docs/captain-hold-lifecycle.md:81. The runner side is feed_reconcile_requests bin/fm-procevent.sh:447-458. "Failures remain best-effort and never acknowledge or suppress the captured result." docs/captain-hold-lifecycle.md:79

The two outcomes

"That board-created request is yours to work off in the turn that receives it" .agents/skills/captain-hold-lifecycle/SKILL.md:41. Both outcomes "refuse unless that task still has the pending request created by the captain's board selection, so neither is a standalone way to mutate a captain call" .agents/skills/captain-hold-lifecycle/SKILL.md:42.

Moot: reconcile close <task-id> --evidence-file <path>

The command requires an evidence file: "a moot call closes on evidence, never on assertion" bin/fm-captain-hold.sh:1513. The evidence goes through the same size and non-empty checks as a decision file. The command writes a resolution record with mode reconciled under the label Reconciliation evidence:, then runs tasks-axi done. "The distinct mode and label are what keep the record honest: it says the call dissolved against verified evidence, and it never claims the captain answered." docs/captain-hold-lifecycle.md:87-89 bin/fm-captain-hold.sh:1499-1563

An exact retry on an already closed call finishes the interrupted close. Different evidence, or a record in any other mode, is refused. In a secondmate home a failed parent publication fails the command bin/fm-captain-hold.sh:1524-1541 bin/fm-captain-hold.sh:1558-1560.

Still active: reconcile note <task-id> --note-file <path>

The note is non-empty and at most 8192 bytes. The call must still be open. The command appends one block to the body and leaves the hold in place:

Captain hold reconciled: <UTC>
Reconcile request: <requested> | <source> | note digest: <sha256>
<note text>

bin/fm-captain-hold.sh:1565-1621

"a marker bound to the request timestamp, provenance, and note digest lets a matching retry finish retirement without appending again while a later request with the same finding still receives its own dated note" docs/captain-hold-lifecycle.md:92. After writing, it checks again that the call is still open: "recording the reconcile note released captain-held task $id" is a failure bin/fm-captain-hold.sh:1619.

reconcile list

This is a read-only enumeration: <task>\trequested=…\tsource=… per request, then reconcile-requests: N bin/fm-captain-hold.sh:1483-1497.

Retirement is checked

"Every retirement is checked: if request removal fails after an answer, close, or note is already durable, the durable outcome stands but the command fails and leaves the pending request visible for retry." docs/captain-hold-lifecycle.md:96 A normal answer also retires a pending request, "because an answered call has no remaining re-check obligation" docs/captain-hold-lifecycle.md:95. The summary guarantee: "No path here closes a captain call without either the captain's words through answer or the evidence through reconcile close." docs/captain-hold-lifecycle.md:97

Known limit: remote secondmate cards

"A remote-secondmate card whose task is absent from the main backlog therefore remains announced but cannot create a main-home request; owner-aware request and mutation routing to the authoritative secondmate home is a separate follow-up." .agents/skills/captain-hold-lifecycle/SKILL.md:40 docs/captain-hold-lifecycle.md:117-118
