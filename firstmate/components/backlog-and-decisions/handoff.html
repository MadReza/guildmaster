Cross-home handoff

When a queued item belongs to a secondmate's domain, fm-backlog-handoff.sh moves it out of the main backlog into that secondmate home's own backlog, then wakes the secondmate. The secondmate owns its own queue. The main backlog never keeps a copy.

Read against Firstmate commit ada21f5b. Up: Backlog and decisions. Secondmate homes themselves belong to Crew and Remote.

Why it exists

"Hand already-identified, in-scope backlog items off from the main firstmate backlog to a secondmate's own home backlog. Use this when a secondmate is created (or whenever an existing queued item should become its domain's work) so the secondmate owns its queue from day one instead of the item staying stranded in the main backlog." bin/fm-backlog-handoff.sh:2-6 It follows from the backlog contract: "Work routed to a secondmate is recorded in that secondmate home's own backlog, not the main backlog" AGENTS.md:536. "secondmate-provisioning and bin/fm-backlog-handoff.sh own cross-home handoff safety." AGENTS.md:545

The provisioning skill gives the usage: "Read data/backlog.md, pick queued items that fit the new scope, and move them with: bin/fm-backlog-handoff.sh <secondmate-id> <item-key>...". "After seeding, run this handoff for the new secondmate's in-scope queued items." .agents/skills/secondmate-provisioning/SKILL.md:185-193

Validation before anything moves

  • A genuine secondmate home. The destination may not be the filesystem root, the active home, or the Firstmate repo. It may not be inside either, or an ancestor of either. It must carry .fm-secondmate-home naming this exact id, plus AGENTS.md and bin/ bin/fm-backlog-handoff.sh:208-260.
  • Real files. Neither backlog may be a symlink or a non-regular file bin/fm-backlog-handoff.sh:262-272.
  • Classify every key first. Each key is sorted as already in the secondmate backlog (skip, idempotent), Queued in main (move), In flight, Done, some other section, or missing. "Abort with no changes if any key matches neither backlog." In flight is refused. Done is refused because "Done records stay with their home and are pruned/archived". Missing keys are refused. In every refusal "nothing was moved" bin/fm-backlog-handoff.sh:953-996. The classifier "reads only section headings and item header lines - never item bodies" bin/fm-backlog-handoff.sh:274-279.
  • Body indentation. Any continuation line that is not two-space indented refuses the handoff "rather than risk leaving it orphaned" bin/fm-backlog-handoff.sh:1017-1028.
  • Compatible tasks-axi with atomic multi-id mv. The manual knob is ignored here: "the config/backlog-backend=manual knob only governs firstmate's own hand-editing of its own backlog, not this validated helper" bin/fm-backlog-handoff.sh:44-48.

Local route

The wake text is fixed: "New routed work is in your backlog. Run bin/fm-session-start.sh now, then act on the routed task." bin/fm-backlog-handoff.sh:98 It goes through fm-send.sh to the secondmate's recorded endpoint. A seeded home that has not yet been spawned is a valid destination, "but its missing endpoint is reported rather than pretending the task was started" bin/fm-backlog-handoff.sh:350-355 bin/fm-backlog-handoff.sh:550-569. A prepared wake "is bound to the exact sorted requested-key batch; an unrelated handoff to that mate refuses until the original batch is retried, so it cannot discard wake intent for work that already moved" bin/fm-backlog-handoff.sh:59-62.

Remote route

"Remote routes use an outbox handoff: one atomic local tasks-axi mv removes the selected set from the dispatchable backlog into data/handoff/<id>.outbox.md, then an idempotent confined transfer and fm-backlog-receive.sh deliver it." bin/fm-backlog-handoff.sh:50-52 "No two-phase journal exists." bin/fm-backlog-handoff.sh:62

  • Older batches first. A fresh handoff never appends to an older recovery batch. "a confirmed wake can survive when outbox cleanup fails; if new work were staged into that outbox, the old confirmation would suppress the wake for the new work" bin/fm-backlog-handoff.sh:813-824.
  • Half-applied moves. "A hard local kill can land tasks-axi's target persist before its source persist. The outbox is already authoritative in that state, so converge by deleting only duplicates that tasks-axi itself confirms are dependency-safe." bin/fm-backlog-handoff.sh:833-836
  • Confined transfer. The put goes through fm-on.sh --stdin <id> fm-remote-file.sh put state/handoff/<id>.outbox.md 1048576 <bytes> <sha> <generation>. An unknown outcome keeps the outbox: "outbox preserved at $outbox" bin/fm-backlog-handoff.sh:688-701.
  • Receiver. The delivered file "must be a non-symlink backlog-format scratch file confined to FM_HOME/state/handoff. Every item must be Queued. Keys already present in data/backlog.md are skipped; every remaining key moves in one dependency-closed tasks-axi mv transaction under tasks-axi's own locks." It clears a stale lock at most once, and only for "its own backlog or delivered lock whose pid is dead and whose mtime is at least 30 seconds old" bin/fm-backlog-receive.sh:2-16.
  • Wake is best effort. After receipt, "the outbox is released and the handoff succeeds regardless of the best-effort wake outcome; an undelivered remote wake remains separately tracked in wake-pending state and is retried under the same correlation" bin/fm-backlog-handoff.sh:66-70.

Public relay commitments

A public relay reply is bound to its work by home and id. Moving the work out of this home therefore makes that binding stale. After a successful move the script warns, for example: "warning: <key> still owes a public reply bound to main/<key>; rebind it to secondmate:<id> …". It also warns when this home has an open public loop with nothing owed. "The move is not blocked: rebinding or rechain is a relay-side decision the caller makes." bin/fm-backlog-handoff.sh:28-32 bin/fm-backlog-handoff.sh:324-348

Decisions stay in the owning home

Handoff moves work items. The captain-hold policy separately requires calls to be registered where the originating work lives: "secondmate-owned work registers in that secondmate home's backlog, and a question already held anywhere is never re-registered as a second row" .agents/skills/captain-hold-lifecycle/SKILL.md:25. A secondmate's holds reach the captain through its parent channel and its bounded home summary (buckets).

Not settled by the source: handing off a held item

The classifier looks only at the section. A captain-held row in ## Queued is therefore classified as movable bin/fm-backlog-handoff.sh:961-974. Nothing in the script refuses it, and nothing records whether the hold's parent-channel line should then come from the new home. The source does not say whether handing off a held item is intended, tolerated, or an oversight.

Not settled by the source: non-markdown homes

The handoff hard-codes MAIN_BACKLOG="$DATA/backlog.md" and SUB_BACKLOG="$SUB_HOME/data/backlog.md", classifies keys with awk over those files, and runs tasks-axi mv … --file "$MAIN_BACKLOG" --to "$SUB_BACKLOG" bin/fm-backlog-handoff.sh:86 bin/fm-backlog-handoff.sh:949 bin/fm-backlog-handoff.sh:1072. A home whose adapter is Beads keeps no such file, so every key would classify as missing. The configuration document says only that handoff "delegates the item move to tasks-axi mv" docs/configuration.md:117. The read source does not settle whether handoff is meant to support non-markdown homes.
