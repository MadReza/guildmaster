Recording answers

A captain call is resolved only by writing down what the captain said. answer records those words in the task and then either closes the call or releases the gated work. Every channel that carries an answer, whether chat or a board, feeds one keyed intake that ends in that same answer.

Read against Firstmate commit ada21f5b. Up: Backlog and decisions. Previous: Captain holds.

The rule

"Never close anything the captain owns without recording what he actually said: bin/fm-captain-hold.sh answer writes his exact words into the task and closes a question-shaped call, while --release frees a captain-gated work item to proceed." .agents/skills/captain-hold-lifecycle/SKILL.md:30 An answer can also be evidence rather than words. That case is reconcile close, and "Never use answer for an evidence-only moot call" .agents/skills/captain-hold-lifecycle/SKILL.md:46.

The answer subcommand

fm-captain-hold.sh answer <task-id> --decision-file <path> [--release]

bin/fm-captain-hold.sh:25. Implementation: bin/fm-captain-hold.sh:997-1110.

  1. Load the words. The decision file must exist, be non-empty, and be at most 8192 bytes. Its SHA-256 is the decision digest bin/fm-captain-hold.sh:322-332.
  2. Lock and read. It takes the per-task control lock and reads the row's state, hold_kind, and body.
  3. Write the resolution record at the top of the body, beneath any leading hold-set stamp. The previous body is kept below it and archived through --archive-body bin/fm-captain-hold.sh:910-941.
  4. Close. --release runs tasks-axi unhold. Otherwise it applies any retained artifact from a pending-close record, then runs tasks-axi done bin/fm-captain-hold.sh:966-973.
  5. Normalise. It removes the stamp, which restores "resolution-first body ordering", verifies the record survived, publishes resolved on the parent channel, and retires any pending reconcile request. It prints answered: <id> or released: <id>.

The resolution record (Level 4)

Resolution recorded by fm-captain-hold.
Decision digest: <sha256 of the decision text>
Resolution mode: answered | released | repaired | reconciled

Captain decision:
<the decision text, verbatim>

bin/fm-captain-hold.sh:503-511. For reconciled, the label becomes Reconciliation evidence:. Records are prepended, "so the first match is the newest record" bin/fm-captain-hold.sh:462-474. Their count gives the parent-channel occurrence number and the --identity suffix.

Release versus closure

The two close modes correspond to the two shapes a call can take. "it closes a question-shaped call, while answer --release frees a captain-gated work item to proceed without completing it" docs/captain-hold-lifecycle.md:17.

Close (default)Release (--release)
ShapeA question whose answer is the deliverableWork waiting on the captain's go
tasks-axidoneunhold: the row stays Queued or In flight
Mode recordedansweredreleased
AfterwardsThe call leaves Captain's Call. The row is Done.The work can be dispatched, or merged. Cleanup closes it after landing.

A merge approval is a release, not a close. "A merge approval uses that existing release path because approval permits the merge to proceed; cleanup closes the work only after it lands and records what shipped. Closing a held row at merge approval instead records completion before landing, so the backlog claims completion before the work actually ships." .agents/skills/captain-hold-lifecycle/SKILL.md:31-32 The merge entrypoints enforce this. "a captain approval must be recorded as an answer --release before this entrypoint is invoked" bin/fm-pr-merge.sh:69-72. Both fm-pr-merge.sh and fm-merge-local.sh refuse a row that open reports as still held bin/fm-merge-local.sh:118-130. The away posture does not change this: "neither posture releases a captain hold" bin/fm-pr-merge.sh:76-78.

When an answer changes what a task must build, the skill hands off to AGENTS.md section 7's Validate contract, which preserves "the captain's words in the brief" and steers the worker .agents/skills/captain-hold-lifecycle/SKILL.md:33.

Input format and parsing

fm-captain-hold.sh answers [<legacy-origin> | --any-origin] --source <provenance>
# stdin, one per line:
<task-id>\t<answer>\t<label>[\t<mode>]

bin/fm-captain-hold.sh:26 bin/fm-captain-hold.sh:1207-1348

  • Key. "The key IS the task id - no identity arithmetic." It must match [A-Za-z0-9._-] and be at most 128 characters. A bad key is dropped silently. The answer and label are sanitised: control characters are stripped and the text is capped at 512 characters bin/fm-captain-hold.sh:1199-1201 bin/fm-captain-hold.sh:1240-1245.
  • Reserved value. The exact answer reconcile is matched "before it reads the close mode, visibly refuses it, and never passes it to answer". It prints refused: <key> (reconcile requests require a bound captured source) bin/fm-captain-hold.sh:96-100 bin/fm-captain-hold.sh:1246-1250.
  • Mode. An empty mode or done completes the call. release lifts the hold. "anything else is skipped" bin/fm-captain-hold.sh:80-82.
  • Decision text. This is a pure function of the inputs, "so the same answer delivered twice is idempotent rather than a conflicting decision" bin/fm-captain-hold.sh:1182-1190: 
    Captain answered this call through <source>.
Task: <task-id>
Answer: <answer>
Answer as shown to the captain: <label>
  • Outcome per key. closed: <id>, or skipped: <id> (<reason>) when the key names no task, is not captain-held, or is already closed, or when the mode mismatches a replay. The run ends with answers: closed=N skipped=M and "exits nonzero when any key was skipped" bin/fm-captain-hold.sh:82-87 bin/fm-captain-hold.sh:1346-1347.
  • Provenance. "--source is provenance text recorded in the durable decision, never a behavior switch: this command has no per-channel branch and no knowledge of chat, review decks, or any transport." bin/fm-captain-hold.sh:87-89

Each key finally runs "$0" answer "$id" --decision-file "$tmp" [--release], "so every guard applies identically no matter which channel the answer arrived on" bin/fm-captain-hold.sh:78-79 bin/fm-captain-hold.sh:1333.

Channel 1: chat (fm-send --resolve-key)

When the supervisor answers a worker's keyed question in chat, fm-send --resolve-key <key> closes that key in the task's status log itself: "the captain-facing OPEN DECISIONS record closes at answer time and never depends on the busy worker writing a matching resolved line" bin/fm-send.sh:154-160. If the status log no longer owns the key, because it was already transferred to a captain-held task, fm-send resolves the key to that task instead. It tries the key as a task id first, then <task>-decision-<key>, and accepts only a row that is not Done and is hold_kind: captain bin/fm-send.sh:565-584 bin/fm-send.sh:639-647. After the answer is delivered, it pipes <task-id>\t<answer>\t into answers --source "a firstmate answer sent to <task>" bin/fm-send.sh:734-746. "fm-send closes nothing itself" bin/fm-send.sh:188-193.

If the key matches neither record, the send is refused and nothing is sent: "no open decision or blocker with that key … and no captain-held task … still open (already closed or mistyped)" bin/fm-send.sh:646. Answering a decision is main-owned while the captain is attended. The away posture relocates that guard to the supervision branch bin/fm-send.sh:649-663. The status-log side of this is documented under Communication.

Channel 2: captured sources (fm-procevent)

A process-event source, such as the Lavish board's answer poll, captures a result detached from its origin. For a bound source, the runner pipes the adapter's own answers <result-file> output into the intake with --source "the captured result <id> sequence <n>" bin/fm-procevent.sh:435-445. This is "silenced and best-effort … because this never acknowledges anything" bin/fm-procevent.sh:430-434. The runner "names no adapter, parses no result, and carries no decision rule" docs/captain-hold-lifecycle.md:60. Only built-in adapters may feed the intake: "Trusted external process-event adapters intentionally expose no answer operation and cannot feed this authority-bearing intake" docs/captain-hold-lifecycle.md:61. The Lavish adapter "reads only rows tagged choice, relays a card's declared close mode, and can never let freeform captain prose forge a task id or a mode" docs/captain-hold-lifecycle.md:62.

Source bindings

fm-captain-hold.sh bind <source-id> [<legacy-origin> | --any-origin]
fm-captain-hold.sh unbind <source-id>
fm-captain-hold.sh binding <source-id>

# state/decision-bindings/<source-id>.origin (mode 0600)
schema=fm-decision-binding.v1
origin=(any)

bin/fm-captain-hold.sh:28-30 bin/fm-captain-hold.sh:1114-1180

"a source with no binding feeds nothing, so this whole path is opt-in per source and an unbound source behaves as if it did not exist. bind deliberately does not require the source to exist yet, so a channel can be bound BEFORE it is armed." bin/fm-captain-hold.sh:121-124 The board enforces that order: binding "ALWAYS precedes arm, so the board can never produce an answer that has nowhere to go" bin/fm-bearings-board.sh:21-24. A corrupted binding is "a hard error rather than a silent 'unbound': feeding nothing is the safe direction only when it is a deliberate choice, never when it is a corrupted record" bin/fm-captain-hold.sh:1124-1127. Retiring a source unbinds it bin/fm-procevent.sh:2033. The (any) marker cannot collide with a real id, because "Slug validation rejects parentheses" bin/fm-captain-hold.sh:315-317.

An unbound source, or a key naming no captain-held task, "simply feed nothing: the answer is still captured and firstmate is still woken, and closing falls back to the direct command above" .agents/skills/captain-hold-lifecycle/SKILL.md:37.

What an answer also retires

"A successful normal answer also retires any pending request, because an answered call has no remaining re-check obligation." docs/captain-hold-lifecycle.md:95 bin/fm-captain-hold.sh:1402-1410 When a pending-close record retained a PR or report for this row, the answer copies it into the row first, so the delivery still reaches Recently Landed (replay).
