Captain holds

A decision only the captain can make is an ordinary backlog task with a captain hold on it. bin/fm-captain-hold.sh hold is the only way to place that hold. It stamps when the hold began, can defer the call to a date, and in a secondmate home tells the parent at once.

Read against Firstmate commit ada21f5b. Up: Backlog and decisions. Next in the lifecycle: Recording answers.

One primitive, no decision type

"There is no separate decision type. A captain call is an ordinary backlog task held for the captain through this script's mandatory hold subcommand, and its identity is simply the task id." bin/fm-captain-hold.sh:12-14 Structurally, a captain call is a row that is not Done and whose hold_kind is captain. That is exactly what the open predicate tests bin/fm-captain-hold.sh:1900-1916.

The script supplies mechanics only. It "never reads report, visual-review, chat, or terminal prose to guess whether the captain owes an answer. The invoking agent decides what is genuinely waiting on the captain; this script supplies guarded creation, a durable record of what the captain actually said, the investigation completion gate, and the one keyed-answer intake every channel feeds" bin/fm-captain-hold.sh:5-10. The policy side lives in the captain-hold-lifecycle skill, which is "Agent-only" .agents/skills/captain-hold-lifecycle/SKILL.md:4.

When the supervisor places a hold

  • Any decision worth tracking. "A decision is simply a task held for the captain" AGENTS.md:537. The same goes for "a pending captain decision or relay reminder … worth durable tracking" AGENTS.md:538.
  • Every unresolved captain question an investigation or review surfaces. Each "must be carried by a captain-held task in the authoritative backlog of the home that owns the originating work before that work or review may be treated as complete" .agents/skills/captain-hold-lifecycle/SKILL.md:19. The completion gate enforces this.
  • Which row to hold. "Prefer holding the work item the question gates over minting a new row … keep one held task per genuine gate: a multi-question review is one held task pointing at its report, not a row per question." The board then shows "exactly one board card" per task .agents/skills/captain-hold-lifecycle/SKILL.md:20-21.
  • Which home. The hold goes in the originating work's own FM_HOME. "a question already held anywhere is never re-registered as a second row" .agents/skills/captain-hold-lifecycle/SKILL.md:25.
  • What does not get a hold. "Resolved findings, recommendations that need no captain choice, and prose that merely sounds decision-like do not create held tasks." .agents/skills/captain-hold-lifecycle/SKILL.md:48

In captain-facing chat the word hold is internal vocabulary. The skill says "do not use the word hold in captain chat" .agents/skills/captain-hold-lifecycle/SKILL.md:63. AGENTS.md rewrites "hold, gate, ask-user, needs-decision, blocked, or paused" as "the concrete decision, wait, approval, blocker, or external delay" AGENTS.md:496.

The hold subcommand

fm-captain-hold.sh hold <task-id> --reason <reason> \
  [--title <title>] [--repo <repo>] [--origin <origin-id>] [--until YYYY-MM-DD]

bin/fm-captain-hold.sh:23-24. Implementation: bin/fm-captain-hold.sh:813-908.

  1. Validate. The task id must be a "privacy-safe slug" ([A-Za-z0-9._-]). The reason must be one line and "must not contain parentheses (tasks-axi hold contract)". --until must be YYYY-MM-DD. The hold time is FM_CAPTAIN_HOLD_NOW or the current UTC time, as YYYY-MM-DDTHH:MM:SSZ bin/fm-captain-hold.sh:829-845.
  2. Serialise. It takes the per-task control lock state/.control-<id>.lock bin/fm-captain-hold.sh:286-290 and requires a compatible tasks-axi that exposes --kind captain.
  3. Existing task. A Done task is refused: "task $id is already closed; a new captain call needs its own task". A task already under an active captain hold keeps its original stamp. A --title that differs from the existing title is refused bin/fm-captain-hold.sh:848-861.
  4. Missing task. --title is required. The repo comes from --repo, else the origin's task metadata project=, else firstmate. The body is Origin: <origin> when an origin is given. It then runs tasks-axi add <id> <title> --kind captain --repo <repo> with BD_DUE_REQUIRED=false bin/fm-captain-hold.sh:862-883.
  5. Stamp, then hold. It writes the hold-set stamp as the leading body line and verifies it. Only then does it run tasks-axi hold <id> --reason … --kind captain [--until …] bin/fm-captain-hold.sh:884-898.
  6. Verify. It re-reads the row. It fails if hold_kind is not captain, or if the stamp was lost while holding bin/fm-captain-hold.sh:899-905.
  7. Publish to the parent channel, if this is a secondmate home (below), and print the task id.

A real invocation from AGENTS.md: bin/fm-captain-hold.sh hold <id> --reason "<reason>", with --until <date> for a deferral AGENTS.md:537. The skill puts "the question and its options in the hold reason" .agents/skills/captain-hold-lifecycle/SKILL.md:21.

The hold-set stamp

The first body line of a held row is Captain hold set: 2026-09-23T17:44:50Z. A date-only form is also recognised bin/fm-captain-hold.sh:755-761. The stamp defines "this hold lifecycle's age". Presentation reads it to decide whether an undated hold has aged out of Captain's Call.

  • Written first. "A concurrent snapshot may see the harmless stamp by itself, but can never see a newly held task without the timestamp that defines this hold lifecycle's age." bin/fm-captain-hold.sh:884-886
  • Preserved across retries. "Retries of an active hold preserve its hold-set timestamp, while re-holding released work starts a new timestamped lifecycle" docs/captain-hold-lifecycle.md:15 bin/fm-captain-hold.sh:763-793.
  • Kept until the close lands. answer writes its resolution block beneath the stamp. It removes the stamp only after the close succeeds, so "If the close is interrupted, the still-held task therefore keeps its original age basis" docs/captain-hold-lifecycle.md:18-19.
  • Older holds. "Existing undated holds without a hold-set stamp fall back to the task's since date." docs/captain-hold-lifecycle.md:130

Deferral with a date

"When the captain says 'later', that is an answer too: re-hold with bin/fm-captain-hold.sh hold <id> --reason "<reason>" --until <date> so the item leaves the live Captain's Call and resurfaces on its date, instead of leaving a live-looking card or fabricating a closure." .agents/skills/captain-hold-lifecycle/SKILL.md:34 The date is "the captain's own deferral date", stored through tasks-axi's date gate bin/fm-captain-hold.sh:52-54. Until it is due, the hold sits in the dated bucket. From that date tasks-axi reports it as no longer held, but the annotations survive, and they are what keep it answerable bin/fm-captain-hold.sh:70-72.

Not settled by the source

Once the date passes, tasks-axi no longer reports the row as held, while hold_kind: captain survives. The dispatch gate tests the held flag bin/fm-backlog-transition-lib.sh:821-826, and open tests hold_kind bin/fm-captain-hold.sh:1902. So an expired deferral on a work item appears both dispatchable and an open captain call. Nothing read here says whether that pairing is intended. The snapshot places such a row in the live bucket, so it reappears on Captain's Call.

The lifecycle of one call

The open predicate

"open is the read-only predicate a mechanical closer asks before it may retire a task's row: is this task still an open captain call? Exit 0 means it is (not Done, hold kind captain), 1 means it is not, and 2 means the answer could not be established, so a caller that must never close a live call can treat 'cannot tell' as its own case instead of as a no." bin/fm-captain-hold.sh:161-165

  • --distinguish-absent returns 3 for an absent task. A home with no backlog file counts as absent, "because it records no captain calls" bin/fm-captain-hold.sh:166-167 bin/fm-captain-hold.sh:1887-1898.
  • --identity prints the call's lifecycle identity, <hold-set stamp>#<recorded answer count>, and only on exit 0. It exists because "re-holding released work starts a new lifecycle without necessarily touching the task's status log, so a consumer that bounds repeated work per call cannot use the task id alone" bin/fm-captain-hold.sh:169-174 bin/fm-captain-hold.sh:1903-1913.
  • Every read failure on a record that exists is a 2, "because a mechanical closer must never read 'cannot tell' as permission to close" bin/fm-captain-hold.sh:1854-1859.

Parent channel: a secondmate's calls reach the captain

"inside a secondmate home a task held for the captain, and its answer, are captain-facing facts the moment they are recorded, so hold publishes needs-decision [key=captain-hold-<task>-<n>] and answer (and answers) the matching resolved line on the parent channel … whether or not the mate model appends anything." bin/fm-captain-hold.sh:194-198

  • The key. <n> is "the count of resolution records the body already carries plus one, so a released and re-held task opens and closes a distinct parent decision with no new persisted state". An exact retry republishes the same line, "which the channel deduplicates" bin/fm-captain-hold.sh:199-202.
  • A main home publishes nothing. The channel library returns 1 for "a main home … nothing to report" bin/fm-parent-channel-lib.sh:47-51.
  • A failed publication does not undo the record. "The hold or answer is already durable in the backlog, so a channel that cannot be written is reported as actionable: on stderr rather than undoing the record" bin/fm-captain-hold.sh:203-205 bin/fm-captain-hold.sh:231-240. One exception: when a pending reconcile request exists, an answer's failed publication fails the command, so the request is not retired silently bin/fm-captain-hold.sh:1402-1410.

The parent channel itself is documented under Communication.

Legacy identities and the shim

Before the collapse, decisions had their own identity, <origin>-decision-<key>, minted by bin/fm-decision-hold.sh. "Those rows are already plain task ids, so they render, answer, verify, and close through the collapsed surfaces with no data migration." docs/captain-hold-lifecycle.md:180-181 Three legacy inputs are still resolved in place docs/captain-hold-lifecycle.md:182:

  • a decision_keys= metadata entry that names no task;
  • a channel key that names no task, when the source's binding carries a concrete legacy origin;
  • resolution records written by the old script, recognised wherever a record is read (Resolution recorded by fm-decision-hold.) bin/fm-captain-hold.sh:451-460.

Resolution order is: the exact task id first, then the legacy derived id, then (on Beads) the migrated row. The result reports how it resolved (exact, legacy, migrated-note, migrated-prefix) "so a caller can record which evidence carried the attestation" bin/fm-captain-hold.sh:723-728. On a Beads home, the marker note migrated from data/backlog.md id <legacy id> is authoritative. The configured prefix is only a guess, accepted "solely for a single row still held for the captain - two such rows refuse rather than attest" docs/captain-hold-lifecycle.md:183-185.

The shim "only maps the retired command surface onto it so in-flight work briefed before the collapse keeps working for one release, and it will be removed in the release after the collapse lands" bin/fm-decision-hold.sh:5-8. Its mapping includes resolve … --routed-to becoming an answer, followed by clearing the recorded blocked-by edges bin/fm-decision-hold.sh:10-28. A decision-hold-lifecycle skill also survives, but only as a "Renamed pointer kept for in-flight briefs" that redirects to captain-hold-lifecycle .agents/skills/decision-hold-lifecycle/SKILL.md:4-5.

Failure behaviour

ConditionResult
The task is already DoneRefused. A new call needs its own task. Closed calls are never reopened.
--title is missing for a new task, or differs from the existing titleRefused before any write.
The reason has parentheses or a newlineRefused, following the tasks-axi hold contract.
A backlog read hits its time boundStops with exit 124, and never reads the timeout as absence, which could mint a duplicate row bin/fm-captain-hold.sh:359-379.
The stamp or hold does not verify after writingFails loudly, naming the task.
The parent channel cannot be writtenactionable: on stderr. The hold stands.
