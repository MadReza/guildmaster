Backlog and decisions

Firstmate keeps one durable queue of work items, and it holds every decision only the captain can make as an ordinary task in that queue. It never uses a separate decision type, and it never leaves a decision only in the conversation.

Read against Firstmate commit ada21f5b. Where Firstmate hands the backlog format to the external tasks-axi tool, the page says so and quotes the help text of the installed tasks-axi 0.2.5. Firstmate's own floor is 0.2.4 (bin/fm-tasks-axi-lib.sh:45).

What this area does

The area has two jobs, and both use one record.

  • The work queue. "The configured tasks-axi backend is the durable queue; the tracked default is data/backlog.md. It tracks work items only, never agents; persistent secondmates never appear as backlog items." AGENTS.md:534-535 Dispatch and cleanup move items through that queue for you (automatic transitions). The supervisor files items, records decisions, and keeps notes current AGENTS.md:540.
  • Decisions held for the captain. "A decision is simply a task held for the captain: create the task with bin/fm-tasks-axi.sh add when needed, then always hold it through bin/fm-captain-hold.sh hold <id> --reason "<reason>", with --until <date> when the captain defers it." AGENTS.md:537

Design intent

The sources state three principles directly. Every mechanism in this area follows from one of them.

One primitive for work and decisions
"A decision is not a separate thing in this system: it is an ordinary backlog task held for the captain, and the task id is the identity every surface and channel uses." docs/captain-hold-lifecycle.md:8 The script header repeats this: "There is no separate decision type." bin/fm-captain-hold.sh:12-14 Older installs had a separate decision identity, <origin>-decision-<key>. That identity has collapsed into plain task ids and is now kept only for compatibility (legacy identities). The policy prefers holding the work item a question gates, and creates a new row "only when no work item exists to hold" .agents/skills/captain-hold-lifecycle/SKILL.md:20.
Durable rather than conversational
A decision the fleet should remember goes into the backlog, not into chat: "When a main-side thread such as a pending captain decision or relay reminder is worth durable tracking, file it as its own work item and hold it through that wrapper." AGENTS.md:538 Each mechanism downstream keeps an open call alive through things that would otherwise erase it. Cleanup reopens the row instead of closing it (retain). An interrupted cleanup replays from a record on disk (replay). A reconcile request is written to disk "so the obligation to re-check cannot be lost between the wake that carried the answer and the turn that acts on it" docs/captain-hold-lifecycle.md:81.
Answered in the captain's own words
"Never close anything the captain owns without recording what he actually said" .agents/skills/captain-hold-lifecycle/SKILL.md:30. answer takes a decision file, writes its digest and text into the task body under a Captain decision: label, and only then closes or releases the task bin/fm-captain-hold.sh:56-62. Anything that closes a call without the captain's words must say so. An evidence-backed reconciliation is recorded under a different label, Reconciliation evidence:, "so it can never read as the captain's words" bin/fm-captain-hold.sh:106-108.

A fourth rule runs through the scripts: scripts never read prose to guess at decisions. fm-captain-hold.sh "never reads report, visual-review, chat, or terminal prose to guess whether the captain owes an answer. The invoking agent decides what is genuinely waiting on the captain" bin/fm-captain-hold.sh:5-8. The presentation layer also buckets holds "only from structured fields … no wording can hide, reveal, or reclassify a decision" docs/captain-hold-lifecycle.md:125-126.

Where this area touches others

  • Communication owns the status log, keyed needs-decision lines, the OPEN DECISIONS fold, fm-send, and the parent channel. This area relies on the fold's closing verbs (divergence) and publishes hold lines on the parent channel (parent channel).
  • Supervision owns the wake drain that prints RECORD DIVERGENCE, and the watcher whose stale alarm is bounded by open --identity.
  • Crew owns fm-spawn.sh and fm-teardown.sh. This area documents only the backlog transition fused into them.
  • Delivery owns merges. The merge entrypoints refuse a still-held task (release), and ask-user-authority decides which findings reach the captain at all.
  • Observability owns the fleet snapshot and Bearings. This area documents only how holds are bucketed (hold buckets).
  • Persistence owns the operational home layout (data/, state/, config/) and the lock primitives used here.
  • Remote owns remote secondmate homes. The remote outbox route is summarised in handoff.

Open questions

These places are where the source does not settle behaviour. Each is detailed on its page.

  • How a home on a non-markdown adapter (Beads) feeds the fleet snapshot, which parses data/backlog.md directly (buckets).
  • Whether handoff works at all on a non-markdown home, since it reads and moves data/backlog.md by path (handoff).
  • Whether a captain-held Queued item may be handed off. The classifier looks only at the section (handoff).
