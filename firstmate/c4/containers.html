Containers

The separately running processes and separately kept stores inside one Firstmate instance, what each is responsible for, and how they talk. Everything here was traced from the scripts, not from the docs alone.

Read against Firstmate commit ada21f5b. Up: System context.

The shape in one paragraph

Firstmate splits two kinds of work. Exact, repeatable mechanics live in bash scripts. Judgement lives in an agent. "the two never mix" VISION.md:34. The supervisor agent is an ordinary harness session that loads AGENTS.md as its job description AGENTS.md:7-9. It changes nothing directly: every spawn, steer, lifecycle action, merge, hold, and cleanup goes through a guarded script in the toolbelt AGENTS.md:329-339 AGENTS.md:363.

A zero-token watcher in bash sleeps on the fleet. It absorbs benign wakes and writes actionable ones to a durable wake queue before exiting, which wakes the agent bin/fm-watch.sh:3-4 bin/fm-watch.sh:258-261. Workers run in isolated worktrees inside a runtime session backend. They receive instructions through durable steering inboxes and report through append-only status event logs. Every obligation is a record in the operational home, so "a restart must be a non-event" AGENTS.md:256.

Operational input marker
Machine-originated input to an agent is prefixed with U+2063 then FIRSTMATE_OP: v1 <kind>:. The kinds are session-start, watcher, turn-end-guard, away-supervisor, launch-brief, and branch-outcome, plus a separate from-firstmate carrier for routed secondmate requests. bin/fm-operational-input.sh:9 bin/fm-operational-input.sh:31 bin/fm-operational-input.sh:39

Whether a worker is busy comes from its adapter's own lifecycle events, never from rendered text. The verdicts are busy, idle, unknown, and dead, each with its source. bin/fm-busy-lib.sh:2 bin/fm-busy-lib.sh:17 bin/fm-busy-lib.sh:49 docs/architecture.md:217-218
