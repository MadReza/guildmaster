Lessons for Guildmaster

What Guildmaster's tracing should take from Honeycomb, what it should leave, and whether any of Honeycomb can run on the patron's machine. In short: borrow the data model and the questions, not the machinery.

Written against vision/tracing-design.md and vision/tracing-research.md as merged on 2026-09-30. This page switches to Guildmaster's vocabulary from TERMINOLOGY.md: patron, Party Leader, Adventurer, posting, register. Everything said about Guildmaster here is this site's proposal inferred, for the patron to accept or not.

The short version

Honeycomb's lasting idea is that one wide, raw record per unit of work, queried at read time, answers questions nobody thought to ask in advance. Guildmaster's design already has that shape: a posting is a trace, spans live in the register, derived measures are queries. What Honeycomb adds is three habits worth adopting, a column store's worth of machinery not worth building, and one local tool pattern for testing. None of it changes the design's ranking of storage and viewers.

First, the scale

Almost every machine on the containers page exists to cope with the right-hand bars: Kafka to absorb bursts and allow replays, a custom store because no database met the cost, S3 and Lambda because local disk ran out, sampling because storing everything costs money. At the left-hand bar, a SQLite file does all of it.

What to borrow

1. One wide row per span, written once, with an open attribute set

Honeycomb. The canonical event is built up during the work and emitted once at the end: "initializes a map and pre-populates it with everything known ... When the request is ready to exit or error, Honeycomb ships it off in one arbitrarily wide structured event" blog-structured-events. The schema is never declared; it is "the set of fields Honeycomb has seen" docs-resource-structure, and on disk a new field is just a new column file blog-virtual-datasets.

For Guildmaster. The design lists a span table but not its columns (Storage and viewer). Give it a few fixed columns (trace id, span id, parent, name, start, end, status) and put every other attribute in one JSON column, read with sqlite3's JSON functions, which gm already requires. Then a new attribute, a new Claude Code field, or a guild.* key added in build step 3, needs no schema migration, and old spans simply lack it. Write each span once, complete, when it ends, rather than as an opening row updated later.

2. Put the high-cardinality ids on everything, and never pre-aggregate

Honeycomb. "Any aggregation that is performed at write time is actively harmful" wb-best-practices; the ids metrics systems drop, user and build ids, are the ones that explain incidents docs-service-map-how docs-custom-instr.

For Guildmaster. The design already stamps guild.posting on every span "so a posting can be found even in a viewer that only searches attributes", and keeps session.id, prompt.id, agent_id and the tool-use id (Guild attributes). Add the camp's git commit at the span's end, and the writ's hash on every span of an Adventurer run, not only the dispatch span: those are the Guildmaster equivalents of a build id. Keep every measure in Derived measures a query over spans, never a stored counter, which is the design's principle 3 in Honeycomb's terms.

3. A BubbleUp of its own: gm stats --compare

Honeycomb. BubbleUp "computes the values of all dimensions both inside the box ... and outside the box (the baseline), and then compares the two and sorts the resulting view by percent of differences" docs-core-loop. It is the feature customers credit most for speed, "from hours to seconds with BubbleUp triage" in one case study cs-depot.

For Guildmaster. The patron's questions are comparative: why did this posting need three exchanges when most need one; why are some model calls slow. With attributes in one JSON column, the comparison is one query. A minimal version, ranking by the difference in share:

-- BubbleUp in the register: which attribute values are over-represented among
-- slow model calls (the selection) compared with all the others (the baseline)?
WITH s AS (
  SELECT (end_ms - start_ms) > 30000 AS sel, attrs
  FROM span WHERE name LIKE 'chat %'
),
tot AS (SELECT SUM(sel) AS n_sel, SUM(1 - sel) AS n_base FROM s),
kv  AS (SELECT s.sel, j.key, CAST(j.value AS TEXT) AS value
        FROM s, json_each(s.attrs) AS j)
SELECT key, value,
       ROUND(100.0 * SUM(sel)     / tot.n_sel,  1) AS pct_selection,
       ROUND(100.0 * SUM(1 - sel) / tot.n_base, 1) AS pct_baseline
FROM kv, tot
GROUP BY key, value
ORDER BY ABS(1.0 * SUM(sel) / tot.n_sel - 1.0 * SUM(1 - sel) / tot.n_base) DESC
LIMIT 10;
$ gm stats --compare 'chat spans slower than 30 s'          (illustrative)
key                              value        selection  baseline
gen_ai.request.model             opus-5-5        81.0%     22.4%
gen_ai.request.reasoning.level   high            77.9%     35.0%
guild.focus                      appt-v2         74.2%     30.1%
guild.role                       party-leader    69.0%     41.7%
guild.attempt                    2               18.3%      1.2%

The selection can be anything the derived measures define: postings that were not right first time, exchanges whose reply took over two minutes, Adventurer runs whose check failed. Honeycomb's scoring formula is not published, so this is the simplest version, not a copy; and its own caveat applies, that very-high-cardinality fields "may not have a meaningful 'baseline'" blog-ai-bubbleup, so ids should be left out of the ranking.

4. SLO thinking without SLO alerts

Honeycomb. An SLI is a per-event function that "returns true (success), false (failure), or null (not applicable)" docs-sli, and SLOs count events rather than time windows, so "a bad minute where 50% of the events fail but only four events were seen won't alert you" blog-budget-rate.

For Guildmaster. Define a few SLIs over register rows, as true, false or null: an exchange answered within a minute; a posting done right first time; an Adventurer run whose check passes. Report each as a ratio over the last 28 days in gm stats. Do not build burn alerts: Honeycomb's own sums say "an SLO of 99.9% needs a minimum level of traffic of a few tens of thousands of events a day to be meaningful" blog-slo-challenges, and the patron produces tens. A target like 80% over four weeks is meaningful at that volume; 99.9% is noise.

5. Span events for repeats, and the GenAI names Honeycomb reads

Honeycomb's advice is to record repeated sub-occurrences as span events rather than overwrite one field docs-add-context, which is what the design already does for retries, compactions and Stop-guard give-ups. For agents, Honeycomb's Agent Timeline needs gen_ai.conversation.id, gen_ai.agent.name and gen_ai.operation.name on every span, and recommends keeping prompts and completions in span events "where your OTel Collector can filter them" and not sampling GenAI telemetry docs-agents. The design's invoke_agent spans already carry all three, but Honeycomb wants the conversation id on every span: "All spans in a conversation must have a gen_ai.conversation.id" docs-agents. Copying it onto every span of a turn on export, in build slice 4, lets any viewer that follows the conventions group a Party Leader's turns, Honeycomb's or not.

6. Test the pipeline locally, the way Honeycomb tells agents to

Honeycomb's own skill for coding agents verifies instrumentation with "a local OTel Collector ... without needing a live Honeycomb account or sending data to a remote backend", using the Collector's debug exporter agent-skill-local. That is a ready-made smoke test for slice 2's loopback collector (Build plan): point Claude Code at 127.0.0.1, run the debug exporter to a file, and assert the expected span names arrive.

7. Watch yourself with yourself

Honeycomb runs a dogfood copy that watches production, and a kibble copy that watches dogfood blog-m6g, and it tags every Lambda invocation with the query that caused it so cost is attributed to its cause blog-aws-costs. The design's equivalents are gm's own guild.hook and guild.notice spans and guild.cost.usd per posting and role; keep tracing gm itself in the same register, so a slow hook shows up in the same waterfall as a slow model call.

What not to copy

Machinery for a scale Guildmaster will not reach

  • A custom column store, Kafka, S3 tiering, Lambda fan-out. Each answers a problem of the right-hand bars above; at a few million rows a year, one SQLite file on the patron's laptop is enough inferred.
  • Approximate aggregates. t-digest and HyperLogLog trade exactness for speed at billions of rows docs-query-build; exact SQL is cheap at thousands.
  • Datasets and environments. Honeycomb splits data by service.name and walls environments apart docs-resource-structure; one register, with guild.focus as an attribute, needs neither.

Choices that conflict with Guildmaster's principles

  • Sampling and Refinery. Sampling exists to cut cost and storage; it makes counts estimates, and Honeycomb itself says not to sample GenAI telemetry docs-agents. Keep every span.
  • 60-day retention. Honeycomb deletes events after 60 days docs-usage; the register keeps spans forever, as the design specifies.
  • A hosted backend. Even Private Cloud is a multi-service AWS deployment docs-pc-arch; the design's principle 5, local by default, rules both out.
  • Paging alerts. Triggers and burn alerts serve on-call teams; one patron reading gm stats needs neither.

Could any part run locally?

Honeycomb itself, no. Its open-source pieces, yes, but none is useful on its own, because each either feeds Honeycomb or samples for it.

What this suggests for the tracing design

Proposals for the patron, in the order the build plan would meet them; none changes the design's storage ranking, its local-only rule or its refusal to sample.

  1. Slice 1: the span table keeps fixed columns for identity and time, and one JSON column for attributes; each span is written once, when it ends.
  2. Slice 1: gm stats reports three SLIs as 28-day ratios, with no alerts.
  3. Slice 1 or later: gm stats --compare <selection>, the BubbleUp query above.
  4. Slice 2: a local Collector with the debug exporter is the first smoke test of Claude Code's telemetry.
  5. Slice 3: the writ hash and the camp's commit go on every span of an Adventurer run.
  6. Slice 4: the export puts gen_ai.conversation.id on every span of a turn, beside the gen_ai.agent.name and gen_ai.operation.name the design already has.
