Honeycomb, as a C4 model

A study of Honeycomb, the hosted observability service at honeycomb.io: what it does, how it is built as far as public evidence shows, what the value in it is, and what Guildmaster's tracing design can borrow from it.

What Honeycomb is

Honeycomb is a hosted service that stores telemetry as structured events and lets engineers query them interactively. A query can group or filter on any attribute, "no matter how high its cardinality", and a dataset can have thousands of columns docs-high-card. The docs promise results "on terabytes of raw event data at sub-second to low-second query times" from a "purpose-built columnar store" docs-intro. Traces, logs and events all land in that store as events docs-logs. Time-series metrics have their own metrics dataset since 2026 docs-metrics.

The company is Hound Technology, Inc. pricing. Christine Yen, a developer, and Charity Majors, an operations engineer, founded it in 2016 manifesto-2026. The two met at Parse, which Facebook acquired founderstalk-86. Inside Facebook, an internal tool called Scuba let Parse "slice and dice on any dimensions in basically real time", which got Parse's backend under control corecursive-19. Majors calls Scuba "famously the inspiration for Honeycomb" charity-one-difference. Majors was chief executive for the first three years, and then the two swapped: Yen is CEO, Majors CTO founderstalk-86 team-page.

It is software as a service. Since November 2025 there is also Honeycomb Private Cloud, which "uses the same architecture and codebase as Honeycomb SaaS" but runs in the customer's own AWS account docs-private-cloud pr-private-cloud. There is no edition that runs on a laptop; Lessons for Guildmaster covers what does.

The problem it solves

The docs give two terms. "High cardinality" means "many possible values for a single attribute", such as a user id. "High dimensionality" means "many different attributes attached to events" docs-high-card. Metrics systems handle both badly: every new value of a tag is a new time series, so teams leave out the very attributes, such as a customer id or a build id, that would explain an incident. Honeycomb's own words are that per-time-series pricing "penalizes high-cardinality data and forces teams to leave out vital context like customer IDs" pr-2026-03.

Honeycomb's answer is to keep one record per unit of work, with as many attributes as the code can attach, and derive every view from it. Majors named this split in 2024. In her account, "observability 1.0" is the "three pillars" generation of metrics, logs and traces, with "many sources of truth". "Observability 2.0" has "one source of truth, wide structured log events, from which you can derive all the other data types" charity-version charity-one-difference. Yen put the same idea as a question: "what is a metric, if not logs that have been aggregated along a single dimension? What is a trace, if not structured logs tied together into a useful hierarchy?" blog-features-2022.

Pricing model

Honeycomb charges by events, not by hosts, seats, gigabytes or cardinality. Every plan has unlimited seats and unlimited querying pricing. "Honeycomb counts a trace that contains 150 spans as 150 events", and each OpenTelemetry span event and link counts as one too docs-usage pricing. An event may be up to 1 MB with at most 2,000 columns pricing. Events that Refinery or an SDK samples away before sending are not counted docs-usage. Events and logs are kept 60 days; time-series metrics 13 months by default, though the pricing FAQ says 60 days docs-usage pricing.

Honeycomb's pitch against other models is that it charges "by event volume rather than by host or ingested GB" pricing; its own Pro bill still rises with every span sent.

The value in it

What Honeycomb and its customers claim

These are vendor numbers, not independent measurements. A Forrester study that Honeycomb commissioned reported a three-year return of 296% for a composite organisation blog-forrester. An IDC study it promotes reports users "79% faster to respond to and remediate performance issues" and with "45% fewer unplanned outages" idc. Case studies report root-cause time falling from about an hour to five minutes at Scribe, three tools retired at Duolingo, and a 60% cut in median time to first token for Intercom's Fin agent cs-scribe cs-duolingo cs-intercom. Its company values put the design stance plainly: "Be like our storage engine: 99% right in milliseconds is better than 100% right in an hour" about-page.

This site's reading inferred

From the documented mechanisms on the following pages, the value comes from five things working together:

  1. Questions do not have to be known in advance. Raw events stay queryable by any attribute, so a new question needs no new metric, index or deploy. That is what "unknown unknowns" tooling means in practice.
  2. Attributes are free; events are the cost. Pricing by event count, not cardinality or column count, rewards putting more context on each event, which is exactly what makes the first point work.
  3. BubbleUp turns "why are these slow?" into a ranked list. Comparing a selection against its baseline on every dimension replaces guessing which attribute to group by.
  4. Alerts and dashboards read the same events as debugging. SLOs, triggers and boards are queries over the same store, so the alert that fires and the investigation that follows see identical data.
  5. One store means one bill and no correlation step. A trace is spans with a shared id, not a separate product joined to logs and metrics afterwards.

The costs are just as structural. It is a hosted service: data leaves the customer's network unless they run Private Cloud in their own AWS account. Every span is billed, so cost grows with traffic, and large users sample, which loses exact counts. The per-event rate more than doubled in 2026. Retention is 60 days.
