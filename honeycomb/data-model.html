Data model

Events, spans and traces

Honeycomb has one record type, the event, and builds everything else from it: a span is an event with trace fields, a trace is the events that share a trace ID, a log is an event with a body. This page sets out the containers they live in, the fields that matter, the limits, and the query semantics on top.

Read on 2026-10-02 from Honeycomb's docs, whose pages carry a modification date rather than an authored one.

The event

"An event is a structured record of a single unit of work." documented docs-resource-structure "Every field in an event is labeled and indexed automatically, which means Honeycomb can filter, group, and aggregate on any field without knowing about it in advance" docs-resource-structure; a dataset's schema is simply "the set of fields Honeycomb has seen across all events sent to that dataset" docs-resource-structure. Types are inferred and can be changed; a value that cannot be coerced "will be set to 0 instead of being dropped" docs-dataset-structure.

Honeycomb's instrumentation advice is to make events wide: "events should be wide because they can contain many different fields. ... One of the most common Honeycomb use cases is to send one event for each HTTP or RPC request" docs-instrumentation. In 2017 Majors put it more sharply: "Any aggregation that is performed at write time is actively harmful", and "each event should be as wide as possible, with as many high-cardinality dimensions as possible" talk/blog wb-best-practices. The pattern Honeycomb uses itself: "When a request enters a service, Honeycomb initializes a map and pre-populates it with everything known or inferred about the request. When the request is ready to exit or error, Honeycomb ships it off in one arbitrarily wide structured event" blog-structured-events. In 2026 "a typical environment has well over a hundred dimensions on its core spans" blog-ai-bubbleup.

Every field there can be grouped and filtered on. user.id and app.build_id are the high-cardinality ones a metrics system would refuse, and they are the ones that answer "which users and which build?" during an incident. Repeated sub-occurrences, such as each retry in a loop, belong in span events rather than overwriting a field docs-add-context.

Teams, environments, datasets

  • Datasets are created by sending. Honeycomb uses "the service name in your instrumentation as the Dataset's name. Once created, Dataset names are permanent" docs-datasets-manage. A span with no service name lands in unknown_service docs-sending-issues.
  • Service datasets and general datasets. "The events in a Service Dataset represent distributed tracing spans"; other events such as deploys or logs go in general datasets docs-organizing-data. Instance detail belongs in fields, "rather than the name of the service itself" docs-organizing-data.
  • A trace spans datasets but not environments. "All the events in a trace must be within the same environment in order to render correctly" docs-organizing-data.
  • Keys follow the hierarchy. Ingest keys send to one environment and cannot be changed after creation; configuration keys manage its boards, triggers and SLOs; management keys act on the team docs-resource-structure docs-api-keys.
  • History. Environments and Services arrived on 2022-03-29 for new teams, and existing teams became "Honeycomb Classic", datasets only talk/blog changelog-es. An in-place migration now converts Classic without re-instrumenting, and newer features, Honeycomb Intelligence and the Service Map among them, need environments docs-es-in-place.

Queries over events

A query is SELECT (once labelled VISUALIZE), WHERE, GROUP BY, ORDER BY, LIMIT and HAVING; leaving SELECT empty returns raw events documented docs-query-build. As JSON, which is also how a query is shared in a link docs-share-query:

{
  "time_range": 7200,
  "calculations": [{"op": "HEATMAP", "column": "duration_ms"},
                   {"op": "P99", "column": "duration_ms"}],
  "filters": [{"column": "service.name", "op": "=", "value": "checkout"}],
  "breakdowns": ["http.route"],
  "orders": [{"op": "P99", "column": "duration_ms", "order": "descending"}],
  "limit": 100
}
  • Calculations: COUNT, CONCURRENCY, SUM, AVG, COUNT_DISTINCT, MAX, MIN, percentiles from P001 to P999, HEATMAP, RATE_AVG, RATE_SUM and RATE_MAX; a query with none gets COUNT docs-query-spec. Percentiles are t-digest estimates and COUNT_DISTINCT a HyperLogLog estimate; "events that do not have a relevant attribute are ignored" docs-query-build.
  • Shape: 100 rows by default and 1,000 at most in the UI; graphs draw the top 50 groups docs-query-build. Granularity must lie between the range divided by 1,000 and by 10 docs-query-spec. HAVING filters on whole-range aggregates, not on time buckets docs-query-build.
  • Calculated fields, formerly derived columns, are per-event formulas such as IF($http.status_code = 200, 1, 0) * 100, evaluated "at query-time, so you can run them on historical data" docs-calc-examples docs-calc-fields.
  • Relational fields make a query trace-aware: root., parent., child., any. and none. prefixes in WHERE and GROUP BY docs-query-build. They join within a buffer of "typically around 3-10 minutes" in high-volume environments, so longer traces can be missed docs-relational.
  • Query Math combines independent query steps with a formula such as $A / $B docs-query-math.
  • The Query Data API (Enterprise) is asynchronous, covers only the past 7 days, runs at most 10 seconds and 10 requests a minute docs-query-data-api.
