Sampling and its maths

Honeycomb bills and stores every event, so at volume its customers keep a fraction and let each kept event stand for the ones dropped. This page covers what a sample rate means, how the query engine weights by it, how wrong the answer can be, and how Refinery picks rates.

Read on 2026-10-02. The error chart is this site's derivation from elementary statistics, not a Honeycomb figure; everything else is cited.

What a sample rate means

A sample rate of N means one event in N was kept and the kept one stands for N: "A 'sample rate' of 100 means that for every 100 requests, we capture a single event and indicate that it represents 100 similar requests" documented repo-dynsampler. Each span carries it: "each span in a trace is given a SampleRate attribute that represents N when you only sample 1/N traces. This allows Honeycomb to weight counts to compensate" docs-sampled-data. On the Events API it is the integer samplerate, defaulting to 1, "meaning 'not sampled'" docs-events-api. For OTLP, Honeycomb's translator reads a sampleRate (or SampleRate) span or resource attribute and removes it; failing that, it derives the rate from the W3C tracestate threshold ot=th repo-husky. When that threshold implies a fractional count such as 10.8, it returns 10 or 11 at random in the right proportions, "so the expected value matches" repo-husky.

How queries weight by it

The query engine multiplies at read time documented docs-sampled-data. With k kept events, each with rate Ni and value xi:

COUNT          ≈  Σ Nᵢ
SUM(x)         ≈  Σ Nᵢ · xᵢ
AVG(x)         ≈  Σ Nᵢ · xᵢ  /  Σ Nᵢ
P99(x)         ≈  the value below which 99% of the weight Σ Nᵢ lies
COUNT_DISTINCT    not corrected: a HyperLogLog estimate over the values present

The docs' own example: two traces sampled at 10, with durations 200 ms and 1,100 ms, give COUNT = 2 × 10 = 20 and AVG = (200 · 10 + 1100 · 10) / (10 + 10) = 650 ms; "sample rate correction applies to SUM and percentile aggregations as well", but "COUNT_DISTINCT operator does not compensate for sampling rate" docs-sampled-data. Usage Mode turns weighting off and exposes the Sample Rate field, so a team can see what it actually stores and pays for docs-sampled-data docs-usage. That heatmaps are weighted is not stated in the docs; a 2025 post says "every single datapoint will be automatically corrected for sampling", which this site reads as including them inferred blog-living-future.

How wrong can it be?

The rule of thumb that falls out, about 1/√(kept events), is Honeycomb's own advice in other words: "don't be afraid of high sample rates. Instead, what's important is to have enough values remaining in order for the sampling to be accurate" talk/blog blog-refining-sampling. Rare things are where it bites. Honeycomb points SLO users to an external sampling-error calculator, warning that it "gives us an estimation" blog-sampling-slos, and its staff recommend: "Never sample traces that contain errors or exceed our threshold for duration, because we don't want our Honeycomb triggers and SLOs unduly impacted by sample rate amplification" blog-tuning-dynamic. The docs suggest considering sampling once "your services generate 1000 or more traces per second" documented docs-sampling-guidelines, and the agent-observability guide says not to sample GenAI telemetry at all docs-agents.

Head against tail

Honeycomb calls head sampling "a blunt instrument" and suggests combining both at extreme volume docs-sampling-guidelines. When both run, Refinery multiplies the incoming rate into its own, so "if you use both, Refinery takes that into account" refinery-readme collect/collect.go:563-590. One subtlety the docs do not raise: the hashes differ, so a head sampler's keep decision and Refinery's deterministic decision are independent rather than nested inferred.

Dynamic sampling, worked through

Refinery's dynamic samplers come from dynsampler-go. Every window (30 s by default for DynamicSampler) it counts spans per key, a key being the values of chosen fields such as status code and route, then documented avgsamplerate.go:112-182 keyCalculation.go:9-56:

goalCount  = Σ count(key) / GoalSampleRate          events to keep this window
goalRatio  = goalCount / Σ log10(count(key))
goal(key)  = max(1, log10(count(key)) × goalRatio)  + unused share passed on from earlier keys
rate(key)  = 1                          if count(key) ≤ goal(key)
           = ⌈ count(key) / goal(key) ⌉  otherwise

Because each key's share grows with the logarithm of its traffic, a key with ten thousand times more traffic gets only a few times more kept events. Rare keys, typically errors, keep everything.

Two limits are visible in the code and the posts. A sampler "can't set the sample rate below 1, and it will always keep at least one of every key it sees", so many small keys make the goal hard to reach talk/blog blog-refinery-ema; and once more than MaxKeys keys (500 in Refinery) appear in a window, new keys fall back to rate 1 avgsamplerate.go:166-174 sample/dynamic.go:16-33. The EMA variants smooth counts with an exponential moving average and recompute early on a burst emasamplerate.go:179-233.

Sampling and the bill

  • "Events your application samples before sending to Honeycomb, such as via Refinery, Beelines, or other sampling methods" are not counted documented docs-usage.
  • A Free or Pro team over its limit for two months is throttled: "The Honeycomb Event API randomly accepts one of every ten events" docs-usage. Those survivors carry no adjusted rate, so counts drop tenfold inferred.
  • Data sampled away can be pulled back from the customer's own S3 archive with the Telemetry Pipeline's Enhance and "Query with Archive" docs-archive pr-pipeline-2025.
  • In September 2026 Honeycomb moved the same algorithms into an OpenTelemetry Collector processor that writes portable ot=th thresholds, criticising the stock tail-sampling processor because its "decisions are plain keep/drop with no sampling probability attached, so kept data generally can't be reweighted downstream" talk/blog blog-adaptive-tail blog-adaptive-collector.
