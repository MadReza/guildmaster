Retriever

Honeycomb's own distributed column store and query engine: how it lays events out on disk, how a query fans out across nodes and Lambda functions, and how it stays correct while being restarted every week. All of it comes from Honeycomb engineers' talks, posts and book; its code is not public.

Read on 2026-10-02. Up: Containers. Retriever's principal author is Ian Wilkes book-oe-1e; the case study in chapter 16 of Observability Engineering (2022) is the most detailed public description, and a 2024 post calls the original 2017 talk "still pretty accurate" blog-virtual-datasets.

Why a column store of its own

Sam Stokes's 2017 talk introduced Retriever as "a custom-built database inspired by Scuba", Facebook's in-memory analytics store, that "ingests events from Kafka, and chooses disk over memory, using an efficient column-oriented storage model" talk/blog strangeloop-2017. Scuba kept "data completely in memory on hundreds of servers each with 144 GB RAM" scuba-paper; Honeycomb's extra constraints were "multi-tenancy, cost to serve, and the limited resources of a startup" strangeloop-2017. The design goals in Christine Yen's 2017 deck were "read-time aggregation", the "ability to reconstruct raw rows", "flexible schemas and sparse rows", fast "best effort" reads and near-real-time behaviour yen-under-the-hood. The principle that follows: "There should be no indexes, so you don't need to decide which column is 'fast' before you start writing data" blog-column-store. Majors's own framing: "we have not written a database, we've written a storage engine" shipit-11. Engineering decisions weighs the choice.

Segments and column files

"Each column file exists on disk as an array holding, alternately, sequence numbers for each row and the column's value for each row" talk/blog book-oe-1e. Out-of-order timestamps are tolerated because each segment records its own time window rather than sorting its rows book-oe-1e. In 2017 there was "no compaction or compression" on the write path yen-under-the-hood; compression arrived with S3 tiering, first gzip and then, from 2019, a "compression-friendly file layout" with LZ4 that made reads "around three times faster" blog-secondary-storage.

When a segment closes is reported differently over the years, which may reflect changes, simplification or both:

Segments live on local NVMe for "the first few hours ... dynamic based on your write throughput", then age to S3 shipit-11. S3 keys start with "a fixed-length hash code" computed "from the dataset id, the partition id, and the segment id" to spread load; a prefix delete missing its trailing slash quietly destroyed live segments for more than two years before it was found in 2022 blog-murder-mystery.

In 2024 Retriever gained virtual datasets: environments with thousands of small service datasets were mapped into shared container datasets with a synthetic virtual_dataset column, because reading "a growing number files from a growing number of segment directories" was failing internal query-time targets. Median query time in such environments fell "from around 20s ... to around 0.2 seconds" talk/blog blog-virtual-datasets.

How a query runs

  1. Prune by time. Segment metadata is "the closest thing we have to such an index" blog-column-store.
  2. Read only what is named. A column store reads the files for the fields in SELECT, WHERE and GROUP BY and nothing else book-oe-1e.
  3. Compute at read time. "We only read at query time, we don't do any aggregation or indexing, even calculated columns are all done at query time. So we wind up being compute bound" infoq-podcast-kerr.
  4. Aggregate in mergeable form. "P99 is estimated using the t-digest algorithm"; "COUNT_DISTINCT is estimated using the HyperLogLog algorithm" documented docs-query-build. Each event's SampleRate weights COUNT, SUM, AVG and percentiles; COUNT_DISTINCT is not corrected documented docs-sampled-data. Sampling and its maths works through it.
  5. Fan out. Local segments are scanned on the Retriever nodes; "if it's in S3, we're going to use a Lambda" qcon-2022. Each Lambda "reads the data from S3, decrypts it, looks at the files just that it needs to" and aggregates; its results, capped at 6 MB, travel back through S3 when large, and "the final reduce" happens "on our persistent Retriever instances" qcon-2022.
  6. Merge and cut. One worker per group merges, then ORDER BY and LIMIT apply; graphs draw the top 50 groups regardless of LIMIT documented docs-query-build.

Lambda is "a force multiplier, with each of our own CPU cores overseeing the work of hundreds of others" blog-secondary-storage. Its numbers, from the 2022 talk: median start about 50 ms with little difference between hot and cold starts; three to four times EC2's price per CPU-second but run "100 times less, at least"; a default burst limit of 500 that AWS had to raise talk/blog qcon-2022. Honeycomb built the CONCURRENCY query operator "specifically for this case of how many Lambdas are we running at once" infoq-podcast-kerr. The query engine is "designed as a best-effort querying system which is ok with occasional incorrect answers" blog-slo-challenges, which its company values put as "99% right in milliseconds is better than 100% right in an hour" about-page. Results of an identical query over an identical time span are cached in S3 for good qcon-2022 blog-query-history.

Staying correct while nodes die

  • Two nodes per shard. "Each shard has two query nodes (in different AZs)" blog-kafka-may-2026. Because ingestion is deterministic, "parallel ingestion workers consuming a single partition must produce identical output", so one uploads and the other checks book-oe-1e. Honeycomb calls the result "not just exactly-once, but exactly-twice" blog-kafka-2026.
  • Offsets are Retriever's, not Kafka's. Retriever "cannot consume a message it has already serialized and written to the columnar store", so it checkpoints offsets to local disk instead of committing them to Kafka, which ruled out MirrorMaker's offset translation in the 2026 Kafka migration blog-kafka-2026. After the December 2025 Kafka incident it gained an offset-reset ability blog-dec-2025.
  • Replace, don't repair. A new node "needs to obtain the latest hourly full filesystem snapshot of its predecessor, along with the Kafka offset", then "replays for at most two hours"; one node is terminated on purpose every week blog-scaling-kafka. Honeycomb also keeps two Retriever clusters and switches between them as "a routine change" blog-what-comes-up.
