Refinery

Honeycomb's open-source tail-sampling proxy: the customer runs it in front of Honeycomb, it holds each trace until the trace is complete, and it then keeps or drops the whole trace. Unlike Retriever, its code is public, so this page is traced through the source at tag v3.4.0.

Read on 2026-10-02 at v3.4.0 (commit 47a9c75, released 2026-09-08) repo-refinery. Code citations link to that tag. Up: Containers, where Refinery is one of the senders.

What it is, and how it got here

"Refinery is a trace-aware tail-based sampling proxy. It examines whole traces and intelligently applies sampling decisions (whether to keep or discard) to each trace" documented refinery-readme. Head sampling decides when a trace starts; tail sampling "considers all or most of the spans within the trace", so it can keep every trace with an error or a slow root while dropping most of the healthy ones docs-sampling. Events it drops never reach Honeycomb and are not billed docs-usage.

Receiving, and finding a trace's owner

The router accepts the Events API (/1/events/ and /1/batch/) and OTLP over HTTP (/v1/traces, /v1/logs) on 0.0.0.0:8080, OTLP over gRPC when an address is configured, and peer traffic on 8081 route/route.go:262-272 route/route.go:1256-1267 config/file_config.go:86-91. A span with no trace ID is "not part of a trace" and goes straight upstream route/route.go:732-740. A span is a root when none of the parent-ID fields (trace.parent_id, parentId) has a value types/payload.go:270-273.

All spans of a trace must meet on one node. The sharder gives each peer about 50 / N + 1 pseudo-random partition hashes and, for each trace, picks the peer whose partition scores the highest wyhash(traceID, partitionHash) sharder/deterministic.go:184-195 sharder/deterministic.go:216-239. That is rendezvous-style hashing inferred, so a change in membership moves only part of the traces; it still "can temporarily cause inconsistent sampling decisions or dropped traces", which is why Honeycomb says Refinery "is not optimized for dynamic auto-scaling" and its Helm chart ships autoscaling off docs-refinery-scale helm-refinery. Spans owned elsewhere are forwarded to that peer route/route.go:782-812. Peers find each other from a static list or through Redis, where each node republishes itself about every three seconds and expires after ten internal/peer/pubsub_redis.go:19-30; "the load on the Redis server is quite light" refinery-readme.

Inside a node, a trace goes to one of several collect workers by wyhash(traceID, seed) % workers collect/collect.go:394-407, and each worker drains peer traffic first, so that the cluster never "deadlocks because peers are waiting to get their events handed off to each other" collect/collector_worker.go:162-174.

The decision, step by step

  1. Late spans first. A worker checks the decision cache before anything else; a span for an already-decided trace follows that decision collect/collector_worker.go:232-267.
  2. A new trace gets a deadline of now plus TraceTimeout, 60 seconds by default config/file_config.go:210-216.
  3. A root span pulls it in to now plus SendDelay, 2 seconds, so stragglers can still arrive; more than SpanLimit spans makes it now. The deadline only ever moves earlier collect/collector_worker.go:286-312. The 32,000 default matches "the limit for trace view in Honeycomb" config/file_config.go:215.
  4. A ticker decides. Every SendTicker (100 ms) each worker takes up to 3,000 expired traces and labels them by why: got its root, hit the span limit, or expired collect/collector_worker.go:316-369.
  5. makeDecision picks the sampler for the trace's environment (or dataset, for Classic keys), calls GetSampleRate, and records the result in the decision cache before sending collect/collector_worker.go:420-498.
  6. Kept spans carry their weight. Each span's SampleRate becomes its incoming rate times the trace's rate, and the original and final rates are written as meta.refinery.* fields collect/collect.go:563-590. Dropped traces are counted in trace_send_dropped collect/collect.go:613-620.

Only the deterministic sampler is a pure function of the trace ID. The dynamic and throughput samplers compute a rate and then keep the trace "randomly with probability 1/rate": rand.Intn(int(rate)) == 0 sample/dynamic.go:81. Honeycomb's own staff warn that dynamic samplers "are not deterministic, meaning you won't know in advance what they'll do", and that they need "no more than a few dozen (certainly <100) unique dynsampler keys" to hit their goal talk/blog blog-tuning-dynamic. The shipped default rule keeps everything: DeterministicSampler at SampleRate: 1 rules.yaml:1-6. The maths of the allocator is on Sampling and its maths.

Remembering decisions

Late spans are why Refinery remembers. Kept traces go into an LRU with their rate and reason (10,000 by default); dropped traces go into "a pair of cuckoo filters" (1,000,000), behind a three-second set of just-dropped IDs collect/cache/cuckooSentCache.go:16-21 config/file_config.go:402-405. A cuckoo filter cannot be emptied, so Refinery keeps "two filters, current and future" and swaps them; going over capacity raises the false-positive rate collect/cache/cuckoo.go:21-31. The docs size this at roughly 200 bytes per kept trace and 4 to 6 bytes per dropped one docs-refinery-configure. Nothing is written to disk: "When you restart the process all in-flight traces will be flushed ... but you will lose the record of past trace decisions" README.md:286-288.

Under pressure

  • Memory. Every 100 ms the collector compares heap use with MaxAlloc, or 75% of AvailableMemory; over budget, each worker decides its heaviest traces first collect/collect.go:259-310.
  • Stress relief. Each node's stress is the largest of its peer-queue, incoming-queue and heap scores; nodes share it over pubsub collect/stressRelief.go:413-445. With Mode set (default never), stress above 90 switches to deciding each span immediately by wyhash(traceID) ≤ MaxUint64 / 100, until it falls below 75 for at least 10 seconds config/file_config.go:420-426 collect/stressRelief.go:540-548.

Running it

Configuration is two files, config.yaml and rules.yaml, read from disk or "with an unauthenticated GET request from a URL" README.md:84-95. Honeycomb's sizing advice: linux on amd64 or arm64, 2 GB and 2 cores per node at least, "in many cases, Refinery only needs one node", and prefer "vertical scaling ... over horizontal scaling" docs-refinery-setup docs-refinery-scale. The Helm chart defaults to Redis peers, three replicas and 2 CPU / 2 GiB helm-refinery. Refinery reports on itself through Prometheus on localhost:2112 or OTLP metrics, with counters such as stress_level and trace_send_kept config/file_config.go:250-298. Honeycomb runs it internally too: production's telemetry passes "through Refinery into dogfood's Shepherd", and one rule keeps every end-to-end test trace talk/blog blog-graviton4 blog-teaching-ai-refinery.

Output always goes to the Honeycomb Events API: kept spans are posted as msgpack to {HoneycombAPI}/1/batch/{dataset} with an X-Honeycomb-Team header transmit/direct_transmit.go:749-753 transmit/direct_transmit.go:497-499. There is no OTLP exporter, so Refinery is useful only in front of Honeycomb or something that speaks its batch API inferred. Lessons for Guildmaster covers what that means for running it locally.

Where the docs and the code disagree
  • The scale page says throughput "is limited by single-thread CPU performance"; since 3.1 a node runs one collect worker per CPU docs-refinery-scale refinery-notes.
  • The docs call the worker assignment "consistent hashing"; the code is a plain modulo of a hash collect/collect.go:394-407.
  • The cluster stress level is described as a "geometric mean" in a comment and "a weighted average" in the 2.7 notes; the code computes a root mean square collect/stressRelief.go:493-530.
  • The set-up page still shows version 2.9.4 and says Redis Cluster is unsupported; 2.8 added it docs-refinery-setup refinery-notes.
